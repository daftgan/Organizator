# Organizator — Architecture et contrat JS ↔ .NET

## Vue d'ensemble

Organizator est une application de bureau Windows :

- **Hôte** : application WPF (.NET 8, `net8.0-windows`) qui affiche une seule fenêtre contenant un contrôle **WebView2** plein cadre. L'hôte gère la persistance sur disque, le lancement des sessions d'agent (Claude Code ou GitHub Copilot CLI) dans PowerShell, la lecture des fichiers de session des deux outils, le sélecteur de dossier et l'état de la fenêtre.
- **UI** : page HTML/CSS/JS **vanilla** (aucun framework, aucune étape de build) dans `src/Organizator/wwwroot/`. C'est le portage hi-fi du mockup `Mockup/design_handoff_organizator/`. Elle parle à l'hôte via `window.chrome.webview.postMessage`.

## Persistance

Dossier : `%LOCALAPPDATA%\Organizator\`

- `data.json` — `{ "version": 1, "tasks": [...], "types": [...], "convos": [...], "remarks": [...], "notifications": [...], "lastType": "k123" }`. Les champs ajoutés dans les objets des tableaux sont conservés par la normalisation : `type.keywords` contient les mots-clés de la catégorie (des objets, voir plus bas) ; `convo.keywords` contient les identifiants des mots-clés choisis et `convo.artifacts` le dernier relevé des fichiers touchés.
- `settings.json` — `{ "topCount": 3, "showBands": true, "compact": false, "defaultCwd": "", "repoDir": "", "terminal": "powershell", "termClick": "panel", "provider": "claude", "claudeModel": "", "copilotModel": "", "claudeEffort": "", "copilotEffort": "", "draftProvider": "claude", "draftModel": "haiku", "draftEffort": "", "articleEnabled": true, "articleTopics": "", "articleAiEnabled": true, "articleModel": "sonnet", "articleEffort": "medium", "windowsNotifications": true, "bitbucketUrl": "", "window": { "x", "y", "width", "height", "maximized" } }`. `provider`, `claudeModel` / `copilotModel` et `claudeEffort` / `copilotEffort` sont l'agent, le modèle et l'effort par défaut, réglés dans le dialogue Réglages : ils présélectionnent le formulaire de nouvelle conversation. Vide = réglage propre de l'outil (rien n'est passé sur la ligne de commande). `draftProvider` / `draftModel` / `draftEffort` sont ceux de la **rédaction assistée**, réglés à part : le modèle vaut pour l'agent choisi et repart à `haiku` (Claude) ou vide (Copilot) quand on en change. `repoDir` est le dossier des sources d'Organizator proposé pour envoyer les remarques ; vide = `env.repoDir` (détecté). `bitbucketUrl` est le serveur interrogé par « Mes PRs Bitbucket » ; vide = celui que l'hôte détecte (voir « PRs Bitbucket »). `articleEnabled` / `articleTopics` / `articleModel` / `articleEffort` règlent l'article du jour (Claude seulement) ; `articleAiEnabled` coupe ou rétablit la veille IA, qui partage le modèle et l'effort. `windowsNotifications` (vrai par défaut) coupe ou rétablit les notifications Windows (voir « Notifications »). `termClick` (`panel` par défaut, ou `terminal` ; toute autre valeur redevient `panel`) dit ce que fait le clic sur l'icône de console d'une carte (voir « État des sessions »). `whisperEnabled` (micro des zones de saisie), `whisperAuto` (transcription d'office des enregistrements joints), `whisperModel` (`base`, `small` par défaut, `large-v3-turbo-q5_0`) et `whisperLanguage` (`fr` par défaut, `en`, `auto`) règlent la dictée (voir « Dictée et transcription »).
- `copilot-models.json` — cache du catalogue Copilot : `{ "fetchedAt": ms, "models": [{ "id", "name", "usage", "price", "enabled" }] }`, rafraîchi par la sonde ACP (voir « Sessions GitHub Copilot CLI »).
- `article.json` — article du jour : `{ "version": 1, "current": article | null, "history": [article…] }` (30 précédents au plus, le plus récent d'abord), écrit par `DailyArticle` ; voir « Article du jour ».
- `article-ai.json` — veille IA, même forme, écrit par le `DailyArticle` du fil `ai` ; voir « Article du jour ».
- `finding-chats.json` — discussions sur les constats de revue : `{ "version": 1, "chats": [chat…] }` (300 au plus, les moins récentes s'en vont), écrit par `FindingChat` seul ; voir « Discussion sur un constat ».
- `claude-models.json` — cache du catalogue Claude : `{ "fetchedAt": ms, "models": [{ "id", "name", "createdAt" }] }`, lu sur `GET /v1/models` de l'API Anthropic (voir « Sessions Claude Code »).
- `attachments\<tâche>\` — copies des pièces jointes d'une tâche (fichiers, images collées, `texte-<id>.txt` des blocs de texte), servies à l'UI sous `https://attach.organizator/` ; voir « Pièces jointes ».
- `whisper\` — modèles Whisper (`ggml-<modèle>.bin`, `.part` pendant un téléchargement) et DLL natives de whisper.cpp extraites de l'exécutable (`runtime-<version>\runtimes\win-x64\`) ; voir « Dictée et transcription ».
- `learning.json` — Révizator : le modèle de l'apprenant (`{ version: 1, subjects: { en: … } }`), écrit tel quel par l'UI (`learnSave`) ; l'hôte ne l'interprète pas (atomique, `.bak`, 20 Mo au plus). Voir « Révizator ».
- `learning\` — Révizator : `lessons\`, `exercises\`, `toeic\`, `sw\` (un `<id>.json` par document généré), `audio\<id>.wav` (enregistrements gardés), `news.json` (cache du menu du jour) ; servi sous `https://learn.organizator/`.
- `tts\` — synthèse vocale : `runtime-1.13.8\` (`onnxruntime.dll`, `sherpa-onnx-c-api.dll`, extraites du paquet NuGet), `kokoro-v1_0\` (`model.onnx`, `voices.bin`, `tokens.txt`, `lexicon-us-en.txt`, `lexicon-gb-en.txt`, `espeak-ng-data\` réduit à 9 fichiers ; `.part` pendant un téléchargement), `cache\<2>\<clé>.wav` (phrases synthétisées, 500 Mo au plus, servies sous `https://tts.organizator/`) ; `runtime-1.13.8.remove` = runtime supprimé pendant que ses DLL étaient chargées, effacé au démarrage suivant. Voir « Synthèse vocale ».
- `probe\` — dossier de travail de la sonde ACP (vide).
- `launch\<sessionId>.ps1` — scripts de lancement générés (peuvent être supprimés à tout moment)
- `www\` — copie extraite des ressources web embarquées (réécrite à chaque démarrage)

Écriture atomique : écrire dans `data.json.tmp`, puis `File.Move(tmp, data.json, overwrite: true)`. Conserver `data.json.bak` (copie de la version précédente) avant chaque remplacement. À la lecture, si `data.json` est corrompu, tenter `data.json.bak`.

L'ordre du tableau `tasks` **est** la priorité, et c'est aussi l'ordre affiché : rien n'est trié au rendu. Une tâche terminée (`done`) reste donc là où elle était — elle prend `✓` à la place de son numéro, n'occupe aucun rang et n'ouvre aucune bande de priorité (celles-ci sont posées par les tâches actives) ; son bouton ↓ (`move-bottom`) la range en fin de tableau quand on le décide. `move-bottom` et `remove-task` ne sont rendus que sur une tâche cochée : une tâche encore en file ne se supprime pas, il faut d'abord la terminer. `removeTask` le vérifie aussi de son côté (une carte rendue avant le décochage ne doit pas pouvoir effacer la tâche). `convos` ne contient plus de messages : la conversation vit dans l'outil ; l'hôte lit le fichier de session pour fournir titre, nombre de messages, date et transcription en lecture seule. Une `convo` sans `provider` (données antérieures) est une session Claude. Les conversations du carnet de remarques portent `taskId: "__feedback__"`, l'identifiant d'une tâche virtuelle que l'UI ne liste jamais.

**Sous-tâches.** `task.parent` désigne la tâche parente, sur un seul niveau : une sous-tâche n'en a pas, et `regroupTasks` (appelé par `normalize` et par `commit`) détache toute tâche dont le parent manque ou est lui-même une sous-tâche. Il remet aussi chaque sous-tâche derrière son parent, dans l'ordre relatif où elles sont, si bien que le tableau `tasks` reste plat et que son ordre reste la priorité, sous-tâches comprises. `visibleTasks` filtre par groupe : la recherche montre tout le groupe dès qu'un de ses membres répond, et une sous-tâche n'apparaît jamais sans son parent. Au rendu (`renderList`), seules les tâches de premier niveau prennent un rang, comptent pour `topCount` et ouvrent les bandes ; une sous-tâche se numérote sous son parent (`3.1`, `3.2`, ✓ si terminée), sa carte porte `is-sub` (retrait, filet) et celle du parent une pastille `sub-chip` (terminées / total, `subtaskProgress`). Cette pastille est un bouton (`toggle-subs`) qui bascule `task.collapsed` : `subsFolded(t)` — vrai si le parent porte `collapsed`, a des sous-tâches et qu'aucune recherche n'est en cours — fait écarter ses sous-tâches par `visibleTasks`. Replié (`is-folded`, chevron tourné, `aria-expanded="false"`), le parent reprend l'état des sessions de ses sous-tâches : `bestState` dans une pastille `sub-st` de l'avancement, et `is-asking` dès que l'une pose une question. `normalize` ne garde `collapsed` que s'il vaut `true` ; `addFromComposer` déplie le parent d'une sous-tâche créée ; `dropNow` pose une tâche lâchée juste sous un parent replié **après** son groupe, au premier niveau, au lieu d'en faire une sous-tâche invisible. Le bouton ↳+ (`add-sub`, sur les tâches de premier niveau seulement) et le trou au-dessus d'une sous-tâche (`data-gap-parent`) ouvrent le dialogue en mode sous-tâche (`ui.composerParent`, catégorie du parent proposée, pas d'import de PRs) ; `addFromComposer` pose la nouvelle tâche dans le groupe — après la tâche visée si elle en fait partie, sinon en dernier. Glisser-déposer (`dropNow`) : un parent emmène ses sous-tâches et reste de premier niveau, posé avant ou après le groupe visé ; une tâche seule lâchée avant ou après une sous-tâche en devient une (même parent), lâchée juste sous la carte d'un parent qui en a devient sa première sous-tâche, lâchée avant une tâche de premier niveau, après un groupe entier ou sur le trou du bas (`ui.overTail`) elle est de premier niveau. `move-bottom` descend un parent avec son groupe, une sous-tâche en bas de sa fratrie ; `remove-task` sur un parent (terminé, comme toute tâche qu'on supprime) détache ses sous-tâches, qui restent dans la file à leur place.

Un mot-clé sans `team` ni `agents` (tout ce qui précède les équipes) se relit tel quel : équipe absente, case décochée. Un agent sans `model` ni `effort` se lit « comme l'agent principal », ce qui est aussi le défaut d'un agent neuf. Décocher la case n'efface pas les agents — ils restent en sommeil, prêts à resservir —, et un agent sans nom est une ligne en cours de saisie : elle se garde, mais ne part pas dans le contexte.

Données antérieures aux mots-clés-objets : un `type.keywords` de chaînes devient une liste d'objets (nom repris, `desc` et `prompt` vides, identifiant attribué), et le `convo.keyword` d'une conversation — un seul mot, sous son nom — devient un `convo.keywords` d'un élément. La conversion se fait à la lecture (`normalize`, côté JS) : `keywordIdsFor` accepte indifféremment un identifiant ou un nom, et ne garde que les mots-clés que la catégorie de la tâche porte encore.

`AgentArtifacts` lit les événements JSONL sans suivre les chemins simplement cités dans le texte : il retient les chemins explicites fournis aux outils d'écriture ou dans un patch (`Write`, `Edit`, `Delete`, etc.), normalise les chemins relatifs au `cwd` (formes Git Bash `/d/…` et `~/` comprises) et déduplique par fichier. Le relevé est **incrémental** : pour chaque transcript, l'hôte garde l'octet atteint (`JsonlTail`) et les fichiers trouvés jusque-là, si bien qu'une écriture n'est payée que pour les lignes qu'elle ajoute. Une session d'équipe cumule des dizaines de Mo de transcripts : les reparser en entier à chaque ligne d'un coéquipier coûtait ~160 ms par passage et par session, contre ~20 ms désormais. Un transcript réécrit ou raccourci est relu du début, un transcript de sous-agent disparu emporte ses fichiers. Trois sources, appliquées dans l'ordre des horodatages pour que le dernier passage sur un fichier dise son action et son auteur :

- le transcript principal, sidechains comprises ;
- les transcripts des **sous-agents** (`ClaudeSessions.GetSubagentsDir` : `<cwd encodé>\<sessionId>\subagents\*.jsonl`, nom lu dans le `.meta.json` voisin, porté par `agent`) — sans eux, un rapport écrit par un coéquipier n'apparaissait nulle part. L'empreinte du cache couvre donc le fichier de session **et** ces transcripts (nombre, taille cumulée, date la plus récente) : un coéquipier qui écrit ne touche pas au fichier de la session ;
- les **commandes shell** (`ShellWrites`, outils `Bash`, `PowerShell`, `powershell`, et tout nom contenant `shell` ou `terminal`, commande lue dans `command` / `cmd` / `script`, même encodée en JSON dans `arguments`) : redirections `>` / `>>` (hors `2>`, `&>`, `>&1`, `/dev/null`, `$null`), `tee`, `cp` / `mv` / `copy` / `Copy-Item` / `Move-Item` (destination), `Out-File` / `Set-Content` / `Add-Content` / `New-Item` (sauf `-ItemType Directory`) / `Export-Csv` (`-Path`, `-FilePath`, `-LiteralPath` ou premier positionnel), et les écritures des scripts en ligne (`open(…, 'w')`, `writeFileSync(`, `File.WriteAllText(`, `Path(…).write_text(`). La commande est découpée par ligne puis sur `&&`, `||`, `;`, `|` ; un `cd` / `Set-Location` / `pushd` déplace la base des chemins relatifs des segments suivants ; les corps de here-documents (`<<'EOF'`) et de here-strings (`@'…'@`) sont sautés pour les redirections. Un chemin n'est retenu que **littéral** : sans `*`, `?`, `$`, `%`, accolades ni backtick, avec une extension d'au plus 8 caractères — une variable ou un joker vaut mieux qu'un faux fichier. L'action est `written` (`modified` pour `>>`, `Add-Content`, `tee -a`).

Le résultat est trié : chemins relatifs (sous le `cwd`) d'abord, puis les autres, chacun par ordre alphabétique.

Le même passage, sans relire les fichiers, relève deux choses de plus :

- **Les fichiers cités** (`AgentArtifact.Cited`) : dans le transcript **principal** seulement (les réponses d'un sous-agent s'adressent à l'agent principal), le texte des réponses finales — lignes `assistant` dont le `stop_reason` est `end_turn`, `stop_sequence` ou `max_tokens`, hors `isSidechain` ; côté Copilot, un `assistant.message` sans `agentId` ni `toolRequests` — est fouillé à la recherche de noms de fichiers aux extensions des rapports (`CitedName`). Le dernier segment de chaque nom, sans casse, garde l'instant de sa dernière citation ; un fichier touché dont le nom y figure porte `Cited` = cet instant. C'est ainsi que l'agent désigne son livrable (« rapport écrit dans review-UDM-1601.md ») : sur 109 conversations réelles, 705 documents détectés dont environ 70 cités, et ce sont les rapports attendus.
- **La consommation** (`SessionUsage`) : pour Claude, l'`usage` de chaque appel du modèle (`input_tokens`, `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`, `cache_read_input_tokens`, `output_tokens`, `server_tool_use.web_search_requests`, `speed`), dédoublonné par `message.id` — Claude Code écrit une ligne par bloc de contenu, chacune avec l'usage du message entier —, dans tous les transcripts de la session, sous-agents compris ; les messages `<synthetic>` sont écartés. Le coût de chaque appel est estimé par `ModelPricing` (tarif public relevé le 9 octobre 2026 ; écriture du cache 1,25 × l'entrée pour 5 min, 2 × pour 1 h ; lecture propre au modèle, 0,20 $ pour Opus 5.5, 0,25 $ pour Fable 5.1 ; mode rapide × 2 ; Haiku 5.5 au-delà de 100 000 jetons de prompt ; 10 $ les mille recherches web) ; un modèle hors grille compte ses jetons dans `Unpriced`. Pour Copilot, le dernier `session.shutdown` (cumulé sur les reprises : `tokenDetails` input / output / cache_read / cache_write, `modelMetrics`, `totalPremiumRequests`) et, en cours de session, `session.usage_checkpoint` (`totalPremiumRequests`) : pas de coût en dollars, les requêtes premium.

L'empreinte commence par `v2|` (`StampVersion`) : changer la forme de la réponse change toutes les empreintes, si bien que l'UI reçoit les listes à jour sans attendre qu'un agent écrive.

L'hôte ne trie pas ces fichiers : c'est l'UI qui les range (`artifactEntries(convs, kind)`). Les **documents** (`doc`) se reconnaissent à leur extension (`REPORT_EXT` dans `app.js` : md, txt, rst, pdf, csv, tableurs, documents, html, images), le reste est le code touché en chemin (`file`). Parmi les documents, le **rapport** (`report`, `mainReport`) est celui que l'agent a cité (`cited` > 0), hors brouillons (`isScratchPath` : un segment `.claude`, `scratchpad`, `tmp` ou `temp`, ou un `$` resté dans le chemin), et pas supprimé ; les autres sont des **documents de travail** (`work`). Une liste relevée avant le marquage (aucun `cited`) retient les documents de la session elle-même, hors brouillons. `reportsOf(convs)` dédoublonne par chemin complet et trie par citation la plus récente. L'icône de fichiers de la carte (`artifactBtnHtml`) n'est rendue que si la tâche a au moins un rapport ; un seul s'ouvre aussitôt dans le lecteur (`open-artifacts`), plusieurs (badge) ou Maj + clic ouvrent le panneau. Le panneau liste les rapports (le premier marqué « Dernier rapport », `is-latest`, quand il y en a plusieurs ; « cité » et l'heure dans la ligne), puis « N documents de travail » (`ui.artifactWorkOpen`) et « N fichiers modifiés » (`ui.artifactFilesOpen`), repliés. Les rapports de revue (`reviewReportsOf`) se cherchent parmi tous les documents hors brouillons : un `review-….md` écrit par le « rapporteur » d'une équipe reste une revue même s'il n'est pas cité. Le « Travail déjà fait » ne cite que les rapports. Un clic sur un fichier l'ouvre dans le **lecteur** (section suivante).

## Lecteur d'artefacts

Un rapport se lit **dans la fenêtre** : cliquer un fichier du panneau des artefacts ouvre un lecteur par-dessus la file et le panneau (`ui.reader`, conteneur `#reader`, rendu par `renderReader`), sans passer par un éditeur. Ses boutons gardent les autres chemins sous la main : « VS Code » (`openPath` avec `editor: "vscode"`), « Dossier » (l'Explorateur). Rien n'est persisté.

- **L'hôte rend, l'UI affiche** (`ArtifactReader`, message `readArtifact`). Le genre est déduit de l'extension, puis d'un sondage (un octet nul dans les 8 premiers Ko = binaire) : `markdown` (HTML rendu par Markdig — tableaux, listes de cases, notes de bas de page, identifiants de titres à la GitHub, liens automatiques, listes de définitions… ; le titre est le premier `#`), `table` (CSV / TSV : séparateur détecté sur la première ligne parmi `;` `,` tabulation `|`, lecture RFC 4180, 5 000 lignes au plus), `text` (bloc préformaté, échappé), `html`, `pdf`, `image` (servis tels quels, voir l'hôte virtuel), `binary` (tableur, document Office, archive… : l'UI referme le lecteur et ouvre le fichier avec l'application associée, `openPath` avec `editor: "default"`), `large` (plus de 3 Mo de texte : renvoi vers VS Code), `missing`. Le fichier est lu en partage (`FileShare.ReadWrite`) : l'agent peut être en train d'y écrire.
- **Hôte virtuel des rapports** : `https://report.organizator/` (`ArtifactReader.Host`) est mappé par `SetVirtualHostNameToFolderMapping` (`DenyCors` : images, cadres et PDF se chargent, aucun script ne peut lire ces fichiers par `fetch`) sur la **racine** du rapport courant — le dossier de travail de la session quand le fichier est dessous, pour que les liens relatifs entre rapports et vers les images tiennent, sinon le dossier du fichier seul. Un seul dossier servi à la fois ; il change avec le rapport ouvert (`BridgeHost.ServeReportRoot`, sur le fil de l'interface). Les liens relatifs du Markdown sont réécrits en URL absolues sous cet hôte (`HtmlRenderer.LinkRewriter`) ; `javascript:`, `vbscript:`, `file:`, `//hôte` et les chemins Windows absolus (`C:\…`, pris pour un schéma d'une lettre) deviennent `#`.
- **Cadre isolé** : le HTML rendu (Markdown, texte, tableau, et une image seule — `<figure class="image">`, car sous `DenyCors` la page de l'application ne peut pas charger elle-même une ressource de l'hôte des rapports, alors que le cadre, d'origine opaque, le peut) est posé dans un `<iframe sandbox="allow-scripts" srcdoc>` : origine opaque, et une CSP (`readerFrameDoc`) qui n'autorise que `fonts.css` et `reader.css` de l'application, les images de l'hôte des rapports (et `data:`), les styles en ligne (alignement des colonnes), et le seul script d'amorçage porteur d'un nonce (`READER_SCRIPT`). Le Markdown brut peut contenir du HTML — Markdig le laisse passer — sans que rien ne s'exécute ni n'atteigne l'application. Ce script reçoit le HTML par `postMessage` (`{ type: "html", html, follow }`), signale `ready`, remonte les clics sur les liens (`link`) et Échap (`close`). Un lien vers `https://report.organizator/…` ouvre l'autre fichier dans le lecteur (`followReaderLink`, bouton ‹ pour revenir : `reader.back` chaîne les lecteurs) ; `http(s):` et `mailto:` partent dans le navigateur par `openUrl` ; une ancre `#…` défile dans le cadre. Une page HTML est chargée dans un cadre `sandbox="allow-scripts"` depuis l'hôte virtuel (ses scripts tournent, sans même origine ni accès à l'application), un PDF dans un cadre sans sandbox (le lecteur PDF intégré n'y fonctionne pas). `MainWindow.OnFrameNavigationStarting` refuse aux cadres toute navigation `http(s)` hors des deux hôtes virtuels et l'ouvre dans le navigateur.
- **En direct** : tant que le lecteur est ouvert, l'UI renvoie `readArtifact` toutes les 2 s (`syncReaderPolling`, fenêtre visible) avec le `stamp` connu (taille + date, `TranscriptAccumulator.FileStamp`) ; l'hôte répond `{ changed: false }` sans relire si rien n'a bougé. Sinon le nouveau HTML est poussé dans le cadre, qui garde son défilement — ou suit la fin s'il y était : un rapport qui s'écrit se lit au fil de l'eau. `sessionsChanged` et `focus` déclenchent aussi une relecture. Le cadre n'est reconstruit que si le fichier ou son genre change (`readerKey`) : un rendu de l'application ne le touche pas, et la barre (dossier, heure, taille) est mise à jour en place.
- Le fond ne porte pas d'action ; ✕ ou Échap referment (depuis le cadre, Échap arrive par message ; les dialogues, au-dessus du lecteur, ont la priorité sur Échap).

### Vue revue

Un rapport de **revue de code** s'ouvre en plein écran sur l'inventaire de ses constats plutôt qu'en texte continu (structure de l'écran Résultats de ReviewTool : colonnes par criticité, puis un constat à la fois avec la liste à côté).

- **Hôte** (`ReviewReport.Parse`, appelé par `ArtifactReader.RenderMarkdown` sur l'arbre Markdig déjà construit) : parcourt les blocs de premier niveau. Un **constat** est un titre (niveau 2 à 6) qui porte un identifiant en tête — `C1`, `M2`, `B1` (lettres + chiffres, suivi d'un séparateur ou d'une pastille), ou un numéro `3.`, `4 —` — et une gravité : pastille avant ou après l'identifiant (🔴 ⛔ 🛑 bloquant, 🟠 majeur, 🟡 mineur, 🔵 ℹ️ ⚪ 💡 suggestion), mot en tête de titre suivi d'un séparateur ou entre crochets (`BLOQUANT —`, `[MAJEUR]`, `MINEUR (latent) ·`, `REMARQUE`, `SUGGESTION`), sinon celle de la **section** qui le contient (titre sans identifiant dont la pastille, ou le seul niveau que nomment ses mots, fixe le contexte : `## 🟠 Majeurs`, `## Problèmes MINEURS`, `## 🔴 À corriger avant fusion` ; un titre « Verdict… » n'en est pas une, le premier `#` du document non plus). Un titre numéroté sans gravité n'est pas un constat (`## 1. Contexte`). Le corps va jusqu'au titre suivant de niveau égal ou supérieur, filet final retiré. Sont extraits : la catégorie (`[Conformité]` en tête de titre, ou une ligne `Catégorie : …`), l'emplacement (`Où :` / `Fichier :` / `Emplacement :`, ou le suffixe `` — `Fichier.cs:~L117` `` d'un titre) — un paragraphe fait seulement de ces étiquettes, toutes reprises, sort du corps —, les renvois de fin de titre en gras entre crochets (`**[#755]**`, `**[hors diff — #743]**`). Chaque corps est rendu par le même pipeline et la même réécriture de liens que le document. Le **verdict** est lu hors des constats : `Verdict : 🔴 …` (titre, paragraphe ou puce, `**Verdict global** : …` compris) ou le premier bloc sous un titre « Verdict » ; celui qui s'ouvre sur une pastille l'emporte, première phrase seulement (160 caractères). Il faut **deux constats**, ou un seul si le nom du fichier contient `review` / `revue`, pour que le document soit une revue ; sinon `review` vaut `null`. Éprouvé sur les seize rapports de `D:\01-dm-umisoft` (5 à 43 constats chacun, quatre formes de titres).
- **Réponse** : `readArtifact` ajoute `review: { verdict, level, findings: [{ id, severity, title, category, where, tags, html }] }` (`level`, `severity` ∈ `blocker` / `major` / `minor` / `info`, `level` aussi `ok` ou vide ; `title` et `where` gardent le code entre accents graves).
- **UI** (`renderReview`, à la place de `renderReader` quand `reviewShown`) : `S.ui.reader.mode` vaut `review` à l'ouverture, `doc` après « Rapport complet » (`rv-doc`, bouton « Vue revue » `rv-review` pour revenir) ; `S.ui.reader.rv` = `{ sel, cat, scroll }` (constat ouvert, catégorie filtrée, défilement des colonnes), conservé par le retour d'un lien suivi. `reviewModel` normalise les constats une fois par lecture (clé unique par identifiant, tri par gravité puis ordre du rapport). Vue d'ensemble : anneau de santé (formule de ReviewTool : bloquant 30, majeur 12, mineur 4, suggestion 1 ; `max(bloquant ? 5 : 55, 100 − 0,9 × poids)`), verdict sans sa pastille, badge « n bloquants avant merge », comptes, pastilles de catégorie (dès deux catégories), quatre colonnes toujours présentes (« Aucun »). Carte : identifiant, catégorie, renvois, titre (`tickHtml` : code en `<code>`, le reste échappé), emplacement court (`reviewLoc` : premier fichier cité entre accents graves, nom + ligne). Constat : en-tête dans la page (position, Précédent / Suivant, gravité, titre, « Où » complet), corps dans un cadre isolé construit **une fois** avec la vue (même `readerFrameDoc`, message `html` avec `variant: 'finding'` → `body.finding` dans `reader.css`), liste latérale groupée par gravité. Les rendus suivants ne réécrivent que ce qui a changé (`setHtml`) et poussent au cadre le corps du constat ouvert : nouveau constat → en haut, même constat relu (le rapport s'écrit encore) → le défilement tient. Clavier : ↑ ↓ (et ← → depuis le cadre, message `key`) passent d'un constat à l'autre, Échap remonte d'un cran (constat → colonnes → fermeture) ; le cadre ne prend pas le focus à son `ready`, pour que les flèches restent à la page.
- **Discussion** : le bouton « Discuter » de l'en-tête d'un constat remplace la liste latérale par un fil de questions-réponses avec l'agent ; voir « Discussion sur un constat » plus bas.
- **Bouton de la carte** (`reviewBtnHtml`, `open-review`) : présent quand une conversation de la tâche a produit un Markdown nommé `review-…` ou `revue-…` (`REVIEW_NAME` ; les notes de mémoire `project_review_…` n'en sont pas). `reviewReportsOf` retient d'abord un fichier sous le dossier de travail (chemin relatif) plutôt qu'un brouillon écrit ailleurs, puis la conversation la plus récente, puis le nom le plus grand (les dates y sont). C'est le nom qui décide, sans lire le fichier : si l'hôte n'y trouve pas de constat, le lecteur ordinaire s'ouvre. Une tâche dont des sous-tâches ont un rapport ouvre plutôt le panneau à onglets (`open-review-group`, section suivante).

### Revues groupées

Les rapports de revue de plusieurs tâches se lisent dans un même panneau plein écran, **un onglet par tâche** : la vue revue ci-dessus, sous une barre d'onglets. Point d'entrée, `openReviewGroup(opts)` — `true` si le panneau s'ouvre, sinon `false` et le toast « Aucun rapport de revue pour l'instant » :

- `opts.parentId` → la parente (si elle a son propre rapport) puis ses sous-tâches, terminées comprises, qui ont un rapport (`reviewReportsOf(convosOf(id))[0]`, chemin figé jusqu'à la réouverture) ou une session `working` / `waiting` / `open` (onglet « Revue en cours… ») ; `opts.taskIds` → ces tâches-là, dans cet ordre ; ni l'un ni l'autre → les tâches non terminées qui ont un rapport, dans l'ordre de la file ; `opts.focusTaskId` → l'onglet ouvert d'abord (sinon le premier qui a un rapport).
- **État** : rien d'autre dans `S.ui` que `S.ui.reader`, rien de persisté. Chaque onglet a son lecteur, de la forme de `S.ui.reader` (`{ path, cwd, view, busy, error, back, mode, rv }`) plus `group` (référence partagée), `taskId`, `pending`, `token` (lecture en cours), `docY` (défilement du rapport complet) ; `group = { scope: { parentId, taskIds }, title, tabs: [{ taskId, state: 'report' | 'pending', path, cwd, r, fetched }], active, entered, prefetch }`. `S.ui.reader` désigne toujours le lecteur de l'onglet actif : `renderReview`, `reviewKey`, `rv-cat`, `rv-doc`, la relecture toutes les 2 s, `followReaderLink` et `backReader` marchent sans changement. Un lien suivi recopie `group` et `taskId` dans le nouveau lecteur (`openReader`) : la chaîne `back` reste dans l'onglet, et un fichier `binary` atteint par un lien s'ouvre dehors en ramenant au rapport (`backReader`) au lieu de refermer le panneau. `closeReader` referme tout le groupe.
- **Onglets** (`reviewGroupTabs` ; `syncReviewGroup` à chaque `renderReader`, sans jamais redessiner elle-même) : un onglet « en cours » dont le rapport paraît devient un vrai onglet, lu aussitôt s'il est actif ; un nouveau rapport ajoute le sien ; un onglet « en cours » dont la session s'arrête sans rapport s'en va, l'onglet voisin prend sa place ; plus aucun onglet → fermeture et toast « Plus aucun rapport de revue à afficher ». `renderActivity` redessine le panneau quand il est groupé : ces changements se voient sans attendre un clic.
- **Lectures** : à l'ouverture l'onglet actif, puis une lecture unique des autres, à la suite et sans empreinte (`prefetchReviewGroup`), pour que leurs pastilles disent leur verdict ; ensuite seul l'onglet actif est relu toutes les 2 s, avec `stamp`. Changer d'onglet (`reviewGroupGo`) affiche aussitôt la vue en cache et relit le rapport **en entier** : `ServeReportRoot` ne sert qu'un dossier, celui du dernier fichier lu, et une réponse `changed: false` ne le resert pas — pour la même raison, si le dernier dossier préchargé n'est pas celui de l'onglet actif, celui-ci est relu à la fin du préchargement. `loadReader(silent)` = `readReport(S.ui.reader, silent)` : un jeton par lecteur (`r.token`) écarte une réponse dépassée ; un lecteur quitté pendant sa lecture garde la vue reçue et repasse `busy = false` (il restait occupé, et n'était plus relu) ; seul le lecteur affiché redessine ; un onglet « en cours » n'est jamais lu.
- **Rendu** : en mode groupe, `readerShellHtml` et `reviewShellHtml` insèrent `<div class="rv-tabs-host" data-role="rv-tabs">` entre `reader-bar` et le contenu, le lecteur ordinaire passe en plein écran (`reader-backdrop rv-backdrop`, `reader is-wide`), l'animation d'entrée ne joue qu'à la première construction (`group.entered`), la clé du cadre (`readerKey`) prend `|g<taskId>`. `renderReviewTabs` ne réécrit la barre (`reviewTabsHtml`) que si son HTML change, et ramène alors l'onglet actif en vue. Onglet : `<button class="rv-tab" role="tab" data-act="rv-tab" aria-selected>` ; pastille `rv-tab-dot` teintée par `--sev` d'après `reviewLevel` (niveau du verdict, sinon le constat le plus grave ; `#2b7a4b` pour `ok` ; grise tant que le rapport n'est pas lu ; `is-pending` bat en opacité) ; libellé `task.jira`, sinon le premier ticket du texte, sinon la première ligne ; `rv-tab-n` = bloquants ; `is-done` (✓) pour une tâche terminée ; infobulle : première ligne et verdict. Dessous, `rv-tab-head` : première ligne de la tâche, `jiraChipsHtml`, `prChipsHtml` (liens `open-url`). Onglet « en cours » (`renderReviewPending`) : « Revue en cours… », « L'agent n'a pas encore écrit son rapport ; cet onglet s'ouvrira dessus dès qu'il paraîtra. » et l'état de sa session (`stateText(bestConvo(…))`).
- **Défilement repris** : les colonnes retrouvent `rv.scroll` (relevé par `keepReviewScroll` en quittant l'onglet ou en passant au rapport complet, rendu après reconstruction de la vue — vaut aussi pour un rapport seul) ; le rapport complet retrouve `docY` — le cadre envoie `{ type: 'scroll', y }` au plus toutes les 250 ms, rangé dans `S.ui.reader.docY` hors vue revue en mode groupe, et `pushReaderHtml` le renvoie en `y` au premier envoi (message `html`, appliqué quand `follow` est faux). Le corps d'un constat ouvert repart en haut.
- **Clavier** : `Ctrl + Pg↓` / `Ctrl + Pg↑` (et `Ctrl + Tab` / `Ctrl + Maj + Tab`) → `reviewGroupStep(±1)`, en boucle, depuis la page (`keydown` global, avant le bloc de la vue revue, sans dialogue ouvert) ou depuis le cadre (`READER_SCRIPT` les fait suivre en `{ type: 'key', key: 'TabNext' | 'TabPrev' }`). Pas `Alt + ← →` : en mode `--wwwroot`, `AreBrowserAcceleratorKeysEnabled` est vrai et la WebView en fait un retour arrière. ↑ ↓ ← → et Échap gardent leur rôle (Échap : constat → colonnes → fermeture du groupe) ; l'aide de la liste latérale ajoute « Ctrl + Pg↑ / Pg↓ ticket ».
- **Accès** : bouton de la carte (`reviewBtnHtml`) — une tâche dont au moins une sous-tâche a un rapport porte `open-review-group` (infobulle « Résultats des revues — 3 rapports de sous-tâches », badge `review-count` = sous-tâches relues), les autres `open-review` comme avant ; bouton **Revues** de l'en-tête (`#reviews-btn`, `open-reviews`, `renderReviewsBtn` appelée par `render` et `renderActivity`) — masqué sans rapport, badge = tâches non terminées qui ont un rapport (le nombre d'onglets), infobulle « Revues de code · 5 rapports (tâches en file) » ; « Ouvrir » du toast de fin d'une revue générale → `openReviewGroup({ parentId })` (voir « Lancement sur les sous-tâches »). Jamais d'ouverture automatique. Ces trois accès et les onglets redemandent les rapports des mêmes tâches à chaque rendu : `taskReviews(id)` (= `reviewReportsOf(convosOf(id))`) ne les calcule qu'une fois par passage de rendu (`renderPass`, qui enveloppe `render` et `renderActivity`) ; hors rendu, rien n'est retenu.

### Discussion sur un constat

Chaque constat d'une vue revue se discute avec l'agent, hors terminal : « Discuter » (`rv-chat`, dans `reviewHeadHtml`) remplace la liste latérale par un volet `rv-chat`, construit une fois avec la vue (`reviewShellHtml`) comme le cadre du constat. Une discussion par constat, identifiée par le rapport (chemin complet) et la clé du constat (`reviewModel` : identifiant, ou rang, suffixé de `′` en cas de doublon).

- **Copie du relecteur.** La première question part dans une copie de la session qui a écrit le rapport : `claude -p <message> --resume <relecteur> --fork-session --session-id <copie> --name "Discussion · C1 · …"`, lancé dans le `cwd` de cette session (sans quoi `--resume` ne la trouve pas). La copie emporte tout l'historique de la revue — ticket, diff, code lus —, la session d'origine n'est ni modifiée ni rouverte. Les questions suivantes font `--resume <copie>`. La session à copier (`reviewSourceConvo`, côté UI) est la conversation la plus récente dont `artifacts` contient le rapport ; une conversation Copilot ne se copie pas, et une session dont le fichier manque (`ClaudeSessions.GetSessionFilePath`) non plus : un **agent neuf** (`--session-id <neuf>`, modèle et effort par défaut des Réglages, `cwd` de la conversation ou dossier du rapport) reçoit alors en plus le texte de la tâche et la consigne de lire le rapport et le code. Modèle et effort d'une copie : ceux de la conversation copiée ; une discussion commencée garde les siens (`chat.model`, `chat.effort`).
- **Lecture seule.** `--tools Read,Grep,Glob,Bash --allowedTools Read,Grep,Glob --permission-mode dontAsk --strict-mcp-config` : les lectures passent partout, une commande shell ne passe que si Claude Code la juge inoffensive (`git log`, `git diff`…), toute écriture est refusée sans question (vérifié : ni `Write`, ni `echo … >`). Aucun serveur MCP : démarrage rapide (un serveur qui ne répond pas retarderait chaque question de 30 s) et rien à poster.
- **Premier message** (`FindingChat.Opening`, en français) : le rapport, l'identifiant, la gravité, le titre, la catégorie et l'emplacement du constat, puis son **Markdown tel qu'il est écrit** (`ArtifactReader.FindingSource` relit le rapport et prend le constat de même rang — `order`, vérifié par le titre ; `ReviewReport.Parse(…, markdown)` remplit `ReviewFinding.Source` de la portée `Span` du titre au dernier bloc) — un rapport écrit par un sous-agent n'est pas dans le contexte de la session principale —, les règles (répondre directement, citer fichier et ligne, lecture seule, dire franchement si le constat est faux, surévalué ou sous-évalué), enfin la question. Rien dans le prompt système : celui d'une session reprise est figé (`--system-prompt-snapshot`), et toutes les copies d'une même revue gardent ainsi le même préfixe, que le cache de l'API ne facture qu'une fois. Une première question en échec ne retient pas la copie : la suivante repart d'une copie neuve, avec le constat en tête.
- **Flux.** `--output-format stream-json --verbose --include-partial-messages`, lu ligne à ligne (`FindingChat.Feed`, événements des sous-agents ignorés) : `content_block_delta` / `text_delta` → texte en cours ; `message_start` range le texte du message précédent (`Run.Said`) — ce que l'agent a dit avant un outil reste affiché, la réponse grandit ; `assistant` / `tool_use` → étape lisible (`Describe` : « Lit Contact.cs », « Cherche « Dispose » dans src », « $ git log -3 », dossier de travail retiré) ; `result` → réponse finale (`result` ne porte que le dernier message : la réponse gardée est `Said` + `result`), erreur, coût, tours, identifiant de session. L'hôte pousse `findingChat` au plus toutes les 300 ms et à chaque étape, avec le texte rendu en HTML (`ArtifactReader.RenderFragment` : même pipeline et même réécriture des liens que le lecteur), puis `phase: "done"` quand la réponse est rangée. 10 min au plus par question, **Arrêter** (`stopFinding`) tue le processus et son arbre ; trois réponses en même temps au plus, une par constat.
- **Stockage** (`finding-chats.json`, hôte seul) : `chat = { report, finding, findingId, title, severity, sessionId (copie ; vide tant qu'aucune réponse n'a abouti), source (session copiée ; vide = agent neuf), cwd, model, effort, created, updated, turns: [{ q, a (Markdown), at, ms, cost, error }] }`, 60 tours au plus. L'hôte rend chaque réponse en HTML à la lecture (`html`, jamais stocké). « Nouvelle discussion » (`forgetFinding`, deux clics dans les 4 s) retire la discussion ; le fichier de la copie reste sous `~/.claude/projects`, comme toute session.
- **Balayage des processus** : un `claude … --resume <relecteur> --fork-session` ne rouvre pas la session du relecteur — `AgentProcessScanner` ignore l'identifiant de `--resume` quand la ligne de commande porte `--fork-session`, sans quoi la conversation de revue passerait pour « en cours » le temps d'une question (et un lot de revue générale ne finirait pas).
- **UI** : `fcStore` (par rapport en minuscules : `chats`, `runs` — réponses en cours, mises à jour par `findingChat` —, `doneAt`, `stopping`) est chargé par `getFindingChats` au premier rendu de la vue (`ensureFindingChats`) et après chaque `done` ; `fcDrafts` garde le texte en cours de saisie par constat (rien de persisté côté page). Le fil est posé dans un second cadre isolé (`rv-chat-frame`, même `readerFrameDoc`, message `html` avec `variant: 'chat'` → `body.chat` dans `reader.css`) : les réponses sont le Markdown de l'agent et n'atteignent pas la page, les questions sont échappées. Un fil de plus (question, autre constat) ramène en bas (`y` très grand), une réponse qui s'écrit garde la lecture en place (`follow`). La zone de saisie, l'en-tête (agent, modèle, effort) et l'état (« Lit Contact.cs… · 23 s », horloge à la seconde sans redessiner) restent dans la page. Clavier : Entrée envoie, Maj + Entrée passe à la ligne, Échap (dans la zone ou ailleurs) referme d'abord la discussion — `reviewKey` remonte désormais discussion → constat → colonnes → fermeture ; les flèches du cadre de discussion y font défiler le fil. Marques `rv-talk` (bulle et nombre de questions, clignotante pendant une réponse) sur les cartes, la liste latérale et le bouton. Une réponse arrivée alors que la discussion n'est pas sous les yeux (`fcWatching`) donne un toast « L’agent a répondu sur C1 » avec **Voir** (`openFindingChatAt`) ; pas pour une réponse arrêtée.

## Pièces jointes

Fichiers, images et blocs de texte joints à une tâche, envoyés à l'agent avec elle.

- **Stockage** (`TaskAttachments`) : tout est **copié** sous `<données>\attachments\<taskId>\` — la tâche reste complète si l'original bouge, et l'agent reçoit des chemins stables. Identifiant de tâche et de bloc vérifiés (`[A-Za-z0-9_-]`), nom de fichier assaini, doublon renommé `nom (2).ext`, 200 Mo au plus par fichier (40 Mo pour un contenu transmis en base64), un dossier refusé. Une suppression n'agit que sous ce dossier. La tâche (`task.attachments`) ne garde que la description ; `normalize` écarte un fichier sans chemin et retire une liste vide.
- **Ajouter** : bouton « Joindre des fichiers » (`addAttachments` avec `pick`, `OpenFileDialog` multiple), **dépôt** de fichiers sur une carte ou sur le dialogue Nouvelle tâche (écouteurs `dragover` / `drop` du document, actifs seulement quand `dataTransfer.types` contient `Files` et qu'aucune carte n'est en cours de déplacement ; la carte visée prend `file-over` ; ailleurs le dépôt est refusé, sans quoi WebView2 ouvrirait le fichier), **collage** (`paste`) pendant l'édition d'une carte ou dans le dialogue. La page ne connaît que le nom d'un `File` : `bridge.call(…, files)` l'envoie par `postMessageWithAdditionalObjects`, et l'hôte lit le chemin de chaque `CoreWebView2File` avant tout `await` (`BridgeHost.AdditionalFiles`, glissé dans `payload.files`). Un objet sans chemin — une capture dans le presse-papiers — est signalé dans `unresolved`, et la page l'envoie alors par son contenu (`pasteAttachment`, nommé `capture-AAAA-MM-JJ-HHhMM.png`). Un collage qui porte du texte **et** seulement des images (copie depuis Word ou Excel) reste un collage de texte.
- **Blocs de texte** (« Ajouter un texte ») : titre facultatif et contenu, édités en place dans la carte en édition ; le contenu vit dans `data.json` et l'hôte en tient une copie `texte-<id>.txt` (`writeAttachmentText`, à la création, 700 ms après la frappe, puis avant tout lancement — `flushTextWrites` — et à `organizatorFlush`).
- **Nouvelle tâche** : l'identifiant de la tâche est tiré à l'ouverture du dialogue (`ui.composerId`) pour que les copies aillent d'emblée à leur place ; « Ajouter la tâche » le reprend avec `ui.composerAttachments`, « Annuler » (ou l'import des PRs) supprime le dossier (`removeAttachments`).
- **Affichage** : sous le texte de la carte, les images en vignette — le dossier est servi par l'hôte virtuel `https://attach.organizator/` (`SetVirtualHostNameToFolderMapping`, accès `Allow`, `attachUrl` compose l'adresse à partir d'`env.attachmentsDir`) —, les fichiers et les blocs en pastilles ; un clic ouvre le lecteur d'artefacts (`openReader(path, '')`, le bloc est d'abord écrit), depuis le dialogue l'application associée. En édition, une croix sur chacune (supprime la copie, jamais l'original), les blocs dépliés, et les boutons d'ajout. La recherche porte aussi sur les noms et le texte des pièces jointes. Supprimer une tâche supprime son dossier.
- **Enregistrements** (`mediaKind` : `AUDIO_EXT` / `VIDEO_EXT`) : un fichier audio ajouté est transcrit d'office (`receiveAttachments` → `transcribeAttachment`, si `whisperAuto`), une vidéo à la demande ; la transcription devient un bloc de texte portant `source` = la pièce audio. Voir « Dictée et transcription ».
- **Envoi à l'agent** (`attachmentsPrompt`, appelé par `buildPrompt` et, quand la tâche repart dans le contexte, par `buildContext`) : les chemins complets des fichiers, et le texte des blocs recopié tant que le total tient sous `ATTACH_INLINE_MAX` (6 000 caractères : le message passe par la ligne de commande, bornée à 32 Ko avec le contexte) — au-delà, le chemin de la copie. Un enregistrement est cité « (enregistrement audio, sa transcription est jointe ci-dessous) » ou « non transcrit », sans compter parmi les fichiers à ouvrir : l'agent ne l'écoute pas, il lit sa transcription. Une sous-tâche reçoit aussi les pièces de sa tâche parente. Le formulaire de lancement ouvert suit les ajouts et retraits tant que son message n'a pas été retouché (`editAttachments`). Une reprise renvoie le contexte, pièces jointes comprises.

Deux tons dans le texte d'une carte : `taskTitleBodyHtml` rend la première ligne en titre (`.task-title`, gras, seule barrée quand la tâche est terminée) et le reste en contexte (`.task-body`, plus petit et plus pâle), lignes vides de tête retirées. La saisie ne change pas.

## Sessions Claude Code

- Lancement d'une nouvelle session : `claude --dangerously-skip-permissions --session-id <uuid> --name "<titre>" [--model <modèle>] [--effort <niveau>] --append-system-prompt <contexte> [<premier message>]` dans le dossier `cwd`. Le premier message est l'argument positionnel : claude ouvre la session et le traite aussitôt, au lieu d'afficher une invite vide.
- Reprise : `claude --dangerously-skip-permissions --resume <uuid> [--model <modèle>] [--effort <niveau>] --append-system-prompt <contexte>` dans le **même** `cwd` (Claude range les sessions par dossier de travail).
- `--model` accepte un alias (`fable`, `opus`, `sonnet`, `haiku`) ou un identifiant complet (`claude-opus-5`). `--effort` : `low`, `medium`, `high`, `xhigh`, `max`.
- La CLI n'expose aucun listing de modèles, mais l'API Anthropic en a un : `GET https://api.anthropic.com/v1/models` répond au jeton OAuth de Claude Code (`~/.claude/.credentials.json`, en-tête `anthropic-beta: oauth-2025-04-20`, le même appel d'identité que « Quotas »), avec `id`, `display_name` et `created_at`, du plus récent au plus ancien. `ClaudeModelCatalog` la garde dans le cache `claude-models.json`, rafraîchi quand il a plus de 24 h (au démarrage, en silence) ou à la demande (bouton ↻, message `refreshModels`), et compose la liste : les alias (`alias`), les modèles de l'API (`anthropic`, nom affiché, identifiant passé à `--model`), puis les identifiants déjà utilisés sur le poste que l'API ne cite pas (`used` : `~/.claude/stats-cache.json` → `modelUsage`, `~/.claude.json` → `projects.*.lastModelUsage`, typiquement les variantes `[1m]`). Sans cache — pas de jeton, jeton périmé, pas de réseau — : alias et déjà utilisés seulement, `fetchedAt` = 0, et l'erreur est rendue en clair au clic sur ↻. Les valeurs par défaut de `~/.claude/settings.json` (`model`, `effortLevel`) sont affichées dans l'option « Par défaut de l'outil ».
- Fichiers de session : `%USERPROFILE%\.claude\projects\<cwd encodé>\<uuid>.jsonl`. Encodage du cwd : chaque caractère qui n'est pas `[A-Za-z0-9]` est remplacé par `-`, casse conservée. Exemples : `D:\02-side\Organizator` → `D--02-side-Organizator`, `C:\Users\dagan.remeur\Impot` → `C--Users-dagan-remeur-Impot`.
- Format JSONL (une entrée JSON par ligne). Entrées utiles :
  - `{"type":"user","message":{"role":"user","content":"texte" | [{"type":"text","text":"..."} | {"type":"tool_result",...}]},"timestamp":"ISO","uuid":"..."}`
  - `{"type":"assistant","message":{"role":"assistant","content":[{"type":"text","text":"..."} | {"type":"tool_use","name":"Read",...}]},"timestamp":"ISO"}`
  - `{"type":"ai-title","aiTitle":"..."}` et éventuellement `{"type":"custom-title","customTitle":"..."}` — titre de la session.
  - Autres types (`mode`, `permission-mode`, `attachment`, `file-history-snapshot`, `last-prompt`, `summary`, `progress`, `system`…) à ignorer.
  - Ignorer les entrées `isSidechain: true` et les messages `user` dont le contenu n'est que des `tool_result`, ou dont le texte commence par `<` (commandes locales type `<command-name>`, `<local-command-stdout>`).
- Compte de messages = nombre d'entrées `user` (texte réel) + `assistant` (au moins un bloc `text` non vide).
- Titre = `customTitle` si présent, sinon `aiTitle`, sinon première ligne du premier message utilisateur (46 caractères), sinon « Nouvelle session ».
- État (voir « État des sessions ») : chaque ligne `assistant` porte le `stop_reason` **final** de son message API — `tool_use` tant que l'agent enchaîne des outils, `end_turn` (ou `stop_sequence`, `max_tokens`) quand la réponse est complète. Une entrée `user` texte relance le traitement, un `tool_result` le poursuit, `[Request interrupted…]` l'interrompt ; `isApiErrorMessage` et `isAbortedMidStream` terminent le tour ; `isCompactSummary` n'est pas un tour. Un `tool_use` nommé `AskUserQuestion` met la session en attente de l'utilisateur.

## Sessions GitHub Copilot CLI

- Lancement : `copilot --allow-all --session-id=<uuid> --name "<titre>" [--model <modèle>] [--effort <niveau>] -i <contexte>` dans le dossier `cwd`. Copilot n'a pas d'équivalent de `--append-system-prompt` : le contexte de la tâche est envoyé comme **premier message** de la session.
- Reprise : `copilot --allow-all --resume=<uuid> [--model <modèle>] [--effort <niveau>]` dans le même `cwd`. Le contexte n'est pas renvoyé, il est déjà dans l'historique. `--effort` : `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
- Fichiers de session : `%USERPROFILE%\.copilot\session-state\<uuid>\` (pas de classement par dossier de travail). `workspace.yaml` porte `name:` (titre donné par Copilot, ou par l'utilisateur quand `user_named: true`) et `cwd:` ; `events.jsonl` contient un événement JSON par ligne.
  - `{"type":"user.message","data":{"content":"…"},"timestamp":"ISO"}` — message de l'utilisateur.
  - `{"type":"assistant.message","data":{"content":"…","toolRequests":[{"name":"powershell",…}]},"timestamp":"ISO"}` — réponse de l'agent ; chaque entrée de `toolRequests` donne une ligne `[outil : nom]`.
  - Les événements qui portent un `agentId` à la racine viennent des sous-agents : ignorés (équivalent de `isSidechain`). Les autres types ne servent qu'à l'état de la session : `assistant.turn_start` / `assistant.turn_end`, `tool.execution_start` / `tool.execution_complete`, `permission.requested` / `permission.completed`, `abort`, `session.error`, `session.start` / `session.resume` / `session.shutdown`. Copilot écrit un `assistant.turn_end` après **chaque** appel du modèle, outils compris : la réponse n'est complète que si aucun `assistant.message` du tour ne portait de `toolRequests`.
- Compte de messages = `user.message` non vides + `assistant.message` dont `content` est non vide.
- Titre = `name` de `workspace.yaml`, sinon première ligne du premier message utilisateur (46 caractères), sinon « Nouvelle session ».
- Détection de la CLI : `copilot.exe` / `copilot.cmd` dans le PATH (en ignorant le « bootstrapper » que l'extension VS Code dépose dans `globalStorage\github.copilot-chat`, qui ne fait que chercher la vraie CLI), sinon `%LOCALAPPDATA%\GitHub CLI\copilot\copilot.exe` (téléchargée par `gh copilot`), sinon `gh copilot --` si `gh.exe` est dans le PATH. Le chemin complet est toujours écrit dans le script.
- Catalogue des modèles (`CopilotModelCatalog`) : la CLI ne l'expose que par son mode **ACP** (Agent Client Protocol, JSON-RPC sur stdio). La sonde lance `copilot --acp --no-auto-update` avec `probe\` comme dossier de travail, envoie `initialize` puis `session/new`, et lit `result.models.availableModels[]` : `modelId`, `name`, `_meta.copilotUsage` (multiplicateur, ex. `1x`), `_meta.copilotPriceCategory` (`low` / `medium` / `high`), `_meta.copilotEnablement`. Elle envoie ensuite `session/close` et ferme l'entrée standard. La CLI ne purge jamais la session vide ainsi créée : la sonde supprime son dossier `session-state\<uuid>` (seulement s'il n'a pas d'`events.jsonl`) et sa ligne `sessions` dans `session-store.db` (Microsoft.Data.Sqlite), pour qu'elle n'apparaisse pas dans `copilot --resume`. Résultat mis en cache dans `copilot-models.json` ; rafraîchi quand il a plus de 24 h (au démarrage, en silence) ou à la demande (bouton ↻, message `refreshModels`). Sans cache, la liste se limite à `auto` et aux identifiants déjà vus dans `~/.copilot` (`settings.json` → `model`, `config.json` → `recentModelIds`, `session.start` → `selectedModel`). Les valeurs par défaut de `~/.copilot/settings.json` (`model`, `effortLevel`) sont affichées dans l'option « Par défaut de l'outil ».
- Le champ libre accepte tout identifiant `[A-Za-z0-9._:/[]-]` (64 caractères max) ; le reste est refusé avant d'être écrit dans un script.

## État des sessions

Chaque conversation affiche ce que fait l'agent. L'état vient de deux sources :

- **Le transcript** (`TranscriptAccumulator.State`, calculé par les deux lecteurs pendant la lecture normale) : `working` (prompt en traitement, outil en cours), `waiting` (question posée via `AskUserQuestion`, autorisation demandée par Copilot), `ready` (réponse complète), `error` (erreur d'API, authentification), `idle` (pas encore de prompt, tour interrompu, session refermée). `stateTs` est l'horodatage d'**entrée** dans l'état : « en cours depuis » le prompt, « réponse prête à » l'heure du `end_turn`. `detail` précise l'outil en cours, le motif (`interrompue`, `fermee`, `question posee`, `autorisation demandee`) ou le message d'erreur (première ligne, 80 caractères).
- **Les processus** (`AgentProcessScanner`) : toutes les 4 s, une requête WMI `Win32_Process` (`System.Management`) liste `claude.exe`, `copilot.exe`, `node.exe` et `bun.exe` et extrait les `--session-id` / `--resume` de leur ligne de commande (environ 300 ms, sur un thread du pool). `alive` vaut `true`/`false`, ou `null` tant que WMI n'a pas répondu ou s'il est indisponible (abandon après 3 échecs, journalisé). Un changement de l'ensemble déclenche `sessionsChanged`.

- **Les agents lancés par la session** (`TranscriptAccumulator.Agents`, alimenté par `ClaudeSessions`) : un agent part par l'outil `Agent` (ou `Task`, `Workflow`) et son résultat revient aussitôt — « Spawned successfully … name: `<nom>` » pour un coéquipier, « launched in background. Task ID: `<id>` » pour une tâche de fond — si bien que la session principale peut atteindre `end_turn` avec toute son équipe au travail. Le retour se lit plus loin dans le même fichier : `<task-notification>` porte le `<task-id>` de la tâche finie, et `idle_notification` le `teammate_id` du coéquipier redevenu disponible. Un `Agent` qui a travaillé sur place (pas de `Task ID`, pas de `Spawned`) est revenu avec son `tool_result`.
- **Les transcripts des sous-agents** (`ClaudeSessions.ScanSubagents`) : Claude Code écrit celui de chaque sous-agent dans `<cwd encodé>\<sessionId>\subagents\agent-…jsonl`, avec un `.meta.json` qui donne son `name`. Un agent au travail y ajoute une ligne à chaque outil et à chaque réponse ; un agent parti sans jamais annoncer son retour (fenêtre fermée, coéquipier arrêté) n'y touche plus. `BridgeHost` croise les deux sources : passé trois minutes de grâce après son départ, un agent n'est encore compté que si son transcript a bougé depuis moins d'un quart d'heure — et un dossier `subagents` absent (autre version de la CLI) laisse le transcript principal seul juge. Reprendre une session dont la fenêtre était fermée efface son équipe d'avant (`_relaunchedAt`) : elle est partie avec la fenêtre.

**La dernière parole de l'agent** (`TranscriptAccumulator.Said`, champ `said`) accompagne cet état : le texte de sa dernière réponse, ramené à une ligne de 160 caractères, sans les lignes `[outil : …]` ni les marques de markdown (titres, puces, gras, code). Quand il pose une question (`AskUserQuestion`), c'est **la question** qui remplace cette parole — `ClaudeSessions.LastQuestion` lit l'`input` de l'outil et joint ses questions par un point médian —, puisque c'est elle qui attend une réponse. Côté Copilot, seul le texte des réponses est retenu : ses demandes d'autorisation ont déjà leur `detail`. La parole est accumulée que la transcription soit collectée ou non, et survit donc à la lecture incrémentale des résumés. L'UI la pose sous l'état, dans la liste des conversations (`.convo-said`, deux lignes au plus, teinte de l'état) et en seconde ligne de l'infobulle de l'icône du terminal.

L'UI en déduit l'état affiché : `alive === false` → « Fermée » quel que soit le transcript ; fichier absent mais processus vivant → « Ouverte » ; un transcript `ready` ou `idle` avec des agents encore au travail → « En cours » (et l'état ne passe au vert, avec toast, que lorsque l'équipe est rentrée) ; sinon l'état du transcript. Sur une carte de tâche, l'état le plus pressant de ses conversations (`waiting` > `working` > `error` > `ready` : une question posée passe devant le travail en cours, puisque c'est elle qui réclame une réponse) est porté par le **bouton terminal** lui-même : classe `is-<état>` sur le bouton (teinte et bordure) et `.btn-dot.st-<état>` posée dans son coin, l'infobulle reprenant `stateText` de la conversation concernée. En `waiting`, la pastille porte un « ? » bleu cerclé d'une onde (`halo-ask`) et la carte reçoit `is-asking`, qui la borde de bleu : cette classe regarde **toutes** les conversations de la tâche, pas seulement la plus pressante, une session pouvant travailler pendant qu'une autre attend. Ce bouton porte aussi, en haut à droite (`.term-count`), le nombre d'agents qui travaillent pour la tâche : par conversation, l'agent du terminal s'il traite un prompt (`state === 'working'`), plus les agents qu'il a lancés et qui ne sont pas revenus ; le badge disparaît à zéro, et une conversation fermée ne compte pour rien. Le clic (`open-term` → `clickTerm(taskId, shiftKey)`) suit `settings.termClick` : `panel` → `openTerm` (le panneau, sur la transcription quand la tâche n'a qu'une conversation) ; `terminal` → quand la tâche a **exactement une** conversation, `resumeConvo` sans message — l'hôte ramène sa fenêtre (ou active son onglet) si elle vit, sinon la reprend (`--resume`) — et ses notifications sont marquées lues ; avec zéro ou plusieurs conversations, `openTerm`. Maj + clic inverse le choix (`wantsTerminal`) : en mode `terminal`, c'est le seul chemin vers le panneau d'une tâche à une conversation, d'où l'on en lance une seconde. L'infobulle commence par ce que fera le clic : « Aller à son terminal » / « Rouvrir son terminal » (conversation `closed`, lue sur la conversation elle-même — `bestConvo` ignore les états hors `STATE_RANK`) suivi de « Maj + clic : le panneau », « Choisir la conversation » (mode `terminal`, plusieurs conversations), sinon « Ouvrir le terminal de l'agent ». Le réglage est la ligne « Clic sur l'icône de console » de l'onglet Agents (`term-click-panel` / `term-click-terminal`). Une seconde icône, représentant un fichier et portant le nombre de rapports, n'est rendue que si au moins un rapport a été produit ; elle ouvre la liste des artefacts sans remplacer l'accès au terminal. Quand une conversation passe de `working`/`waiting` à `ready`, l'UI affiche un toast et envoie `notify` : l'hôte fait clignoter le bouton de la barre des tâches (`FlashWindowEx`) si la fenêtre n'est pas au premier plan. La notification est aussi gardée dans la cloche, une question posée en fait autant, et hors d'Organizator elles deviennent des notifications Windows : voir « Notifications ».

### Journal d'une conversation

Le panneau d'une conversation (`panelTranscriptHtml`) montre son journal (`getTranscript` : messages `user` / `assistant`, l'hôte fusionnant les entrées assistant consécutives et écrivant une ligne `[outil : X]` par appel d'outil). Il se lit comme une conversation : en-tête par message (« Vous » / « Agent », heure `fmtTime`), vos messages dans une bulle, police de l'interface. Le texte est rendu en Markdown **par la page** (`mdBlocksHtml`, `mdInline`) : tout est échappé d'abord ; code délimité, lignes d'outils, titres, filets, tableaux, citations, listes (numérotation gardée par `value`, sous-éléments en retrait, cases ☐ ☑) et paragraphes ; code entre accents graves, gras, italique, barré ; seuls les liens `http(s)` (`[texte](url)` ou adresse nue) deviennent des `<a data-act="open-url">`, ouverts dans le navigateur — `javascript:` et le HTML brut restent du texte. Les lignes d'outils consécutives (lignes vides comprises) font une seule ligne `.msg-tools` : un nom par outil dans l'ordre d'apparition, avec son nombre (« Read ×3 »), un outil MCP par son dernier segment. Un message de l'utilisateur de plus de `LOG_FOLD_LINES` (14) lignes ou `LOG_FOLD_CHARS` (1 400) caractères se replie (`is-folded`, fondu) ; « Afficher tout » / « Replier » (`log-fold`) bascule `ui.logOpen[conversation:rang:longueur]`. Le rendu de chaque texte est gardé en mémoire (`logHtmlMemo`, 600 au plus) : le journal est relu toutes les deux secondes.

### Fraîcheur de l'affichage

Trois mécanismes bornent le délai entre « l'agent a répondu » et « la carte le montre » :

- **Lecture incrémentale** (`SessionScan`) : un fichier de session atteint plusieurs mégaoctets et grossit à chaque outil ; le relire en entier à chaque écriture coûtait ~30 ms par rafraîchissement et par session. Chaque lecteur garde, par session, l'octet où il s'est arrêté et l'accumulateur correspondant : seules les lignes ajoutées sont relues (une ligne encore sans `\n` est laissée au passage suivant). Un fichier plus court, ou modifié sans avoir grandi, fait repartir la lecture du début — comme un fichier supprimé puis recréé. Un scan par session pour les résumés, un seul pour la transcription (l'UI n'en affiche qu'une).
- **Notification** (`SessionsWatcher`) : les événements du `FileSystemWatcher` sont regroupés sur 250 ms, mais jamais repoussés au-delà d'**1 s** — un agent qui écrit sans arrêt retardait sinon la notification indéfiniment. Tampon de 256 Ko ; si la surveillance tombe (débordement) ou si le dossier n'existe pas encore (Copilot avant la première session), une reprise est tentée toutes les 15 s et `sessionsChanged` est levé dès qu'elle aboutit, des événements ayant été manqués.
- **Relecture périodique** (UI) : filet de sécurité si une notification manque malgré tout. `refreshSessions` toutes les 1,5 s tant qu'une conversation est `working`/`waiting`/`open`, 10 s sinon, 30 s fenêtre cachée ; relance immédiate au retour au premier plan. Le rendu n'est refait que si un état a changé, pour ne pas interrompre une sélection ou une saisie. La transcription ouverte est relue toutes les 2 s.

`getSessions` porte sur **toutes** les conversations à chaque `sessionsChanged`, `focus`, relecture périodique et au démarrage. L'hôte garde en cache le résumé de chaque transcript avec une empreinte taille + date (`GetStamp`) et ne redemande une lecture que pour les fichiers qui ont changé. Tout ce qui touche au disque — résumés, fichiers produits, transcripts des sous-agents (`ActiveAgents`) — se fait hors du fil de l'interface, qui est aussi celui par lequel passent les touches non imprimables de la WebView.

**Une relecture à la fois.** Trois règles, posées après qu'Organizator a saturé deux cœurs et demi au bout de quelques heures (septembre 2026) :

- `refreshSessions` ne lance jamais un `getSessions` par-dessus un autre : une demande reçue en cours de route (`sessionsChanged`, `focus`, minuteur) est retenue et servie par **une** relecture à la fin (`sessionsInFlight`, `sessionsAgain`). Délai de réponse : 60 s (`SESSIONS_TIMEOUT`), le premier relevé lisant tous les transcripts — une vingtaine de secondes disque froid.
- La boucle périodique n'a qu'**un** minuteur, toujours désarmé avant d'être réarmé (`armSessionsPoll`). L'ancienne boucle réarmait le sien à la fin de chaque relecture sans voir celui qu'un événement de l'hôte avait armé entre-temps : deux boucles tournaient côte à côte, puis trois, et au bout de quelques heures des dizaines de relectures par seconde (chacune suivie d'une sauvegarde complète et d'un rendu complet) saturaient l'hôte et la page. La relecture silencieuse du journal (`loadTranscript(true)`) ne part pas non plus par-dessus une autre (`transcriptInFlight`).
- La liste des fichiers produits ne repart que si elle a changé : l'UI renvoie pour chaque session l'empreinte reçue la fois précédente (`artifactsStamp`, en mémoire seulement), l'hôte omet `artifacts` quand elle n'a pas bougé. Elle pesait l'essentiel de la réponse (plus d'un millier de fichiers pour une soixantaine de sessions).

Ce que la relecture recopie dans `data.json` (titre, nombre de messages, date, fichiers) change à chaque ligne écrite par un agent : `saveDataLater` l'enregistre au plus toutes les 5 s, au lieu de réécrire tout `data.json` à chaque relecture ; une sauvegarde ordinaire ou la fermeture (`organizatorFlush`) l'emporte avec elle.

**La frappe d'abord.** Les rendus provoqués par une relecture (`renderActivity` : sessions, journal silencieux) ne redessinent que ce qui montre l'état des sessions — la file, le panneau, le bouton Remarques —, jamais les dialogues, qui n'en affichent rien. Ils attendent une pause de frappe : tant que le focus est dans un champ et qu'une touche a été frappée il y a moins de 1,2 s (`TYPING_QUIET_MS`), ou qu'une composition est en cours (touche morte `^`, `¨`, IME), le rendu est remis de 0,6 s en 0,6 s. Sans quoi le champ en cours de saisie était reconstruit toutes les secondes : frappe retardée, touche morte avalée, historique d'annulation perdu.

### Performances

« L'application rame, la frappe traîne » doit laisser une trace, avec sa cause probable. `PerfMonitor` (hôte) écrit dans `host.log`, sous l'étiquette `[PERF]` :

- **Le fil de l'interface.** Une sonde lui confie un travail vide toutes les 500 ms (`Dispatcher.BeginInvoke`, priorité `Send`) et mesure le délai avant qu'il le prenne. Au-delà de 250 ms, il était occupé : la fenêtre ne répondait plus, et les touches non imprimables (retour arrière, flèches, Entrée), que WebView2 soumet à l'hôte avant de les laisser à la page, attendaient avec lui. Un blocage de plus d'une seconde est noté sur le moment, avec le dernier message reçu du pont (une ligne par 30 s au plus).
- **Les messages du pont** : nombre, durée moyenne et maximale par type, de la réception à la réponse (`RecordMessage`).
- **L'interface web** : `app.js` observe les tâches longues de son fil (`PerformanceObserver` `longtask`, plus de 50 ms d'affilée), les saisies lentes (`event`, plus de 104 ms entre la touche ou le clic et l'affichage) et la durée de ses rendus, et les envoie chaque minute (message `perf`, et à `organizatorFlush`). Une tâche longue ou une saisie de plus d'une demi-seconde est notée aussitôt (`log`, niveau `perf` : ligne `[JS/PERF]`, une par 30 s au plus).
- **Le processus** : CPU en % d'un cœur, mémoire, threads.

Toutes les 10 minutes, une ligne de bilan : `[PERF] Bilan (10 min) : CPU 3 % d'un coeur, 190 Mo, 41 threads | fil UI : fluide | pont : getSessions 480 x (moy 18 ms, max 90 ms), … | UI web : 0 tache(s) longue(s), 0 saisie(s) lente(s), 310 rendu(s) (moy 9 ms, max 40 ms)`, et une dernière à la fermeture. Elle passe en `[PERF/WARN]` quand quelque chose cloche : blocage du fil de plus d'une seconde, CPU au-delà d'un demi-cœur, saisie ou tâche longue de plus d'une demi-seconde, ou plus de 2,5 `getSessions` par seconde (`emballement` : c'est le défaut décrit sous « Une relecture à la fois », qui en faisait jusqu'à trente). Pour les retrouver : `Select-String '\[PERF' $env:LOCALAPPDATA\Organizator\host.log`.

Côté page, deux règles de rendu tiennent aussi à la fluidité : les animations en boucle n'animent que `transform` et `opacity`, que le compositeur joue sans repeindre la page — l'onde des pastilles « réponse prête » et « question » est un disque posé derrière la pastille (`.btn-dot::before`, `z-index: -1`, d'où `isolation: isolate` sur `.icon-btn`). Animer `box-shadow` repeignait la page à chaque image pour chaque carte concernée : 17 % du fil principal au repos avec vingt cartes prêtes, contre moins de 1 % désormais.

## Notifications

Ce qui est annoncé à l'utilisateur est gardé, consultable après coup et, hors d'Organizator, poussé dans Windows.

- **Annonces** (`refreshSessions`) : `announce` pour une conversation passée de `working` / `waiting` à `ready` (toast « Réponse prête », comme avant), `announceQuestions` pour une conversation passée à `waiting` depuis un autre état connu (pas au premier relevé, `before` nul) — toast « Question de l'agent » ; `batchEndToast` pour la fin d'un lot de sous-tâches. Chacune enregistre une `notification` (`recordNotification`) : titre de la tâche, parole de l'agent (`saidOf`), titre de la conversation. Une conversation ne garde qu'une notification **non lue** de chaque genre — la dernière remplace l'autre —, et la liste est bornée à `NOTIF_MAX` (60). `data.json` les porte à sa racine (`DataStore.NormalizeData` recopie `notifications`) ; `normalize` écarte un genre inconnu.
- **Cloche** (`#notifs-btn`, `renderNotifsBtn`) : badge = non lues ; chaque changement du compte part à l'hôte (`badge`), qui pose la même pastille sur le bouton de la barre des tâches (`TaskbarBadge`, `TaskbarItemInfo.Overlay`, rond terracotta 32 px cerclé de blanc, « 9+ » au-delà). Son menu (`renderNotifs`, `#notifs`, position fixe sous le bouton — `placeNotifs` le replace au défilement de la page et au redimensionnement —, rendu par `render` et à chaque notification) : genre et heure, tâche, parole, conversation ; non lues teintées ; **Tout marquer comme lu**, **Effacer**, état des notifications Windows et lien vers les Réglages. Un clic ailleurs ou Échap le referme.
- **Ouvrir** (`openNotification`) : lue ; tâche disparue → toast ; lot avec rapports → `openReviewGroup({ parentId })` ; sinon le parent replié se déplie, `openTerm` puis `openTranscript` de la conversation, et `revealTask` amène la carte au centre (recherche vidée s'il le faut) et l'éclaire 1,8 s — `S.ui.flash` (`{ id, at }`) : un rendu dans la foulée reprend l'animation là où elle en était (`animation-delay` négatif, `flashStyle`) au lieu de la perdre. `openTerm` marque lues toutes les notifications de la tâche (`markTaskNotificationsRead`).
- **Windows** (`notifyOutside` → `notify` avec `toasts`, sauf réglage `windowsNotifications` coupé) : l'hôte fait clignoter le bouton et, **seulement si la fenêtre n'est pas active**, montre chaque notification (`WindowsToasts.Show`) : titre « Réponse prête · <tâche> », corps = parole de l'agent, attribution = conversation, `launch` = `n=<id>`, `tag` = identifiant de la conversation (une conversation n'en laisse qu'une dans le centre de notifications), `group` = `Organizator`.
- **`WindowsToasts`** : l'API est WinRT, appelée par son ABI COM pour ne pas passer le projet sur un framework cible `windows10.0.x` (la projection pèse ~24 Mo, l'exécutable 5) : `RoGetActivationFactory` / `RoActivateInstance`, chaînes `HSTRING` (`WindowsCreateString`), interfaces `[ComImport]` déclarées avec les trois emplacements d'`IInspectable` en tête (`IToastNotificationManagerStatics`, `IToastNotifier`, `IToastNotificationFactory`, `IToastNotification(2)`, `IXmlDocumentIO`, `IToastActivatedEventArgs`). L'AUMID `Organizator` est déclaré dans `HKCU\Software\Classes\AppUserModelId\Organizator` (`DisplayName`, `IconUri` = `notification-icon.png` du dossier de données, tiré de l'icône de l'exécutable par `PrivateExtractIcons` en 256 px), au premier affichage de chaque lancement ; l'AUMID du processus n'est pas changé, pour que la fenêtre reste groupée avec un Organizator épinglé. Le clic arrive par `add_Activated` : le gestionnaire est un objet .NET exposé en COM (`TypedEventHandler<ToastNotification, Object>`, IID `ab54de2d-97d9-5528-b6ad-105afe156530`, recalculé par l'algorithme `pinterface` des types paramétrés), qui lit `IToastActivatedEventArgs.Arguments` ; `BridgeHost` ramène la fenêtre (`SW_RESTORE` si réduite, `Activate`, `Topmost` basculé, `SetForegroundWindow`) et émet `notificationClicked`. Les 100 dernières notifications restent référencées : leur `Activated` ne part que tant que l'objet vit. Sans serveur COM d'activation enregistré, un clic après la fermeture d'Organizator efface la notification sans relancer l'application. Un échec (Windows refuse, interface absente) est journalisé une fois et coupe les notifications Windows pour le reste de la session ; la cloche continue.
- Shim : `notify` est noté dans `window.__notifies`, `badge` dans `window.__badge`.

## Consommation

Chaque conversation garde ce qu'elle a consommé (`convo.usage`, recopié de `getSessions` par `refreshSessions` sous la même empreinte que les fichiers produits, normalisé par `normalizeUsage`, persisté dans `data.json`) ; voir « Sessions » plus haut pour le relevé côté hôte.

- **Carte** (`usageChipHtml`, en fin de ligne de pastilles) : la somme (`usageOf`) des conversations de la tâche, et pour une parente de ses sous-tâches. Texte `usageText` : « ≈ 2,40 $ · 18 M jetons », « 3 req. premium · 99 M jetons » (`fmtCost` : deux décimales sous 10 $, une sous 100, aucune au-delà, « < 0,01 $ » ; `fmtTokens` : k, M, Md). Infobulle `usageTip` : la mention du tarif public (ce qu'aurait coûté la tâche facturée à l'usage — l'abonnement compte en quotas), jetons d'entrée, de sortie, lus et écrits dans le cache, requêtes premium, les quatre premiers modèles avec leur part, les jetons non chiffrés, le nombre de conversations.
- **Panneau** : le total en tête de « Conversations » (`panel-kicker-usage`), puis une ligne `convo-usage` sous chaque conversation.

## Quotas des agents

Deux cartes en tête de fenêtre montrent la part consommée des limites de chaque agent (`UsageMonitor`, message `getUsage`) :

- **Claude** (`ClaudeUsageReader`) : `GET https://api.anthropic.com/api/oauth/usage` avec le jeton OAuth de `~/.claude/.credentials.json` (`claudeAiOauth.accessToken`, en-tête `anthropic-beta: oauth-2025-04-20`), l'appel que Claude Code fait pour `/usage`. Le tableau `limits` donne `session` (5 h), `weekly_all` et `weekly_scoped` (par modèle, `scope.model.display_name`) en `percent` avec `resets_at` ; les champs historiques `five_hour` / `seven_day` / `seven_day_opus` / `seven_day_sonnet` servent de repli, et `extra_usage` ajoute une jauge s'il est activé. Le plan vient de `subscriptionType` + `rateLimitTier` (« Max 5× »). Le jeton n'est jamais renouvelé par Organizator : passé `expiresAt`, l'état est `expired` jusqu'à ce que Claude Code le rafraîchisse.
- **Copilot** (`CopilotUsageReader`) : hôte et login du dernier compte connecté dans `~/.copilot/config.json` (JSON avec commentaires, `lastLoggedInUser`), jeton OAuth lu dans le Gestionnaire d'identifiants Windows (`WindowsCredentials`, cible `copilot-cli/<hôte>:<login>`, UTF-8 ou UTF-16), sinon `COPILOT_GITHUB_TOKEN` / `GH_TOKEN` / `GITHUB_TOKEN`. `GET <api>/copilot_internal/user` (`Authorization: token …`) avec `api.github.com`, `api.<sous-domaine>.ghe.com` pour la résidence des données, `<hôte>/api/v3` pour GHES. `quota_snapshots.premium_interactions` donne `entitlement`, `remaining`, `percent_remaining`, `overage_permitted` ; `chat` et `completions` ne donnent une jauge que s'ils ne sont pas `unlimited` ; `quota_reset_date` (jour, minuit local) et `copilot_plan`.

Chaque rapport porte `status` (`ok` ; `missing` : pas de compte connecté ; `expired` : jeton périmé ou refusé ; `error` : réseau), un `message` technique ASCII, `plan`, `account`, `host` et des `bars` (`key` session/weekly/extra/premium/chat/completions, `scope`, `percent` consommé, `used`, `limit`, `overage`, `resetsAt`). L'UI porte les libellés et les messages accentués. L'hôte lit les deux en parallèle (délai 12 s), garde la dernière lecture 2 min sauf `force`, et en cas d'erreur réseau rend les jauges précédentes marquées `stale`. L'UI relit toutes les 5 min fenêtre visible, au `focus`, 2 s après l'arrivée d'une réponse (le quota vient de bouger), et d'un clic sur une carte. Aucun jeton n'est journalisé ni transmis à l'UI.

Les dialogues (nouvelle tâche, réglages) ne se ferment que par leurs boutons ou Échap : le fond (`.dialog-backdrop`) ne porte plus d'action.

Les Réglages sont rangés en onglets (`SETTINGS_TABS` : Affichage, Agents, Rédaction, Dossiers, Bitbucket), un seul affiché à la fois dans un panneau de hauteur fixe qui défile au besoin. L'onglet ouvert vit dans `S.ui.settingsTab` (mémoire de la session, pas `settings.json`) : le dialogue rouvre sur le dernier consulté. Chaque agent a sa carte (modèle + ↻, effort, provenance du catalogue) ; `renderDialogs` garde la position de défilement du panneau d'un rendu à l'autre, sauf changement d'onglet.

## PRs Bitbucket

« Mes PRs Bitbucket » (dialogue Nouvelle tâche, message `getPullRequests`) : `BitbucketPullRequests` interroge le tableau de bord de Bitbucket Data Center, `GET <url>/rest/api/1.0/dashboard/pull-requests?role=REVIEWER&state=OPEN&participantStatus=UNAPPROVED&order=OLDEST` (pages de 50, 10 au plus), avec `Authorization: Bearer <jeton>` : c'est le serveur qui filtre — PRs ouvertes où l'utilisateur du jeton est relecteur et n'a ni approuvé ni demandé des corrections. L'en-tête `X-AUSERNAME` de la réponse donne le compte (`account`), sans appel supplémentaire.

- **Accès** (`Discover`) : l'adresse vient de `settings.bitbucketUrl`, sinon du premier serveur MCP de `~/.claude.json` dont l'`env` porte `BITBUCKET_URL` (racine `mcpServers`, puis `projects.*.mcpServers`), sinon de la variable d'environnement ; le jeton est celui qui accompagne cette adresse (même hôte : `BITBUCKET_TOKEN` du même serveur MCP, ou de l'environnement). `JIRA_URL` (serveur MCP Atlassian, ou environnement) sert au lien du ticket. Rien n'est écrit ni journalisé : `env` ne porte que `bitbucketUrl`, `bitbucketSource`, `bitbucketToken` (présent ou non) et `jiraUrl`, pour le texte d'aide des Réglages (détection sans le réglage de l'utilisateur).
- **Réponse** : `{ status: ok | missing | expired | error, message, host, account, jiraUrl, fetchedAt, prs: [{ id, title, project, projectName, repo, repoName, branch, target, author, url, created, updated, comments, openTasks, draft, key }] }`. `key` est la clé Jira (`[A-Z][A-Z0-9]+-\d+`, non collée à d'autres lettres ou chiffres) lue dans la branche, sinon dans le titre, sinon vide. `missing` = pas d'adresse ou pas de jeton, `expired` = HTTP 401/403, `error` = réseau, délai (20 s), réponse illisible ; `message` est technique, l'UI porte les phrases.
- **Côté UI** (`ui.prImport`, rendu par `prImportHtml` à la place de la zone de texte du dialogue) : `groupPullRequests` fait un groupe par clé, dans l'ordre d'ouverture de la première PR (une PR sans clé fait son propre groupe) ; `prTitle` ôte du titre le préfixe de branche (`Feature/`, `Bugfix/`…) et la clé. `prGroupStatus` cherche une tâche **non terminée** portant `task.jira === key`, sinon l'adresse d'une des PRs (dans `task.prs` ou dans son texte) : `new` (rien en file), `update` (des PRs manquent : elles sont ajoutées au texte par `prAppendText`, après la dernière ligne de PR et avant celle du ticket, et à `task.prs`), `same` (grisé, non cochable). Coché d'office sauf `same` et les groupes tout en brouillons. `createFromPrImport` crée les tâches dans la catégorie du dialogue, à `insertAt`, dans l'ordre des groupes, avec `jira` et `prs` (`prTaskText`), puis ferme le dialogue et le dit en toast. Une tâche terminée ne compte pas : la PR qui revient après de nouveaux commits fait une nouvelle tâche.
- **Import groupé** (`ui.prImport.group`, case `pr-group-toggle` rendue par `prGroupToggleHtml` sous la liste, décochée à l'ouverture, désactivée tant que `prImportCounts().create` vaut 0) : à la première tâche à créer, `createFromPrImport` insère à `insertAt` une parente `{ text: "Revue générale · 01/10" (prGroupTitle, jour et mois), reviewGroup: true }`, puis chaque groupe `new` en sous-tâche (`parent`), texte, `jira` et `prs` inchangés ; `commit` → `regroupTasks` les range derrière elle. Les groupes `update` complètent leur tâche sans la déplacer, les `same` et les brouillons décochés ne bougent pas. Bouton « Créer la revue générale · n sous-tâches[, compléter n tâches] » (`prImportGrouped`) ; toast « Revue générale créée avec n sous-tâches · 1 tâche déjà en file complétée, laissée à sa place. ». Rien de l'option n'est persisté : elle vit le temps du dialogue.
- **Pastilles de tickets** (`jiraChipsHtml`, dans la ligne méta de la carte, juste après la catégorie) : `taskJiraKeys` prend `task.jira` puis les clés du texte (`JIRA_KEY_RE`, 2 à 10 caractères avant le tiret, non collées à une lettre, un chiffre, `_` ou `-`), dédoublonnées, sans les sigles de `NOT_JIRA` (`UTF-8`, `ISO-…`, `GPT-5`…), trois au plus. L'adresse vient de `jiraBase` : `env.jiraUrl`, sinon la racine du premier lien `…/browse/<clé>` trouvé dans une tâche ; inconnue, aucune pastille. Chacune est un `<a data-act="open-url">` vers `<jira>/browse/<clé>`, non déplaçable (la carte l'est).
- **Pastilles de PRs** (`prChipsHtml`, juste après celles des tickets) : `taskPullRequests` lit les adresses de `task.prs` puis celles du texte avec `PR_URL_RE` — `…/<dépôt>/pull-requests/<n>` (Bitbucket DC et Cloud), `…/<dépôt>/pull/<n>` (GitHub), `…/<dépôt>/-/merge_requests/<n>` (GitLab) —, coupées après le numéro (`/overview`, `/diff`, `/files` tombent) et dédoublonnées sur cette adresse sans tenir compte de la casse. Libellé `<dépôt> #<n>` précédé de `ICON.pullRequest`, le nom du dépôt seul tronqué au-delà de 200 px (`.pr-chip-repo`) pour que le numéro reste lisible. Trois au plus ; les suivantes font un `<span class="pr-chip-more">+n PR</span>`, non cliquable, dont l'infobulle les nomme. Même mécanique que les tickets (`<a data-act="open-url">`, `draggable="false"`), sans adresse de serveur à connaître.
- `taskTextHtml` rend cliquables les adresses `http(s)` du texte d'une tâche (`<a data-act="open-url">` → `openUrl`), sans ouvrir l'édition — le dispatcher prend l'action la plus proche du clic.

## Remarques sur Organizator

Le carnet (bouton « Remarques » de l'en-tête) est une tâche virtuelle côté UI : `taskById("__feedback__")` renvoie un objet fixe, jamais présent dans `tasks`, si bien que le panneau, le formulaire de lancement, la liste des sessions et le transcript sont ceux des tâches ordinaires. Ses conversations ont `taskId: "__feedback__"`.

- `remarks` (data.json) : une remarque est en attente tant que `sentAt` vaut 0 ; l'envoi la date et note la session (`sessionId`). L'historique des envoyées est effaçable d'un bouton.
- **Ce qu'a reçu chaque session** : `markRemarksSent` recopie aussi les remarques envoyées dans la conversation (`convo.remarks`, `{ id, text, sentAt }`), à la création comme à un renvoi (↪) — effacer l'historique ne fait donc pas perdre ce qui a donné lieu à une conversation. `normalize` reconstitue `convo.remarks` des conversations d'avant par `remark.sessionId`, et le retire hors du carnet. `convoListHtml(convs, true)` pose sous le titre `convoRemarksHtml` : les remarques numérotées comme l'agent les a reçues, groupées par envoi (`sentAt`), chaque renvoi précédé de « ↪ envoyée le … » ; trois lignes au plus par remarque (`-webkit-line-clamp`, sauts de ligne gardés), le texte entier en infobulle.
- Envoi direct (bouton principal) : agent par défaut des réglages (ou le seul installé), son modèle et son effort par défaut, dossier = `settings.repoDir` / dernière session / `env.repoDir` ; le texte encore saisi devient une remarque avant l'envoi. Sans dossier connu, le formulaire s'ouvre. Le lien secondaire ouvre ce formulaire (agent, modèle, effort, dossier).
- Envoi : `startSession` avec `context` = consignes fixes (lire README et ARCHITECTURE, construire via la solution, ne pas fermer l'application qui tourne, préserver `%LOCALAPPDATA%\Organizator`, répondre en français) et `prompt` = les remarques numérotées comme dans le panneau (les lignes suivantes d'une remarque sont indentées de trois espaces), suivi d'une consigne de récapitulatif. Titre : `Remarques Organizator · <n> · <date>`.
- Envoi dans une session existante : `resumeSession` avec le même `prompt` (bouton ↪ sur la session) ; le contexte est déjà dans l'historique.
- Dossier de travail proposé : `settings.repoDir`, sinon le dossier de la dernière session du carnet, sinon `env.repoDir` (premier parent de l'exécutable contenant `Organizator.sln`).
- Bouton de l'en-tête : badge = remarques en attente ; point d'état = état le plus pressant des sessions du carnet (même règle que la pastille des cartes de tâches).

## Contrat de messages (bridge)

### JS → hôte

```js
window.chrome.webview.postMessage({ id: "<uuid ou compteur>", type: "<type>", payload: {...} });
```

L'hôte répond **toujours** avec un message au même `id` :

```js
{ id, ok: true,  payload: {...} }
{ id, ok: false, error: "message lisible en français" }
```

### Contexte transmis à Claude

`context` (construit côté JS) :

```
Tu travailles sur la tâche suivante, extraite d'Organizator (file de tâches de l'utilisateur).
Catégorie : <label>
Mots-clés : <noms retenus, séparés par des virgules — ligne absente si aucun>
Ce que ces mots-clés demandent :            (ligne absente si aucun ne porte de consigne)
- <nom> : <consigne, lignes suivantes indentées de deux espaces>

Équipe à lancer : …                         (bloc absent si aucun mot-clé retenu n'arme d'équipe)
- <agent> [<rôle>] (modèle …, effort …) : <mission>   (agents groupés par rôle ; parenthèse absente si rien n'est demandé ;
                                             « Pour « <mot-clé> » : » en tête si plusieurs équipes)

Travail déjà fait — ce qu’ont rendu les conversations précédentes liées à cette tâche. Lis-le avant de
commencer, lis sur le disque les rapports qu’il cite s’ils te servent, et ne refais pas ce qui est fait.
<résumé, voir « Travail déjà fait »>          (bloc absent si le formulaire n'en porte pas)

Réponds en français.
```

Le texte de la tâche n'est pas dans le contexte : il est le **premier message** (`buildPrompt`), pour que l'agent démarre dessus plutôt que d'attendre une saisie. Le formulaire de lancement le donne à relire dans une zone « Premier message » (`ui.newConvoPrompt`, remplie à l'ouverture par `buildPrompt`, Ctrl + Entrée lance) : ce qui s'y trouve est ce qui part.

```
Tâche :
<texte complet de la tâche>
```

Les **pièces jointes** suivent le texte de la tâche, dans le message comme dans le contexte (`attachmentsPrompt`, voir « Pièces jointes ») :

```
Pièces jointes de la tâche parente (« <titre du parent> ») :   (sous-tâche dont le parent en a)
- <nom> (image) : <chemin complet de la copie>
Pièces jointes :
- <nom> : <chemin>
- Texte « <titre> » :
    <texte du bloc, indenté de quatre espaces>
- Texte « <titre> », <n> caractères, à lire sur le disque : <chemin de texte-<id>.txt>
Ouvre ces fichiers avant de commencer : ils font partie de la demande (…).   (s'il y a au moins un chemin)
```

Seul un message **identique à la tâche** la retire du contexte : elle y ferait doublon. Champ vidé (aucun message ne part, l'agent ouvre son invite et attend) ou message retouché (« commence par reproduire le bug »), `buildContext` reprend la tâche (`withTask`) — sans quoi l'agent n'aurait jamais l'énoncé. Une **reprise** passe toujours `withTask`, le texte de la tâche y étant renvoyé à jour. Côté Copilot, qui n'a pas de prompt système, l'hôte recolle les deux (contexte, ligne vide, message) en un seul `-i` : la session reçoit mot pour mot ce qu'elle recevait avant ce partage.

`title` = première ligne de la tâche, 46 caractères max.

### Travail déjà fait

Une nouvelle conversation ne part pas de rien : `openNewConvo` appelle `loadRecap`, qui réunit les tâches concernées (`priorTasksOf`) — pour une sous-tâche, la tâche parente, les sous-tâches sœurs qui la précèdent dans la file, puis elle-même ; pour une tâche de premier niveau, elle-même puis ses sous-tâches ; jamais le carnet de remarques —, ne garde que celles qui ont des conversations, et demande à l'hôte (`getRecaps`) la dernière réponse de chacune, par ordre de création. `buildRecap` compose alors le texte : par tâche, `## Tâche parente | Sous-tâche précédente | Sous-tâche | Cette tâche : <première ligne> (terminée | en cours)` et, sauf pour la tâche elle-même, le reste de son texte ; par conversation, `### Conversation « <titre> » — <agent · modèle · effort>, <date>, <état>`, `Dernière réponse de l’agent :` suivie de la réponse (`RECAP_ANSWER_MAX` = 3 000 caractères), `Rapports produits (à lire sur le disque) :` avec le chemin complet de chaque rapport (`artifactFullPath` recolle le `cwd` aux chemins relatifs), et le nombre des autres fichiers modifiés. Le contexte part sur la ligne de commande de `claude` / `copilot`, bornée à 32 Ko : `fitRecap` tient le tout sous `RECAP_TOTAL_MAX` (12 000 caractères) en raccourcissant les réponses de la plus ancienne à la plus récente (`RECAP_SHORT` = 500), puis en les omettant dans le même ordre. Côté hôte, `TranscriptAccumulator.LastAnswer` prend le texte final du dernier tour de l'agent — ce qui suit sa dernière ligne `[outil : …]`, là où il récapitule —, ou tout le tour sans ces lignes s'il n'a rien dit après ; `ClaudeSessions.GetLastAnswer` et `CopilotSessions.GetLastAnswer` lisent le fichier d'un seul tenant, avec un `SessionScan` à part, pour ne pas dérégler la lecture incrémentale du journal affiché. Un lot lancé sur les sous-tâches d'une parente écarte les sœurs du résumé de chacune (voir « Lancement sur les sous-tâches »).

Le formulaire montre le résultat dans un bloc « Travail déjà fait » (`newFormRecapHtml`, textarea `new-recap`, `ui.newConvoRecap`), avec le nombre de conversations et de rapports couverts ; « lecture… » tant que l'hôte n'a pas répondu (`ui.newConvoRecapBusy`, la réponse arrive après le rendu du formulaire, `preserveFocus` garde la saisie en cours). Le bloc est absent quand il n'y a rien à transmettre. Ce qui s'y trouve à l'envoi — retouché ou non — est ce que `buildContext` écrit, entre l'équipe et la tâche ; vidé, rien ne part ; lancé pendant la lecture, rien ne part non plus. Une reprise (`resumeSession`) ne passe pas de résumé : la session a son historique. Côté Copilot, le contexte étant le premier message, le résumé y est aussi.

Un mot-clé peut **lancer une équipe** : cochée, la case ajoute au contexte la consigne d'ouvrir aussitôt les agents décrits, en parallèle, dans la **même session** — c'est l'agent principal qui délègue (outil `Agent` / `Task`), Organizator n'ouvre pas d'autre terminal. Les sous-agents ainsi lancés sont ceux que le badge de la console compte (voir « Agents au travail »). Chaque agent porte un nom, un **rôle** (champ libre, `AGENT_ROLES` n'en propose que quelques-uns dans une `datalist`) et une mission ; `agentsByRole` les groupe par rôle dans le contexte, `teamOf` écarte ceux qui n'ont pas de nom et rend la liste vide si la case est décochée.

**Niveau d'un agent.** `model` et `effort` disent avec quel modèle l'ouvrir et quel soin attendre de lui. Vides — le cas ordinaire —, il travaille comme la session qui l'ouvre ; sinon le contexte le dit agent par agent, avec une phrase qui explique quoi en faire. **Rien n'est contraint** : comme pour le reste de l'équipe, Organizator écrit une consigne, c'est l'agent principal qui ouvre le sous-agent (l'outil `Agent` / `Task` accepte un modèle ; l'effort, lui, tient à la définition du sous-agent, d'où la consigne de le redire dans sa mission à défaut).

Le vocabulaire des deux listes vient de l'**agent de lancement** (`teamProviderId` : le réglage `provider`, pas celui de la rédaction assistée), puisque c'est lui qui ouvrira l'équipe : `teamModels` aplatit son catalogue (`catalogFor`, groupes compris), `teamEfforts` rend ses niveaux d'effort. Une valeur qui n'y figure plus — catalogue changé, agent par défaut changé — reste offerte dans la liste plutôt que d'être perdue.

Les mots-clés se gèrent dans le dialogue **Catégories** (`catsHtml`, ouvert par `ui.catsOpen`, prioritaire sur les autres dialogues) : un nom tapé puis Entrée (ou une virgule) crée le mot-clé et ouvre son éditeur (`keywordEditorHtml`, `ui.catKeywordEdit`) — nom, description, consigne, puis l'équipe (`keywordTeamHtml`, `agentRowHtml`), le tout enregistré au fil de la frappe. Ils sont normalisés et dédupliqués sans tenir compte de la casse (`normalizeKeywords`, 32 par catégorie) ; un nom vidé ne survit pas à la fermeture du dialogue. Retirer un mot-clé le retire aussi des `convo.keywords` des conversations des tâches de cette catégorie.

Ils ne sont **proposés qu'au lancement** (`newFormKeywordHtml`, sous le choix du modèle, absent pour une tâche sans catégorie et pour le carnet de remarques) : pastilles à cocher, choix multiple (`ui.newConvoKeywords`, identifiants), un « + » (`ui.newKeywordOpen`) pour créer un mot-clé sans quitter le formulaire — il est coché d'office, et peut y recevoir son équipe (case + ✦, `ui.newKeywordTeam` / `ui.newKeywordAgents`, retouche fine dans Catégories) —, et un lien vers le dialogue Catégories. Une pastille dont le mot-clé arme une équipe porte le nombre d'agents (`.kw-team-n`), comme l'icône des rapports porte le sien. Le choix est enregistré dans `convo.keywords`, affiché sous le titre de la session et repris lors d'une reprise.

### Lancement sur les sous-tâches

Une tâche de premier niveau dont au moins une sous-tâche n'est pas terminée (`batchSubsOf`) se lance au choix sur elle-même ou sur ses sous-tâches : `newFormTargetHtml` pose en tête du formulaire « Lancer sur : Cette tâche / Chaque sous-tâche · n » (`pick-target`, `ui.newConvoTarget` = `self` | `subs`). Jamais pour une sous-tâche ni pour le carnet de remarques.

- **Ouverture** (`openNewConvo`) : `subs` d'office si la tâche porte `reviewGroup`, ou si chacune de ses sous-tâches non terminées a au moins une PR (`taskPullRequests`) ; `self` sinon. `ui.newConvoSubs` (id → coché) décoche celles qui ont déjà un rapport de revue (`reviewReportsOf`) ou une conversation `working` / `waiting` / `open`. Le dossier proposé est `groupCwdFor` : celui de la tâche si elle a des conversations, sinon celui de la plus récente conversation de ses sous-tâches, sinon le réglage. `loadRecap` n'est appelé que sur `self` — au premier passage sur « Cette tâche » s'il a été sauté. « Cette tâche » se comporte exactement comme avant : premier message, « Travail déjà fait » de la tâche et de ses sous-tâches, pas de lot.
- **Formulaire `subs`** (`newFormSubsHtml`, à la place du premier message et du « Travail déjà fait ») : une case par sous-tâche non terminée (`batch-sub`), avec la raison d'une case décochée (« rapport de revue déjà écrit », « conversation en cours ») et « sans « Review-one » : autre catégorie » quand un mot-clé coché n'existe pas dans la catégorie de la sous-tâche ; une **précision** commune (`batch-note`, `ui.newConvoNote`), ajoutée après une ligne vide à la fin de chaque premier message. Mots-clés proposés : ceux de la catégorie de la parente. Bouton « Lancer n conversations dans PowerShell », grisé sans case cochée ; pendant le lot « Préparation… » puis « Lancement 2 / 4… » (`ui.batchProgress`). Entrée dans le dossier ne lance rien : un lot ne part que du bouton.
- **Lancement** (`launchBatch`) : agent, modèle, effort, dossier, **noms** des mots-clés, précision et cases sont figés au départ. `flushTextWrites`, puis `loadBatchRecaps` : un seul `getRecaps` (60 s) pour l'union des conversations, et pour chaque sous-tâche un « Travail déjà fait » réduit à sa parente et à elle-même (`batchRecapEntries` : `priorTasksOf` sans les sœurs, qui tournent en même temps — l'agent lirait sinon la revue d'un autre ticket, sur le budget de 12 000 caractères). Une lecture en échec laisse partir le lot sans résumé. La parente reçoit alors `batch = { id: "b…", at, n: 0, endedAt: 0 }`, qui remplace le lot précédent. Les sous-tâches partent **l'une après l'autre**, à `BATCH_LAUNCH_GAP_MS` (1,5 s) d'intervalle : `launchSession(sub, { …, keywords: keywordIdsFor(sub, noms), prompt: buildPrompt(sub) + précision, taskInContext: false, recap, batch: id })`. Les mots-clés passent par leur nom parce qu'une sous-tâche peut être rangée dans une autre catégorie ; `taskInContext: false` parce que le message porte toujours la tâche, précision ou non. L'hôte n'est pas touché (un script `launch\<Guid>.ps1` par session) ; l'espacement tient au fil de l'interface que `Process.Start` occupe plus de 250 ms (`[PERF/WARN]`), aux écritures concurrentes de `~/.claude.json`, à l'ordre des onglets de Windows Terminal et au balayage des processus toutes les 4 s. Chaque conversation lancée est enregistrée aussitôt (`recordConvo`, `convo.batch = id`, `saveDataLater`). À la fin : `batch.n` = sessions lancées ; aucune → le lot précédent est rétabli (ou `batch` retiré) et le formulaire reste ouvert ; sinon il se referme si le panneau est encore sur la parente. Toast : « 4 conversations lancées, une par sous-tâche — la revue générale est en cours » (la fin sur une `reviewGroup` seulement), « 3 conversations lancées sur 4 — échec pour « UDM-1600 · … » : <message> », « Lancement impossible : <message> », suivi de « (sans « Travail déjà fait » : lecture impossible) » au besoin.
- `startSession` (conversation ordinaire, carnet) et `launchBatch` partagent `launchSession` (appel `startSession` de l'hôte, sans verrou ni formulaire ni toast ; `taskInContext`, s'il est donné, remplace la règle « message identique à la tâche ») et `recordConvo` (ajout de la conversation, `sessionExists` à faux).
- **Fin du lot** (`checkBatches`, à chaque `refreshSessions`, juste après `announce`) : pour chaque tâche dont `batch.endedAt` vaut 0 (sauf le lot en cours de lancement), `batchConvos` = les conversations portant `batch.id`. Aucune (supprimées) → clos sans bruit. Sinon toutes doivent avoir rendu la main (`batchConvoDone`) : jamais avant `BATCH_GRACE_MS` (30 s — le processus n'est vu vivant qu'au premier balayage et `displayState` dirait « Fermée » d'ici là) ; `ready`, `error`, `closed` ou `idle` → finie (l'agent a rendu la main, le terminal peut rester ouvert) ; ni fichier ni processus passé `BATCH_DEAD_MS` (2 min) → jamais démarrée, finie aussi ; `working` (équipe encore dehors comprise), `waiting`, `open` → pas finie. Le constat doit tenir à deux relectures espacées d'au moins `BATCH_CONFIRM_MS` (5 s, `batchDoneSince`, en mémoire) : un agent qui enchaîne deux tours passe un instant par « réponse prête ». Alors `endedAt` = maintenant, `saveDataNow`, et `batchEndToast` : n = sous-tâches dont une conversation **du lot** a écrit un rapport de revue (`reviewReportsOf`) ; « Revue générale terminée — 4 rapports[, 1 en erreur] » avec le bouton **Ouvrir** (`openReviewGroup({ parentId })`, voir « Revues groupées ») ; sans rapport, « Revue générale terminée — aucun rapport de revue écrit » sur une `reviewGroup`, « Conversations des sous-tâches terminées — « <titre> » » ailleurs, sans bouton. Rien ne s'ouvre tout seul.
- **Toast avec action** : `toast(msg, { label, run })` ajoute un bouton (`toast-act`, classe `has-act`) et laisse le toast 12 s au lieu de 3,4 ; un clic le referme puis appelle `run`. Un toast ordinaire arrivé entre-temps le remplace (le bouton de la carte parente reste). Les appels `toast(msg)` sont inchangés.
- Rien n'est ajouté à la racine de `data.json` (`DataStore.NormalizeData` en liste les clés) : `reviewGroup` et `batch` vivent dans la tâche, `batch` dans la conversation, que la normalisation recopie telles quelles. Côté UI, `normalize` ne garde `reviewGroup` que s'il vaut `true`, retire un `batch` de tâche qui n'est pas un objet avec `id` (sinon `at` / `n` / `endedAt` en nombres), et un `convo.batch` vide.

## Article du jour

Une carte en tête de fenêtre (`articleCardHtml`, rendue par `renderUsage` à la suite des quotas) et un panneau latéral (`articlePanelHtml`) proposent chaque jour un article du web lié à ce que fait l'utilisateur, avec son résumé.

Deux **fils** suivent ce même mécanisme, chacun avec sa carte, son panneau, son état et son fichier : l'**article du jour** (`daily`, `article.json`), pour les sujets de l'utilisateur, et la **veille IA** (`ai`, `article-ai.json`), l'actualité récente de l'IA vue par un développeur qui travaille avec des agents, sans regarder sa file. Côté hôte, `ArticleFeed` (`Daily`, `Ai`) porte ce qui les distingue — consignes, fiche, ce que le prompt dit de l'utilisateur, fichier — et `BridgeHost` tient un `DailyArticle` par fil, choisi par le `kind` des messages (`daily` par défaut). Côté UI, `ARTICLE_FEEDS` porte les libellés, l'identifiant du panneau (`__article__`, `__article_ai__`), l'interrupteur (`articleEnabled`, `articleAiEnabled`) et les centres d'intérêt ; `S.ui.articles.daily` / `.ai` les états. Les deux fils sont indépendants : chacun cherche le sien, en parallèle, et un échec de l'un ne touche pas l'autre. Modèle et effort sont communs (`articleModel`, `articleEffort`).

- **Hôte** (`DailyArticle`) : `claude -p <prompt> --no-session-persistence --tools WebSearch,WebFetch --allowedTools WebSearch,WebFetch --output-format json --json-schema <fiche> --append-system-prompt <consignes> [--model] [--effort]`, dans le dossier de données, hors du fil de l'interface (`Task.Run`), 240 s au plus (`AgentDraft.RunAsync`, partagé avec la rédaction). `--tools` borne l'agent au web : ni disque ni shell. La fiche revient dans `structured_output` de l'enveloppe JSON (`result` en repli) : `title`, `url` (http(s) absolue, sinon refus), `source` (l'hôte de l'adresse à défaut), `author`, `published` (AAAA-MM-JJ), `language`, `readingMinutes`, `topic`, `summary`, `keyPoints` (5 au plus), `why`, bornés en longueur ; l'hôte ajoute `day` (jour local), `fetchedAt`, `model`, `ms`, `seenAt`. `is_error` ou une sortie illisible deviennent un message (`AgentDraft.Explain` reconnaît « pas connecté »). Les consignes (en dur dans l'hôte) : lire l'article avant de le résumer, un article de fond plutôt récent, en français ou en anglais, ni accueil ni produit ni vidéo, priorité aux sujets fixés par l'utilisateur, vouvoiement. Le prompt ajoute la date, les centres d'intérêt reçus de l'UI (6 000 caractères au plus), les articles déjà proposés (à ne pas reproposer) et les sujets des cinq derniers (à varier). **Veille IA** : consignes propres — le fait le plus utile des derniers jours pour un développeur qui travaille avec des agents de code (modèles, agents et outils, pratiques, recherche, secteur), sources de première main ou presse technique sérieuse, sans agrégateur ni rumeur —, une fenêtre de fraîcheur en dates dans le prompt (sept jours de préférence, quatorze au plus, date à vérifier) à la place des centres d'intérêt, ignorés, et les sujets des dix derniers donnés comme « faits déjà couverts, à ne pas reprendre » ; dans la fiche, `topic` est le fait marquant, `why` ce que cela change pour l'utilisateur, et `published` est exigé. Une seule recherche à la fois : une demande qui arrive pendant l'autre attend la même. `today` rend l'article gardé s'il date d'aujourd'hui, sans rien lancer. Le précédent passe en tête de `history`. Le journal note la source, la durée, les tours et le coût au tarif public.
- **Centres d'intérêt** (`articleInterests`, côté UI, article du jour seulement : la veille IA envoie `interests: ""`) : `articleTopics` (« prioritaires »), puis la première ligne des 25 premières tâches non terminées et les titres des 12 conversations les plus récentes hors carnet de remarques, adresses retirées et doublons écartés.
- **Quand** (`ensureArticle(fil)`, `ensureArticles` pour les deux) : au démarrage, après `peek` (`peekArticles`, un par fil ; `S.ui.articles[fil].loaded` : rien n'est cherché avant d'avoir les données), au `focus` et toutes les 10 min (changement de date), si l'article gardé n'est pas celui du jour ; pas par-dessus une recherche en cours, ni moins d'une heure après un échec (`failedAt`) — **Réessayer** passe outre. Un `peek` qui répond `busy` (page rechargée pendant une recherche) enchaîne sur `today`, qui attend la même.
- **Affichage** : une carte par fil, `usage-card article-card article-daily` ou `article-ai` (`open-article` ; toutes les actions des cartes et du panneau portent `data-feed`) — titre sur deux lignes, pied `article-card-foot` : « source · 8 min · en anglais » et le bouton **Suivant ›** (`article-next`, action `article-another` : le dispatcher prend l'action la plus proche du clic, le panneau ne s'ouvre pas), point `article-new` tant que l'article du jour n'a pas été ouvert ; pendant une recherche, « Recherche d'un nouvel article… » (clignotant) et le bouton grisé ; sans article, « Recherche de l'article du jour… » ou « Indisponible · <message> », sans bouton. Le panneau est celui des tâches (`S.ui.termTaskId = ARTICLE_ID`, `renderPanel` le reconnaît avant `taskById`) : en tête (`article-head`) la date et **Article suivant ›** (`article-another`, « Recherche en cours… » grisé pendant une recherche ; absent sur un article précédent), puis titre-lien (`open-url`), auteur, date de publication, sujet, résumé, « À retenir », « Pourquoi pour vous » (veille IA : « Ce que ça change pour vous »), **Lire l'article ↗**, puis les articles précédents (`article-show` affiche l'un d'eux, `S.ui.articles[fil].shown`, « ‹ Article du jour » ou « ‹ Veille IA du jour » revient) et un lien vers l'onglet **Articles du jour** des Réglages (`articleSettingsHtml` : interrupteur de l'article du jour, sujets, interrupteur de la veille IA `toggle-article-ai`, modèle et effort Claude communs). Ouvrir le panneau marque l'article lu (`articleSeen`) ; un article arrivé panneau ouvert l'est aussitôt, un article arrivé panneau fermé garde son point. Un `another` qui échoue garde l'article affiché : le panneau montre l'erreur sous la fiche, et lancé panneau fermé, un toast « Pas d'autre article pour l'instant : <message> » le dit — la carte, elle, ne montre pas d'erreur tant qu'elle a un article.
- Shim : `getArticle` / `articleSeen` simulés, par `kind` ; `window.__fakeArticleStore` (veille IA : `__fakeArticleStoreAi`) impose l'état gardé, `window.__fakeArticle` (`__fakeArticleAi`) la fiche fabriquée (ou `'error'`), chaque appel est noté dans `window.__articleCalls`.

## Rédaction assistée

Le bouton **✦ Rédiger** (dialogue « Nouvelle tâche », tâche en cours d'édition, éditeur d'un mot-clé, composition d'une équipe, mission d'un de ses agents) demande un texte à un agent **hors terminal** : `AgentDraft` lance la CLI en mode non interactif, lit sa sortie standard et la rend à l'UI, qui la propose sans rien enregistrer.

- Claude : `claude -p <prompt> --no-session-persistence [--model …] [--effort …] [--append-system-prompt <consignes>]`.
- Copilot : `copilot -p <consignes + prompt> --session-id=<uuid> [--model …] [--effort …]` — la CLI n'a pas de prompt système, et la session qu'elle crée est supprimée juste après (`CopilotSessionCleanup`, sans égard pour ses événements : elle n'existait que le temps de l'appel).
- L'exécutable est celui qu'`AgentLauncher` a détecté (`CommandFor`) ; les arguments passent par `ArgumentList` (pas de script, donc pas d'échappement PowerShell à refaire). Dossier de travail : le dossier de données, neutre — un dossier de projet vide peut y apparaître sous `~/.claude/projects`, sans fichier de session.
- Deux pièges : **`--bare` est à proscrire** (ce mode saute les lectures du trousseau, l'appel répond « Not logged in » alors que la session l'est), et `--no-session-persistence` est indispensable pour qu'une rédaction ne laisse pas de conversation dans `~/.claude/projects`.
- La sortie est débarrassée des codes ANSI et d'un éventuel bloc ``` encadrant. Vide ou code de retour non nul : message lisible, reconnaissant le cas « pas connecté ». Abandon au bout de 120 s (l'UI attend 150 s), processus tué avec ses enfants. Une seule rédaction à la fois (sémaphore), et le bouton est grisé pendant ce temps.
- Prompts et découpage sont côté UI : pour un mot-clé, l'agent doit rendre `Description: …` puis `Consigne: …` (format non suivi : tout est pris pour la consigne) ; pour une tâche, seul le corps est demandé, et « Garder » le pose sous la première ligne, qui reste le titre écrit par l'utilisateur. L'état vit dans `ui.draft` (`{ key, kind, target, prompt, turns, busy, text, desc, team, note, error, ms }`) : une proposition à la fois, jetée à la fermeture.
- `kind` dit quoi en faire : `composer` / `task` (corps d'une tâche), `keyword` / `new-keyword` (consigne), `team` / `new-team` (composition d'une équipe) et `agent` (mission d'un agent). Pour une équipe, l'agent doit rendre une ligne par membre, `Nom | rôle | modèle | effort | mission` ; les cases du milieu ne sont prises pour un niveau que si `tuneCell` y reconnaît un modèle du catalogue, un effort, ou un tiret (« rien de particulier ») — sinon la mission commence là, et l'ancien format à trois cases se relit inchangé. `teamVocabPrompt` donne au passage les rôles, modèles et efforts possibles, et demande de les régler sur la mission plutôt que de tout mettre au maximum. `parseTeamDraft` relit aussi « Nom [rôle] — mission » et « Nom : mission », numérotation et puces comprises, et l'encadré affiche alors la liste plutôt qu'un bloc de texte. « Garder » remplace l'équipe en conservant l'identifiant des agents dont le nom n'a pas changé (`setKeywordAgents`), pour ne pas refermer la mission qu'on était en train de lire. Une réponse illisible n'écrase rien : l'encadré propose de réessayer.
- **La proposition se discute.** `turns` garde les versions déjà rendues et ce que l'utilisateur en a dit (`{ text, note }`) ; `draftPrompt` reconstruit à chaque tour la demande de départ suivie de tout l'échange, puisque la CLI est appelée sans mémoire de session (`-p`). « Renvoyer » ajoute la version affichée et la note saisie avant de relancer, « Autre version » fait de même avec une note vide (le prompt dit alors que l'utilisateur redemande autre chose). La saisie de la note ne déclenche pas de rendu — seul l'état du bouton est touché — pour ne pas reconstruire le champ à chaque frappe.

### Atelier d'un mot-clé

Le bouton **En discuter** (`kw-chat` dans l'éditeur d'un mot-clé, `kw-new-chat` dans le « + » du formulaire de lancement) ouvre une discussion qui règle la **fiche** entière — nom, description, consigne, équipe — plutôt qu'un champ après l'autre. Même canal que la rédaction (`draftText`, même agent, même modèle), mais un état et un dialogue à part : `ui.chat` (`{ typeId, keywordId, launch, card, turns, note, busy, error, ms }`), rendu par `chatHtml` — `renderDialogs` lui donne la priorité sur les autres dialogues, si bien qu'il se pose par-dessus Catégories et se referme dessus.

Ce que l'agent reçoit à chaque tour (`chatPrompt`) : les **autres mots-clés de la catégorie** avec description, consigne et équipe (`catalogText`, 12 au plus — de quoi s'en inspirer sans les redoubler), la **fiche en cours** (`cardText`), puis toute la discussion (12 derniers échanges), la CLI n'en gardant rien. Il répond soit `Question: …`, soit la fiche (`Nom:`, `Description:`, `Consigne:`, `Équipe: oui|non` suivi des lignes `nom | rôle | modèle | effort | mission`, mêmes règles de relecture que pour une équipe, `teamVocabPrompt` compris).

- **Questionner est le mode normal, boucler ne l'est pas.** Le prompt du tour dépend de l'état de la discussion (`questionRun` compte les tours de questions posés d'affilée, les réponses de l'utilisateur ne le remettant pas à zéro) : tant qu'aucune fiche n'a été proposée, l'agent est invité à interroger (une à `CHAT_QUESTIONS` questions d'un coup, une ligne `Question: …` chacune), et une fiche encore vide lui dit explicitement qu'il vaut mieux demander que deviner ; une fois une fiche posée, on lui demande la fiche revue, **sans** lui interdire de questionner si l'utilisateur le réclame ou s'il lui manque quelque chose d'irremplaçable ; à `CHAT_RUN` tours de questions d'affilée, le prompt le lui dit en clair et réclame la fiche, sauf demande expresse de l'utilisateur. C'est un remplacement de la borne « une seule question, au premier tour », qui empêchait bien la boucle mais rendait l'atelier sourd à une demande de questions.
- **« Questionne-moi »** (`chat-ask` → `askChat`) n'est pas un mode : il pousse dans la discussion un tour utilisateur qui demande des questions, précédé de ce qui était déjà tapé. C'est donc le transcript — la seule chose que l'agent relit — qui porte la demande, sans drapeau à maintenir dans l'état.
- `parseQuestions` relit une ligne `Question: …` par question ; à défaut d'étiquette, une liste dont plusieurs lignes portent un « ? » en est une aussi ; sinon tout le texte fait une seule question. Une réponse hors protocole n'est donc jamais perdue — elle s'affiche comme un message (`parseChatReply`), en liste dès qu'il y a plusieurs questions.
- `parseCard` relit les étiquettes ligne à ligne (la consigne peut tenir sur plusieurs lignes) et récupère l'équipe avec `parseTeamDraft` ; si des lignes « nom | rôle | mission » ont glissé dans la consigne faute d'un `Équipe:`, elles en sont extraites. `mergeCard` garde ce qu'une fiche partielle ne redit pas.
- « Garder la fiche » (`keepChat`) écrit tout d'un coup et rouvre l'éditeur sur le mot-clé ; depuis le lancement (`launch`), elle remplit le formulaire au lieu d'enregistrer. Un nom déjà porté par un autre mot-clé de la catégorie n'est pas repris — il disparaîtrait à la normalisation, qui déduplique — et un toast le dit.
- **Rien de la discussion n'est conservé** : `ui.chat` meurt à la fermeture, rien ne part dans `data.json`. Rouvrir l'atelier plus tard repart de la fiche telle qu'elle est alors, retouches manuelles comprises — c'est la reprise voulue, sans historique à stocker ni à faire vieillir.

Deux détails d'affichage tiennent à ce que l'interface se redessine entièrement à chaque clic : les animations d'apparition ne sont posées qu'à l'ouverture (classe `enter` sur `.panel`, `.dialog` et `.new-form`), sans quoi cocher un mot-clé rejouerait le fondu du formulaire — il clignotait ; et le rayon de bordure « pilule » du thème (`.input { border-radius: 999px }`) est ramené à `--radius-md` pour les `textarea`, dont le rayon suivait la hauteur au point de donner des coins en arcs de cercle.

### Reprise d'une session déjà ouverte

`resumeSession` n'ouvre pas systématiquement un terminal. Si la session n'a **rien à recevoir** (`prompt` vide) et qu'elle tourne encore — `AgentProcessScanner.PidsFor` connaît les processus qui la portent, le plus récent d'abord (plusieurs quand elle a été reprise en double), ou, avant que le balayage ne les voie, le PowerShell ouvert pour elle il y a peu —, `AgentWindows` cherche sa fenêtre et la ramène au premier plan : la réponse vaut alors `{ focused: true }` et aucun second agent n'est lancé sur le même fichier de session. **Une session vivante n'est jamais relancée** : si sa fenêtre reste introuvable, la réponse vaut `{ focused: false, alive: true }`, et l'UI le dit dans un toast dont le bouton « Ouvrir un second terminal » renvoie la demande avec `force: true` — seul cas où deux agents partagent la session, à la demande de l'utilisateur. Des processus morts entre deux balayages (session qu'on vient de fermer) ne comptent pas : elle est rouverte normalement. Avec un `prompt` à remettre (remarques envoyées dans une session existante), la reprise se fait comme avant : seul un `--resume` sait transmettre le message. Côté UI, `resumeConvo` n'envoie qu'une reprise à la fois par conversation (`resuming`) : un double-clic en envoyait deux.

La fenêtre ne se trouve pas directement : elle n'appartient jamais au processus de l'agent. `AgentWindows.Find` la demande à **la console de l'agent elle-même** : `TerminalTabs.ConsoleWindow` s'y attache le temps d'un `GetConsoleWindow` (même emprunt que pour le titre, ci-dessous), qui rend `ConsoleWindowClass` pour une console classique, `PseudoConsoleWindow` quand Windows Terminal héberge la session. Dans ce second cas la vraie fenêtre est le propriétaire racine de la pseudo-console (`GetAncestor`/`GA_ROOTOWNER`), c'est-à-dire la fenêtre Windows Terminal qui porte l'onglet ; tant que le terminal ne l'a pas rattachée (une pseudo-console naît sans propriétaire), il n'y a rien à montrer et `Find` rend zéro. Elle est restaurée si elle était réduite, puis passée au premier plan ; `Raised` (`raised` dans la réponse) dit si `GetForegroundWindow()` la montre bien ensuite — sinon Windows a refusé, son bouton clignote dans la barre des tâches, et le toast le dit.

Remonter la chaîne des parents, comme on le faisait, ne suffit pas : Windows attribue la pseudo-console tantôt au PowerShell, tantôt à l'`OpenConsole.exe` qui la sert — lancé par COM (`svchost`), hors de la lignée. Relevé le 8 octobre 2026 : 15 sessions vivantes sur 25 dans ce cas, et ce sont exactement celles dont le clic « ne faisait rien ». La remontée tombait alors sur Organizator.exe, parent du PowerShell, dont elle ramenait la propre fenêtre — déjà devant : rien ne bougeait, et le journal disait « fenetre ramenee au premier plan » ; Organizator redémarré entre-temps (parent mort), elle ne trouvait rien et un second `--resume` partait sur la session vivante. La remontée (instantané `CreateToolhelp32Snapshot`, six niveaux au plus) ne sert plus que de repli quand l'attache échoue, et ne retient alors qu'une fenêtre de console, en s'arrêtant à Organizator ; une fenêtre d'Organizator n'est jamais retenue.

Cette fenêtre-là groupe souvent une dizaine de sessions en onglets : la ramener devant sans plus montrerait la session que l'utilisateur avait laissée, pas la sienne. `TerminalTabs` active donc l'onglet, en deux temps :

1. **Quel onglet ?** Le nom d'un onglet est le titre de la console qu'il héberge, caractère pour caractère (vérifié en UI Automation) ; l'agent le réécrit (`✳ <nom>` au repos, `◐ <nom>` au travail), et plusieurs sessions portent souvent le même — conversations d'une même tâche (même `--name`), sessions de remarques d'un même jour, session reprise en double. Comparer des titres ne suffit donc pas. L'hôte **marque** la console : il s'y attache (`AttachConsole`, puis `FreeConsole`), lit son titre et lui ajoute une marque invisible — `U+2063` puis un numéro en seize espaces sans chasse (`U+200C` / `U+200B`) —, que Windows Terminal reporte sur le nom de l'onglet en 5 à 12 ms, 200 au plus s'il vient de changer de titre (il regroupe les changements rapprochés). L'onglet dont le nom contient la marque (comparaison ordinale : une comparaison culturelle ignore les caractères sans chasse) est le bon ; la marque est retirée aussitôt, sauf si l'agent a déjà réécrit son titre par-dessus. 600 ms d'attente, deux essais. Éprouvé : 20 sur 20 sur deux onglets jumeaux, 33 à 36 ms en tout. La marque n'atteint pas l'onglet quand la session tourne dans un **volet** inactif (l'onglet montre le titre du volet actif) ou que l'utilisateur a renommé l'onglet : on se rabat alors sur le titre lu, à l'identique puis sans le glyphe d'activité, s'il ne désigne qu'un onglet ; sinon aucun n'est activé, `tab` porte le titre et l'UI dit lequel activer. Organizator n'ayant pas de console, l'emprunt réussit toujours ; il demande à ignorer `Ctrl+C` avant de s'attacher, pour ne pas recevoir celui du terminal, et sérialise ces emprunts (une console attachée à la fois par processus).
2. **L'activer.** Windows Terminal n'offre aucune commande pour cela, mais il expose ses onglets en **UI Automation** : chacun est un `TabItem` qui porte le motif `SelectionItem` — `Select()` l'amène devant, fenêtre en arrière-plan comprise.

**Terminal qu'on vient d'ouvrir.** Sous Windows 11, Windows Terminal est le terminal par défaut : le `powershell.exe` lancé par une reprise lui est confié, et il le range volontiers en **onglet d'une fenêtre déjà ouverte**, restée derrière Organizator. `AgentLauncher.ResumeSession` rend le PID du PowerShell (`null` sous `wt.exe`, qui ne fait que relayer) et `BridgeHost.BringLaunchedForwardAsync` appelle `AgentWindows.FocusWhenShownAsync` : la fenêtre est cherchée toutes les 150 ms (8 s au plus, abandon si le processus meurt), puis ramenée devant et son onglet activé, sans retarder la réponse. L'attache échoue pendant la remise de la console à Windows Terminal, puis la pseudo-console paraît sans propriétaire : la bonne fenêtre n'est trouvée qu'après 350 à 700 ms (mesuré) — l'ancienne remontée rendait au premier essai, vers 100 ms, la fenêtre d'Organizator. Le balayage des processus ne voyant l'agent qu'après quelques secondes, le PID du PowerShell est aussi retenu (`_launchedTerminal`, 2 min), au lancement d'une session (`StartSession`, `StartedSession.TerminalProcessId`) comme à sa reprise : un second clic dans l'intervalle attend sa fenêtre (`FocusWhenShownAsync`, 3 s) au lieu d'ouvrir un second terminal sur la même session. Il est oublié dès que le balayage voit l'agent vivant — un PowerShell `-NoExit` survit à l'agent qui quitte, il ne faut pas le prendre pour la session.

`Find` (attache à la console) et UI Automation partent dans des `Task.Run` (six secondes au plus pour l'onglet), jamais sur le fil de l'interface. La réponse porte `tabActivated: true` quand l'onglet a été amené devant, et `tab` vide quand il n'y a rien à faire — onglet activé, ou fenêtre qui ne groupe pas ses sessions (console classique, onglet unique).

**Journal.** Chaque essai laisse une ligne `[FOCUS]` dans `host.log` — processus visé (agent ou terminal lancé), fenêtre retenue (classe, titre, PID), premier plan accepté ou refusé, sort de l'onglet, durée —, et `TerminalTabs` une ligne « Onglet de la session : N onglets, titre '…', designe par : marque | titre | aucun (k onglet(s) de ce nom) ». Un échec se lit d'un coup d'œil : `Select-String '\[FOCUS\]|Onglet de la session' $env:LOCALAPPDATA\Organizator\host.log`.

Pour le carnet de remarques, `context` est un texte fixe (consignes du dépôt) et `prompt` porte les remarques ; voir « Remarques sur Organizator ».

### Script PowerShell généré (hôte)

```powershell
$Host.UI.RawUI.WindowTitle = 'Organizator — <titre>'
Set-Location -LiteralPath '<cwd>'
$ctx = @'
<contexte, tel quel>
'@
$ctx = [regex]::Replace($ctx, '(\\*)"', '$1$1\"')
if ($ctx -match '\s') { $ctx = [regex]::Replace($ctx, '(\\+)$', '$1$1') }
& claude --dangerously-skip-permissions --session-id '<uuid>' --name '<titre>' --model '<modèle>' --effort '<niveau>' --append-system-prompt $ctx
```

Pour une reprise : `& claude --dangerously-skip-permissions --resume '<uuid>' [--model '<modèle>'] [--effort '<niveau>'] --append-system-prompt $ctx`.
Avec un `prompt`, un second here-string `$msg` (mêmes deux lignes de protection) est ajouté en argument positionnel final : `… --append-system-prompt $ctx $msg`, à la création comme à la reprise ; claude ouvre la session et traite ce message aussitôt.
Avec Copilot : `& '<chemin>\copilot.exe' --allow-all --session-id=<uuid> --name '<titre>' [--model '<modèle>'] [--effort '<niveau>'] -i $ctx`, et à la reprise `--resume=<uuid>` sans `-i`. Copilot n'ayant pas de prompt système, un `prompt` est fusionné au contexte dans `$ctx` (contexte, ligne vide, message) à la création ; à la reprise, `$ctx` ne contient que le message et `-i $ctx` est écrit.
`--model` et `--effort` ne sont écrits que si une valeur a été choisie ; `--append-system-prompt` / `-i` que si le contexte n'est pas vide (PowerShell 5.1 supprime un argument vide, l'option resterait sans valeur).
Les apostrophes dans les chaînes simples sont doublées (`'` → `''`). Le here-string `@'…'@` n'a pas besoin d'échappement (le terminateur `'@` doit être seul en début de ligne).
Les deux lignes `[regex]::Replace` compensent un défaut de Windows PowerShell 5.1 : il n'échappe pas les guillemets doubles quand il transmet un argument à un exécutable natif, si bien qu'un texte de tâche contenant `"` arrivait tronqué et découpé. Elles appliquent les règles de `CommandLineToArgvW` (antislashs doublés devant un guillemet, guillemet échappé, antislashs finaux doublés quand PowerShell entourera l'argument de guillemets). Le titre passé à `--name` subit le même traitement côté hôte (`AgentLauncher.NativeArg`).

Commande de lancement : `powershell.exe -NoExit -NoLogo -ExecutionPolicy Bypass -File "<script.ps1>"` avec `WorkingDirectory = cwd`, nouvelle console. Si `settings.terminal == "wt"` et que `wt.exe` existe : `wt.exe -d "<cwd>" powershell.exe -NoExit -NoLogo -ExecutionPolicy Bypass -File "<script.ps1>"`.

Environnement hérité : au démarrage, l'hôte retire de son propre environnement les marqueurs qu'une session Claude Code pose dans ses processus enfants (`InheritedEnvironment` : `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET` / `_TOKEN`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `AI_AGENT`) et note dans `host.log` ceux qu'il a trouvés. Lancé depuis une session Claude Code (par exemple par l'agent des remarques après une publication), Organizator les transmettrait sinon à chaque `claude` qu'il ouvre ; celui-ci se croirait session enfant et n'enregistrerait pas sa transcription (« Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker ») : conversation illisible dans le panneau et impossible à reprendre. Les variables que l'utilisateur fixe lui-même dans `~/.claude/settings.json` (`env`) ne sont pas touchées : `claude` les réapplique à son démarrage.

Même passage, mêmes causes : les variables qui coupent la couleur (`NO_COLOR`, `FORCE_COLOR`, `CLICOLOR`, `CLICOLOR_FORCE`) sont retirées elles aussi. Claude Code pose `NO_COLOR=1` dans ses enfants pour lire leur sortie sans codes ANSI ; hérité, il rendait **entièrement gris** chaque terminal ouvert depuis Organizator, l'agent y suivant la règle de `supports-color`. Elles ne sont retirées que si elles ne figurent **pas** dans l'environnement persistant de l'utilisateur ou de la machine (`EnvironmentVariableTarget.User` / `Machine`, c'est-à-dire le registre) : un réglage voulu est respecté, un réglage hérité d'un parent ne l'est pas.

## Dictée et transcription

Whisper (whisper.cpp, par **Whisper.net 1.8.1**) tourne dans l'hôte, sur le processeur : la voix ne quitte pas le poste. Deux usages, un même service (`WhisperTranscriber`) : la **dictée** dans les zones de saisie, et la **transcription des enregistrements joints** aux tâches.

**Hôte.**

- **Moteur natif.** Le paquet `Whisper.net.Runtime` copie ses DLL (`whisper.dll`, `ggml-*.dll`) à côté de l'exe par ses propres cibles, en `None` : la publication en fichier unique les laisserait hors de l'exe. Le `.csproj` exclut donc ces cibles (`ExcludeAssets="build;buildTransitive"`) et embarque les quatre DLL win-x64 en ressources (`whisper/win-x64/…`, chemin du paquet par `GeneratePathProperty`) ; `PrepareNative` les extrait sous `<données>\whisper\runtime-<version>\runtimes\win-x64\` (réécrites seulement si leur taille change) et pointe `RuntimeOptions.LibraryPath` dessus, avec `RuntimeLibraryOrder = [Cpu]`. Un processeur sans AVX2 reçoit un message lisible.
- **Choix mesurés** (Core Ultra 7 265H, audio de synthèse en français, 8 fils) : `small` transcrit 11 s de dictée en 2 à 3 s et 1 min 43 en 17 s ; `large-v3-turbo-q5_0`, plus juste sur les noms propres, prend 18 s et 64 s ; `base`, 0,7 s mais approximatif. Le runtime **Vulkan** (iGPU Intel Arc) était plus lent (12 s) et pesait 58 Mo : seul le CPU est livré. **Whisper.net 1.9** a été écarté : il tire `Microsoft.Extensions.AI` et System.Text.Json 10 dans l'appli, pour 25 % de vitesse. Réduire `audio_ctx` sur une dictée courte accélérait mais faisait halluciner (« Merci. ») : pas retenu.
- **Modèles** (`Models` : `base`, `small` par défaut, `large-v3-turbo-q5_0`) : `ggml-<id>.bin` téléchargé depuis `huggingface.co/ggerganov/whisper.cpp` en `.part`, renommé une fois complet (taille = `Content-Length`) — un fichier présent est donc entier. Un seul téléchargement par modèle, partagé par tous ceux qui l'attendent ; annuler une transcription cesse d'attendre sans interrompre le téléchargement. `RemoveAsync` interrompt un téléchargement ou supprime le fichier (refusé pendant une transcription).
- **Transcription** (`TranscribeAsync(job, load, model, language, paragraphs, what)`) : modèle téléchargé s'il manque (événement `download` sur `job`, puis ceux du modèle), décodage hors du fil de l'interface (`AudioDecoder`), puis **une transcription à la fois** (sémaphore ; `queue` si une autre tourne). Le modèle chargé (`WhisperFactory`) reste en mémoire dix minutes après la dernière, puis il est libéré ; un autre modèle remplace le précédent. `WithThreads(clamp(cœurs / 2, 2, 8))`, `WithLanguage` (`auto` = détection), avancement par `WithProgressHandler` (toutes les 250 ms). L'annulation passe par le rappel d'abandon de whisper.cpp (jeton lié). Les segments « fantômes » que Whisper entend dans un silence — didascalies `[Musique]`, `(rires)`, mentions de sous-titrage — sont écartés. Dictée : texte d'un seul tenant ; enregistrement : un paragraphe à chaque silence de 2 s ou plus.
- **Transcription enrichie** (Révizator, `transcribe` avec `detail`) : `TranscribeAsync(…, detail, reference, accent)` ajoute `WithTokenTimestamps()` et `WithProbabilities()` — jamais de `prompt` : le texte attendu ne sert qu'à l'alignement, Whisper le recopierait. Sans `detail`, rien ne change (mêmes appels, même réponse, même journal : vérifié contre l'ancienne DLL). Les mots sont refaits des jetons de chaque segment gardé (`SpeechAssessment.WordsFromTokens` : un jeton qui commence par une espace ouvre un mot, jetons `[_…]` et `<|…|>` écartés, `p` = moyenne des jetons, `pMin` = minimum). **P(en)** (avec `accent: true`) vient d'une détection libre de la langue sur les 30 premières secondes, même quand `en` est imposé : Whisper.net 1.8.1 ne rendant que la langue gagnante, `NativeLanguage` refait ses appels (`whisper_init_state`, `whisper_pcm_to_mel_with_state`, `whisper_lang_auto_detect_with_state`) par l'API C de la `whisper.dll` chargée et lit tout le tableau des probabilités ; à défaut, `DetectLanguageWithProbability`. Cette détection est un passage d'encodeur de plus — le double du temps d'une dictée courte — : l'UI ne la demande pas par défaut. `SpeechAssessment` (fonctions pures) : normalisation avant alignement (casse, ponctuation, apostrophes typographiques, contractions, hésitations retirées, orthographe britannique ramenée à l'américaine, mots composés ; nombres en chiffres — « two forty-seven » = « two hundred and forty-seven » = « 247 », « twenty twenty-seven » = « 2027 », « six fifteen p.m. » = « 6.15pm », « three thirty » = « 3.30 », « $39.99 », « March third » = « March 3 ») ; alignement de Levenshtein par jeton (`wer` = (S + D + I) / jetons attendus, `accuracy` = 1 − WER borné ; `ref` / `hyp` sous forme normalisée, `refIndex` / `wordIndex` pour colorer le texte tel qu'écrit) ; pauses sur l'énergie (RMS par 20 ms, seuil = bruit de fond + 35 % de l'écart avec la parole, 6 à 25 dB ; silences de 300 ms ou plus entre la première et la dernière parole, rattachés au mot dont la fin est la plus proche — au précédent si Whisper a écrasé ce mot contre lui) ; débit sur la durée premier → dernier mot resserrée sur l'énergie, débit d'articulation sans les pauses. `keep` écrit le WAV reçu par `LearningStore.SaveAudio` (`learning\audio\rec-<date>-<6 hex>.wav`) après une transcription réussie ; un échec d'écriture laisse la transcription (`keepError`). Mesuré : pauses de 1,26 s et 0,80 s retrouvées sur un WAV de synthèse ; lecture parfaite avec chiffres, WER 0 (0,14 à 0,58 sans normalisation) ; anglais lu par une voix française, P(en) 0,19 (≥ 0,99 pour les voix natives). Journal : `Whisper : dictee (detail) de 10,1 s transcrit en 18321 ms (small, en, 126 caracteres) ; detail : P(en) 0.19 (fr, 8003 ms), 21 mots, 144 mots/min, 0 pauses, exactitude 0.74`.
- **Fantômes anglais** : le filtre écarte aussi « Thank you for watching », « Thanks for watching », « Subtitles by … », « Captions by … », « Please subscribe… », « Don't forget to like and subscribe… » (segment entier) ; « Thank you. » seul reste, c'est une vraie réponse.
- **Limites à garder en tête** : Whisper est un modèle de langue, il lisse les hésitations et répare des fautes de grammaire ou de prononciation devinables (d'autant plus que le modèle est grand : Small pour noter) ; un mot non reconnu est un vrai signal, un mot reconnu ne prouve pas une bonne prononciation ; les horodatages des jetons sont à ±100-200 ms.
- **`AudioDecoder`** : fichiers par `MediaFoundationReader` (NAudio) — mp3, m4a/aac, wav, wma, flac, et ogg/opus/webm/mkv grâce aux extensions multimédias de Windows (webm/opus et wma vérifiés) ; le son d'une vidéo est lu de même. Mixage des canaux (`DownMix`), rééchantillonnage `WdlResamplingSampleProvider` à 16 kHz, trois heures au plus. Un format que Windows ne lit pas donne « Windows ne sait pas lire « x » (…). Convertissez-le en .mp3 ou .wav. »
- **Micro** : `MainWindow.OnPermissionRequested` accorde `Microphone` à la page de l'application (`app.organizator`) et à elle seule, sans quoi WebView2 afficherait sa propre demande ; un rapport affiché dans un cadre n'y a pas droit.
- `transcribe` avec `path` n'accepte qu'un fichier sous le dossier des pièces jointes. `host.log` note chaque transcription (`Whisper : enregistrement x de 103,0 s transcrit en 17459 ms (small, fr, 1487 caracteres)`), les chargements et libérations de modèle, les téléchargements.

**UI** (`app.js`, section « Dictée et transcription ») :

- **Le micro** (`#dictate`, créé par `bindDictate`, hors des zones de rendu) se pose dans le coin bas droit, à l'intérieur, de la zone de texte qui a le focus (`dictTarget` : une `textarea` avec `data-focus-key`, ni désactivée ni en lecture seule), barre de défilement évitée (`placeDictate`). Il suit le focus (`focusin` / `focusout` en capture, avec repli sur `document.activeElement`), la frappe, le défilement et chaque rendu (`syncDictate` en fin de `render` et de `renderActivity`) ; un champ reconstruit se retrouve par sa clé (`dictField`). `mousedown` sur le micro est annulé : le champ garde le focus et le curseur.
- **Enregistrement** (`startDictation`) : `getUserMedia` (écho, bruit et gain automatiques), `MediaRecorder` par tranches d'une seconde, `AnalyserNode` pour le niveau ; `whisperWarm` part aussitôt pour que le modèle se télécharge ou se charge pendant qu'on parle. La pastille (`is-rec`) montre le chrono et le niveau, réécrits sur place toutes les 100 ms (`tickDictate`), sans redessiner. **Ctrl + Maj + Espace** (écouteur `keydown` sur `window`, en capture) démarre et termine, Échap annule — tous deux arrêtés là (`stopPropagation`) pour ne pas refermer le dialogue dessous. Dix minutes au plus ; moins de 0,4 s, c'est un clic involontaire (« Rien d'enregistré »).
- **Envoi** (`recordingStopped`) : le webm/opus est décodé (`decodeAudioData`) et rééchantillonné en mono 16 kHz par un `OfflineAudioContext`, encodé en WAV 16 bits (`wavBlob`), puis `transcribe` avec `data` ; la pastille (`is-busy`) dit l'étape (`whisperPhaseLabel` : « Téléchargement du modèle · 37 % », « Chargement du modèle… », « Transcription · 50 % »), × abandonne (`cancelTranscribe`).
- **Insertion** (`insertDictation`) : à la sélection courante si le champ a encore le focus, sinon là où était le curseur au départ ; espace ajoutée de part et d'autre au besoin, majuscule en début de champ, de ligne ou de phrase. Par `document.execCommand('insertText')` : l'annulation (Ctrl + Z) défait la dictée, et l'événement `input` qu'il déclenche fait enregistrer la saisie par les gestionnaires existants (`composer-text`, `edit-text`, `remark-new`, `rv-chat-q`…) — rien n'est propre à un champ. Repli (jsdom) : valeur posée puis `input` émis. Champ disparu : presse-papiers et toast.
- **Enregistrements joints** : `transcribeAttachment(owner, att)` (bouton `transcribe-attachment`, ou d'office depuis `receiveAttachments`) tient l'état dans `ui.transcribing[att]` (`{ owner, job, phase, percent, received, total }`) ; `attachMediaHtml` pose à côté de la pastille de l'enregistrement l'avancement (`.att-tr`, libellé `data-tr` réécrit par `patchTranscribing` sans rendu) avec × (`cancel-transcribe`), ou le bouton **Transcrire** tant qu'aucun bloc ne porte `source` = cet enregistrement. Résultat : un bloc `{ kind: "text", name: "Transcription — <nom>", text, source }` poussé dans la liste (le formulaire de lancement ouvert suit, `editAttachments`), copie disque par `writeTextNow`. Tâche supprimée, création abandonnée ou enregistrement retiré : la transcription est annulée (`cancelOwnerTranscriptions`, `removeAttachment`) et rien n'est joint. Texte vide : « Aucune parole reconnue ».
- **Événement `whisper`** (`onWhisperEvent`) : un `job` met à jour la dictée ou la pièce jointe concernée ; un téléchargement de modèle (`model` seul) fait avancer tout ce qui attend ce modèle et la ligne des Réglages (`data-whisper-dl`), puis `downloaded` / `download-failed` relit l'état (`refreshWhisper`).
- **Réglages › Dictée** (`voiceSettingsHtml`) : interrupteurs `toggle-whisper` et `toggle-whisper-auto`, langue (`whisper-language`), et une ligne par modèle (`wm-row`) : choix (`whisper-model`), taille, note, état — Télécharger (`whisper-download`), « Téléchargement · 35 % » avec Interrompre, ou Téléchargé avec Supprimer (`whisper-remove`). L'état est relu à l'ouverture de l'onglet.

## Pages

La file est la page d'accueil ; d'autres pages s'enregistrent auprès d'`app.js` par `window.__organizator.registerPage(def)`, avant le premier rendu (leurs scripts sont chargés après `app.js` dans `index.html`, et `boot` attend `DOMContentLoaded`). Une seule aujourd'hui : **Révizator** (`revizator/core.js`).

- `def = { id, label, title, icon, badge(), render(host, enter), renderBar(bar), onBoot(), onShow(), onHide(), onFocus() }`. `registerPage` rend le **`pageApi`**, seul accès d'une page aux internes d'`app.js` : `state`, `render`, `toast`, `goPage`, `currentPage`, `addAction(name, fn)` (actions `data-act`, sans écraser celles de la file), `addInput(role, fn)` / `addChange(role, fn)` (rôles `data-role`, consultés avant ceux de la file), `addKey(fn)` (raccourcis, appelés seulement si aucun dialogue, lecteur ou cloche n'est ouvert), `addSettingsTab({ id, label, lead, html(settings), onOpen() })` (onglet inséré avant « Dossiers »), `openSettingsTab(id)`, `overlayOpen()`, et les utilitaires `esc`, `uid`, `color`, `setHtml`, `isTyping`, `icon` (= `ICON`), `fmtDate`, `fmtTime`, `fmtDay`, `fmtSize`, `fmtClock`, `setRowHtml`, `setFieldHtml`, `switchHtml`, `modelSelectHtml`, `effortSelectHtml`, `catalogFor`, `catalogHas`, `customModel`, `hasProvider`, `recordVoice`, `recording`, `wav16k`, `readBase64`, `whisperOn`, `whisperPhaseLabel`.
- **En-tête** : `.brand` réunit le titre et `#page-tabs` (`renderPageTabs` : « File », puis une pastille par page, `data-act="go-page"`, badge facultatif). La page courante est `S.ui.page` (`currentPage()` rend `queue` pour une page inconnue), retenue dans `localStorage` (`organizator.page`), une commodité d'affichage.
- **Rendu** : `render()` pose `#app[data-page]` ; sur la file, `renderFilters` et `renderList` comme avant ; sur une autre page, `renderPageBody` appelle `def.renderBar(#page-bar)` (barre propre à la page, à gauche des boutons globaux de `.filters`) et `def.render(#page-host, enter)` (`enter` vrai au premier affichage de la page). La recherche, les filtres, les revues, les catégories et la file sont masqués en CSS (`.app[data-page]:not([data-page="queue"]) …`) ; la cloche, les remarques, les réglages, le panneau, le lecteur, les dialogues et les cartes de l'en-tête restent communs. `renderActivity()` ne redessine la file que si elle est affichée. `openNotification` revient d'abord à la file.
- **Micro** : `recordVoice({ maxMs, noiseSuppression, onTick(ms, level), onLimit })` enregistre comme la dictée (`getUserMedia`, `MediaRecorder`, WAV 16 kHz mono par `wav16k`) et rend `{ stop() → Promise<{ data (base64), seconds, blob }>, cancel(), level() }` ; une seule prise de son à la fois, dictée comprise. Deux attributs de `textarea` règlent la dictée : `data-dict="off"` (pas de micro : un exercice d'écrit se tape) et `data-dict-lang="en"` (langue forcée pour ce champ, quel que soit le réglage).
- **Shim** : `bridge.shimRegister(type, fn(payload, emit))` (hors WebView2 seulement) ajoute une simulation consultée avant celles de `bridge.js` ; `fn` rend la réponse, une Promise, ou `undefined` pour laisser la main (ex. `transcribe` sans `detail`). `bridge.shimEmit(name, payload)` pousse un événement.
- `window.organizatorFlush` est enveloppé par la page pour vider aussi sa propre sauvegarde à la fermeture.

## Révizator

L'espace « réviseur » d'Organizator : l'anglais d'abord (matière `en`). Un noyau (`revizator/core.js`, `revizator.css`) fournit l'objet global `window.Revizator` (alias `R`) ; des modules y enregistrent leurs vues, leurs cartes d'accueil, leurs actions et leurs simulations. **L'API exacte est décrite en tête de `core.js`.** Préfixes : actions et rôles `rz-…` (`rz-lesson-…`, `rz-srs-…`, `rz-tutor-…`…), classes `.rz-` (noyau), `.rzx-` (exercices), `.rzl-` (cours), `.rzt-` (bilans), `.rzp-` (progrès), `.rzv-` (tuteur).

### Le noyau

- **Vues** : `R.view(id, { label, icon, order, nav, render(enter) → html, after(host), onShow(params), onHide(), keydown(e, el, role) })`, `R.go(id, params)`. Une vue rend une chaîne HTML, réinsérée dans `#page-host` (par `setHtml`) à chaque rendu complet de l'application : l'état vit dans `R.ui.<module>` (mémoire) ou `R.data` (persisté), jamais dans le DOM ; un champ porte un `data-focus-key` stable ; un conteneur défilant `data-rz-scroll="<clé>"` garde son défilement. La saisie met l'état à jour sans rendu complet (au plus un `R.patch`). `R.renderSoon()` attend une pause de frappe. La vue ouverte est retenue (`localStorage`, `organizator.revizator.view`, sauf `session`).
- **Accueil** : `R.homeCard({ id, area: 'hero'|'main'|'side', order, html() })` ; le noyau y pose le premier lancement (objectif, rythme, niveau de départ, voix) tant que `profile.onboarded` est faux, puis les cartes des modules et les siennes (« Votre niveau » : bandes CECRL par compétence ; « Cette semaine » : séances faites / objectif, minutes par compétence).
- **Persistance** : `learnLoad` au démarrage (`onBoot`), `R.data` = `learning.json.subjects.en` normalisé, `R.save()` 800 ms après la dernière modification (immédiat avec `R.save(true)`, au changement de page, à la fermeture et quand la fenêtre est masquée). Les listes sont rognées (journal de révision 3 000, séances 500, tentatives 200, cours et séries 100, conversations 30). Documents : `R.doc(kind, id)` (cache mémoire), `R.docSave`, `R.docDelete`.
- **Générations** : `R.gen(kind, params, { model, effort, context, job, timeout })` envoie `learnGenerate` avec le modèle et l'effort des réglages (`lessonModel` / `lessonEffort` pour le cours, `genModel` / `genEffort` pour exercices et bilans, `gradeModel`, `tutorModel`, `cardModel` pour le correcteur des cartes, `haiku` par défaut) et le **contexte de l'apprenant** (`R.context()` : objectif, centres d'intérêt, niveaux par compétence, dernier bilan, points faibles du journal d'erreurs avec un exemple, derniers cours, cartes déjà connues, langue des explications — 8 000 caractères au plus). L'avancement (`learn`) met à jour sur place les lignes `[data-rz-job]` et la barre (« Cours en préparation · 1:12 ») ; la fin émet `jobDone`. Au démarrage, `learnJobs` réattache les générations encore en cours côté hôte (`learnWait`) : un rechargement de la page ne perd rien, et les modules intègrent les résultats de façon idempotente.
- **Modèle de l'apprenant** : un θ par compétence (`read`, `listen`, `write`, `speak`, `lang`), sur une échelle logit où un niveau CECRL vaut une unité (A2 = −1, B1 = 0, B2 = 1, C1 = 2 ; « B1+ » au-delà de B1 + 0,2), affiché en bande, jamais en décimales, avec une confiance. `R.observe(skill, cefr, x)` (réponse à un item, Elo : `θ += K (x − p)`, `K = max(0,6 / (1 + 0,05 n), 0,08)`), `R.observeLevel(skill, level)` (niveau estimé d'une production par le correcteur), `R.calibrate(skill, θ, poids)` (bilan). Journal d'erreurs par catégorie de la taxonomie fermée (`R.addErrors`, `R.weakPoints` : nombre × récence). Séances (`R.logSession`, minutes par compétence) et semaine (`R.week`, lundi → dimanche, une séance compte à partir de 5 minutes). Langue des explications : français jusqu'à B1+, anglais simple avec notes en français en B2, anglais au-delà (`R.explainLang`, réglable). Séance reprenable : `R.setActive` (le cours du jour).
- **Audio** : `R.tts.say(text, opts)`, `R.tts.script(lines, speakers, opts)`, `R.audio(url)` rendent un lecteur (`play`, `pause`, `toggle`, `stop`, `replay`, `setRate`, `done`). Moteur : les voix naturelles (`speak` / `speakScript`, lecture dès la première phrase annoncée, une ligne de dialogue après l'autre avec un blanc de 450 ms) si elles sont installées, sinon `speechSynthesis` (voix OneCore de Windows), sinon un minuteur qui simule la durée. Les voix suivent l'accent et le sexe de chaque locuteur (`R.tts.voicesFor`, voix américaine et britannique préférées dans les réglages). Un seul lecteur à la fois, et dans un lecteur **une phrase à la fois** : pendant le blanc entre deux lignes, la suivante est déjà programmée (`gapTimer`) et `pump` n'en programme pas d'autre — une phrase annoncée par l'hôte, ou la fin de la synthèse, pendant ce blanc relançait la même phrase une seconde fois, d'où des voix en double, dont une qu'aucun « stop » n'atteignait ; chaque `Audio` ne fait avancer la lecture que s'il est encore le son courant. `R.h.player(key, { source, maxPlays, label })` dessine les boutons (lecture, reprise, vitesse 0,8 / 1 / 1,15) ; l'état et le surlignage de la ligne lue (`[data-rz-say=key][data-rz-idx=i]`) sont mis à jour sur place, sans rendu.
- **Micro** : `R.h.rec(key, { maxMs, stt: { reference, keep }, onResult })` (bouton, chrono, niveau, réécoute de sa propre voix ; Espace démarre et termine quand un seul micro est affiché) ; `R.stt(data, { reference, keep, accent })` envoie `transcribe` avec `detail` et la langue `en`, modèle `prefs.whisperModel` (Small par défaut : un grand modèle devine trop bien ce que l'apprenant voulait dire).
- **Retour de correction** : `R.h.feedback(grade, { response, mode })` (niveau de la réponse, notes 0-5, réussites, priorité, erreurs prioritaires avec catégorie et explication, améliorations repliées, texte corrigé en différences mot à mot, tournures à réemployer).
- **Réglages › Révizator** : voix (état, téléchargement ou suppression des voix naturelles, moteur, voix US et GB, débit), agents (modèle et effort par usage), apprentissage (séances par semaine, durée habituelle, langue des explications, objectif, centres d'intérêt, rétention visée, modèle Whisper de l'oral), données (comptes, « Repartir de zéro » en deux clics). Les préférences vivent dans `learning.json` (`prefs`, `profile`), pas dans `settings.json`.
- **Notifications** : une génération finie hors de la page ou fenêtre masquée → toast « Ouvrir » et notification Windows (`notify`, `args` = `rz=<vue>`, que le noyau reconnaît dans `notificationClicked`).

### Les modules

- **Cartes, items, exercices** (`srs.js`, `items.js`, `exercise.js`) : FSRS-6 de py-fsrs (21 paramètres par défaut, `prefs.retention`), échéances au début de journée (bascule à 4 h), dispersion stable par carte, Difficile ≤ Bien < Facile. Étapes d'apprentissage jouées dans la séance : une carte ratée revient après 3 à 5 autres, trois fois au plus. `R.cards` gère `R.data.cards` (`{ id, kind, front, back, example, audioText, origin: { kind, ref }, createdAt, suspended, fsrs: { state, S, D, due, last, reps, lapses, step } }` ; doublon = même recto normalisé) et `R.data.reviewLog` (`{ c, g, at, ms }`). Le composant `R.srs.start(clé, { max, minutes, newMax, onDone })` / `R.srs.html(clé)` s'insère dans n'importe quelle vue (échauffement du cours) ; le mode d'une carte (reconnaissance, production, production inverse au-delà de S = 7 j, correction d'erreur) est déduit de son contenu. Notation automatique par `R.text.match` (exact → Bien, presque / indice / lenteur → Difficile, faux → À revoir) ; Facile seulement sur action ; une réponse tapée refusée part chez le **correcteur** (`askChecker` → `R.gen('cardcheck', { level, card, instruction, prompt, expected, answer })`, affichage `checkHtml` sous le verdict) : `right` relève la note proposée (Bien, Difficile après indice ou lenteur) et, avec `accept`, ajoute la réponse à `card.accepted` ; `close` → Difficile ; `wrong` confirme, avec ce qu'il fallait taper. Une révision validée par Entrée (note proposée, `cur.rated.auto`) avant son retour est renotée (`regrade` : même état de départ, même instant, même dispersion, entrée du journal de révision corrigée, reprise dans la séance retirée si elle n'a plus lieu d'être, carte sortie des sangsues) tant que la carte n'a pas été revue ; une note choisie (1 à 4) n'est pas touchée ; correcteur indisponible → le verdict local reste. **Cartes floues** (`fuzzy` : révisées en tapant, hors reconnaissance inverse et prononciation, dont le verso nettoyé contient `=`, `≠`, `…`, ` — `, ` / ` ou une seconde phrase, ou dont la réponse attendue dépasse 40 caractères) : `fixFuzzy` en envoie 12 au plus à `R.gen('cardfix', { level, cards })` en tâche de fond — à l'ouverture de la vue Cartes, au début d'une séance, 4 s après l'ajout d'une carte floue, lot suivant 1,5 s après ; échec → nouvel essai dans 30 min — et `applyFix` remplace recto, verso (la réponse exacte), note et exemple, ajoute les variantes à `accepted`, garde l'original dans `card.orig` ; toute carte envoyée reçoit `fixedAt`. Vue Cartes : filtre « Clarifiées par le correcteur », mention « clarifiée par le correcteur » (avant → après en infobulle), « Version d'origine » (`unfix` : original rétabli, `fixKeep`, plus jamais proposée), variantes acceptées affichées ; sangsue au 6e oubli (suspendue). `R.items.check(item, réponse)` → `{ verdict, score, expected }` pour les 15 genres de la spec (QCM, vrai/faux, trous, transformation, traduction, ordre, erreur à corriger, dictée complète ou à trous, paires minimales, accent de mot, shadowing, lecture à voix haute, écrit et oral libres) ; une réponse corrigée appelle `R.observe` au premier essai ; l'écrit et l'oral libres passent par `R.gen('grade')`, puis `R.addErrors`, `R.cards.addMany`, `R.observeLevel`. Vue Exercices : 21 types sur 6 compétences, suggestions tirées des points faibles et de la compétence la moins travaillée, consigne libre ; une série en cours garde sa progression dans `R.data.exercises[].progress`, son résultat dans son document.
- **Le cours du jour** (`lesson.js`) : carte d'accueil selon l'état (préparation en cours, reprise, cours prêt, fait, échec, ou formulaire : durée, sujet), `R.gen('lesson', { minutes, level, topic, voices, avoidRubrics, timeless })` ; pendant la préparation, les étapes de l'agent et les titres du jour (`learnNews`). Le cours est indexé dans `R.data.lessons` (`{ id, day, minutes, title, rubric, tone, keywords, grammar, genre, level, status, createdAt, doneAt, result? }`), le document complet restant dans `learning\lessons\<id>.json`. Un sujet imposé (`R.data.nextTopic`) n'est consommé qu'au succès. La séance vit dans `R.data.active` (`{ kind: 'lesson', id, step, data }`, sauvegardé à chaque geste) : étapes du `plan` sans blocs vides + bilan, secondes passées par étape (minuteur seulement vue affichée et fenêtre visible), réponses par item, écrit et oral (texte, correction, phrase refaite, transcription compacte). Échauffement par `R.srs`, corrections par `R.gen('grade')` suivies d'une action (réécrire ou redire `redo`, cartes), fin par `R.logSession` (minutes réelles par compétence), cours marqué fait avec son bilan, `nextTopic` enregistré.
- **Le tuteur** (`tutor.js`) : six écrans (`pick`, `chat`, `summary`, `history`, `open`, `capsule`). Les scénarios portent le rôle, l'objectif et le cadre en anglais pour le modèle, leur version française pour l'écran, une voix et quatre tournures d'appui. Un tour : la réplique de l'apprenant (micro, `keep: true`, mots à `pMin` < 0,5 soulignés, ou champ texte), puis `R.gen('tutor', { scenario, history (12 derniers tours), level, lesson, end, lang, explain })` ; la réponse est lue par `R.tts.say`, la reformulation (`recast`) rattachée à la dernière réplique si `said` y figure. Échec, annulation ou rechargement : la réplique reste, « Réessayer » relance. La fin (`end: true`) rend le bilan, appliqué une fois : `R.addErrors`, `R.observeLevel('speak')`, `R.logSession({ kind: 'tutor' })`, cartes à la demande. Conversations dans `R.data.tutor.chats` (sauvegardées à chaque tour, reprenables ; `R.setActive` reste au cours du jour), capsules dans `R.data.capsules`.
- **Bilans et progrès** (`test.js`, `progress.js`). **Estimateur** (`R.toeic`, port ES5 de l'estimateur du rapport de recherche) : modèle logistique à pente commune et pseudo-hasard fixé (c = 0,8 / nb d'options), `P = c + (1 − c) / (1 + exp(−(S − d) / σ))` avec σ = 90 (écoute) / 95 (lecture), difficulté `d` = centre de la bande CECRL officielle du niveau de l'item + ajustements par caractéristiques (réponse indirecte, paraphrase, recoupement entre textes…) + décalage de calibration ; EAP sur une grille −150…650 (pas 5), a priori de population faible (N(325, 150²) en écoute, N(260, 150²) en lecture), erreur de modèle 35 points (25 puis 20 après calibration), IC à 90 % par quantiles élargis, probabilités CECRL par masse a posteriori entre les seuils ETS (fiche 2025 : écoute 110 / 275 / 400 / 490, lecture 115 / 275 / 385 / 455 pour A2 / B1 / B2 / C1). Total = L + R, écarts types combinés. Tendance : Kalman 1D par section, total, S et W (dérive de 4 points par √jour). Oral et écrit : composite pondéré → 0-200 (`estimateProductive`, heuristique de conception, non ETS). `thetaOfScore` place chaque seuil officiel à mi-chemin de deux centres de niveau du noyau pour `R.calibrate`. Précision simulée d'un bilan express : ≈ ±55-65 points par section, IC à 90 % ≈ ±150 sur 990. **Bilan express** : composition du format adaptatif officiel réduite (étape 1 : écoute P2 ×5, P3 ×3, P4 ×3, lecture P5 ×3, P6 ×4, P7 ×3 ; étape 2 facile ou difficile : P2 ×3, P3 ×6, P4 ×3, P5 ×3, P7 ×7) ; `prep` (trois `R.gen('toeic')` en parallèle, jobs persistés, intégration idempotente des `jobDone` réattachés) → `run` (état complet persistant dans `R.data.toeic.run` : phase, position, réponses `docId:setId:qId → indice`, chrono de lecture `ms + (from ? now − from : 0)`). Routage par section (`routeStage2` sur l'EAP provisoire de l'étape 1) ; les sections d'étape 2 non servies sont gardées en banque pour le bilan suivant. Un minuteur commun (250 ms) fait avancer les échéances et réécrit les chronomètres par `R.patch`, sans rendu complet ; il met l'examen en pause dès que la vue Bilans n'est plus affichée. Audio : `R.tts.script` (une voix par locuteur, narrateur distinct ; en P2 la question puis « A. … B. … C. … » par une autre voix), fin d'audio = `player.done`. `R.setActive` n'est pas utilisé (le cours du jour garde cet emplacement). **Bilan oral et écrit** : étapes dérivées du document `sw` ; micro `R.h.rec` déclenché par `R.recToggle` à la fin de la préparation ; corrections `R.gen('grade', { rubric: 'sw', … })` dans une file à 3 en parallèle, jobs persistés et réintégrés après rechargement ; corrections complètes gardées dans le document `sw` (`learnDocSave`), notes compactes dans `R.data.toeic.swRun.grades`. **Progrès** : SVG en chaînes (viewBox fixe, largeur 100 %), couleurs par jetons CSS `--rzp-*`, info-bulle unique `.rzp-tip` posée par délégation (`pointermove`, `focusin`), texte par `textContent` ; chaque marque interactive porte `data-rzp-tip` et `tabindex="0"` ; chaque graphique a sa table de données (`<details>`). Mention obligatoire partout où un score paraît : « format type TOEIC® · score estimé, non officiel — TOEIC est une marque déposée d'ETS, qui n'est pas associé à Révizator ». Simulation : `revizator/fixtures/toeic-<module>.json`, `sw.json` (de vrais documents de l'hôte).

### L'hôte

Trois services, créés par `BridgeHost` :

- **`LearningStore`** — `learning.json` à la racine des données (écrit tel quel par l'UI ; l'hôte ne l'interprète pas) : écriture atomique (`.bak` de la version précédente, seulement si elle est lisible, `.tmp` puis `Move`), relecture du `.bak` si le fichier est illisible, refus au-delà de 20 Mo. Dossier `learning\` : `lessons\`, `exercises\`, `toeic\`, `sw\` (un `<id>.json` par document, identifiant `[a-z0-9-]{4,40}`, jamais de chemin venu de l'UI), `audio\<id>.wav` (enregistrements gardés : `SaveAudio(wav, id?)` → `{ id, url, path }`, utilisé par `transcribe` avec `keep`), `news.json` (cache du menu). `learning\` est servi sous `https://learn.organizator/` (`MainWindow`, accès `Allow`).
- **`NewsMenu`** — menu du jour du cours : 13 flux de presse (BBC, Guardian, France 24, Euronews, Al Jazeera, NPR, The Conversation, The Local, RTÉ, The Register, Phys.org, ESPN…) et 3 flux BBC Learning English lus en parallèle par `HttpClient` (user-agent de navigateur, 5 s par flux, < 1 s en tout). Filtres : doublons, live blogs, vidéos, revues de presse, lettres d'information, contenus sponsorisés, plus de 48 h ; titres « lourds » marqués `heavy`. `readable` dit si WebFetch peut ouvrir la page (BBC, Guardian, Reuters… sont fermés à l'outil de Claude) ; NPR est réécrit vers `text.npr.org`. 30 à 40 titres et 2 à 4 épisodes (mp3 en https). Cache de 30 minutes. Le menu passe dans le prompt du cours : l'index de WebSearch a un à deux jours de retard, la fraîcheur vient des flux.
- **`LearningAgent`** — générations par `claude -p`, **prompt sur stdin** (la ligne de commande est bornée à 32 767 caractères, 8 191 par un `claude.cmd`), `--no-session-persistence`, `--strict-mcp-config`, `--json-schema`, `--append-system-prompt`, `--tools` = `--allowedTools` (`WebSearch,WebFetch` pour le cours d'actualité, rien ailleurs), `--output-format stream-json --verbose --include-partial-messages`, jamais `--bare`. Huit genres, chacun avec ses consignes, son schéma strict (toutes propriétés requises, énumérations banales, aucun champ calculé par le modèle) et son `Sanitize` (classes internes `LessonGenre`, `ExerciseGenre`, `ToeicGenre`, `SwGenre`, `GradeGenre`, `TutorGenre`, `CardGenre` pour `cardcheck` et `cardfix`) : la sortie du modèle est toujours normalisée vers la forme attendue par l'UI (QCM mélangés et clé recalculée, plan sommé, mots de la lecture comptés, dictée à trous réalignée, edits de correction vérifiés dans la réponse de l'apprenant, nombres en lettres dans l'audio des bilans, écoute authentique reprise du menu…). Les documents `lesson`, `exercise`, `toeic`, `sw` reçoivent `id` (`<genre>-<aaaammjj>-<6 hex>`), `kind`, `createdAt`, `day`, `model`, `ms`, `cost`, `turns` et sont enregistrés avant la réponse ; `grade` et `tutor` ne le sont pas. Un modèle ou un effort vide prend les défauts du genre (sonnet / medium pour le cours, sonnet / low pour le reste, haiku pour le tuteur et le correcteur des cartes). Le correcteur n'enregistre rien : `cardcheck` rend `{ verdict: right | close | wrong, expected, explanationFr, accept }` (`accept` seulement avec `right`) ; `cardfix` rend `{ cards: [{ id, front, answer, accepted, note, example }] }`, réduit aux cartes demandées, une erreur à corriger gardant sa phrase fautive et une phrase à trous ne devenant pas autre chose (sinon la carte est écartée). Trois générations au plus, un seul cours à la fois (« Un cours est déjà en préparation. ») ; un `job` réussi il y a moins de 15 minutes rend son résultat sans relancer.

Limites (agent tué avec ses enfants au-delà) : cours 300 s, bilan express 240 s, exercices et bilan oral et écrit 150 s, correction 120 s, réécriture des cartes 120 s, tuteur 60 s, vérification d'une carte 50 s. Mesures du 9 octobre 2026 (haiku 5.5) : `cardcheck` 5 à 7 s, 0,001 $ ; `cardfix` de 6 cartes 24 à 26 s, 0,004 $. Mesures du 8 octobre 2026 : cours 20 min ≈ 100 à 135 s et 0,3 $ au tarif public (une fiche sur trois environ est réécrite par la CLI après un refus du schéma, + 20 à 40 s) ; module de bilan express 100 à 130 s, 0,2 à 0,3 $ ; bilan oral et écrit 15 s, 0,04 $ ; série d'exercices 20 à 30 s, 0,06 à 0,08 $ ; correction 13 à 25 s, 0,04 à 0,07 $ ; tour du tuteur (haiku) 6 à 12 s, 0,002 $. Journal : une ligne `Revizator <genre>` par génération (modèle, durée, tours, coût, taille), une par échec et par fiche refusée.

**Contrat de correction** (`grade`) : corrections minimales, étiquetées `error` ou `improvement`, catégorie de la taxonomie fermée (`pron.*`, `gram.*`, `lex.*`, `disc.*`, `mech.*` — liste dans `core.js`, `CATEGORIES`), `original` présent tel quel dans la réponse (sinon écarté par l'hôte), trois erreurs prioritaires au plus, rien de correct n'est touché, explication courte en français jusqu'à B1+. Les modèles de langue sur-corrigent : c'est ce contrat qui garde le retour utile.

## Synthèse vocale

Les voix anglaises de Révizator sont neuronales et tournent dans l'hôte, sur le processeur : **sherpa-onnx 1.13.8** (`org.k2fsa.sherpa.onnx`, Apache-2.0) et le modèle **Kokoro v1.0 fp32** (82 M de paramètres, Apache-2.0), dix voix — six américaines, quatre britanniques. Un seul service, `TextToSpeech`.

- **Rien dans l'exe.** Le paquet `org.k2fsa.sherpa.onnx.runtime.win-x64` apporterait 21 Mo de DLL natives dans l'exécutable unique : ses actifs sont exclus (`ExcludeAssets="all"`), comme les natives des autres plateformes tirées par le paquet principal (`ExcludeAssets="native"`, sans quoi chaque build copiait 230 Mo sous `bin\…\runtimes\`). L'exe ne gagne que le `sherpa-onnx.dll` managé (50 Ko).
- **Téléchargement** (`EnsureModelAsync`, environ 375 Mo, une fois) : le `.nupkg` du runtime sur `api.nuget.org` (SHA-512 de NuGet vérifié), dont on extrait `onnxruntime.dll` (1.28.2) et `sherpa-onnx-c-api.dll` ; puis les 14 fichiers du modèle, un par un, sur `huggingface.co/csukuangfj/kokoro-multi-lang-v1_0` à la révision épinglée `f7b96bb6` — un dépôt personnel : taille et SHA-256 de chaque fichier sont en dur. `espeak-ng-data` est réduit aux 9 fichiers de l'anglais (0,8 Mo au lieu de 18). Chaque fichier passe par `.part`, son empreinte se calcule au fil de l'eau, il n'est renommé que si tout concorde : un fichier présent est entier. Un seul téléchargement, partagé ; 60 s sans octet, il abandonne. Mesuré : 30 s à 12 Mo/s.
- **Natives** : chargées une fois par processus par leur **chemin complet** — `C:\Windows\System32\onnxruntime.dll` (Windows ML 1.17) n'est pas la bonne version — et `NativeLibrary.SetDllImportResolver` dit au runtime où est `sherpa-onnx-c-api`. Elles ne sont jamais libérées ; supprimées pendant qu'elles sont chargées, elles sont marquées (`runtime-1.13.8.remove`) et effacées au démarrage suivant.
- **Garde-fous du code natif** : un réglage invalide ne lève rien à la construction de `OfflineTts`, et le premier appel tue le processus (`AccessViolationException`, inattrapable). Le code natif ne lit pas non plus les chemins non ASCII (`Données-é`) ni ceux de plus de 260 caractères. Avant chaque chargement, chaque fichier est donc contrôlé (présence, taille), le dossier du modèle passe par son nom court 8.3 (`GetShortPathNameW`) s'il le faut, le plus long chemin qu'espeak-ng composera doit rester sous 240 caractères (sinon : « lancez Organizator avec un dossier de données au nom simple, par exemple `--data C:\OrganizatorData` »), et le pointeur natif de l'objet construit est vérifié avant tout appel.
- **Instances** : une par accent, chargée à la demande — `en-US` = `lexicon-us-en.txt` + `Lang = "en-us"`, `en-GB` = `lexicon-gb-en.txt` + `Lang = "en"` (le code espeak `en-gb` est refusé et rend un son nul). `NumThreads = clamp(cœurs / 2, 2, 6)` : au-delà de 6, le calcul déborde sur les cœurs E et LP-E et n'accélère plus. Un « Hello. » à blanc suit le chargement. Environ 0,5 Go par instance au chargement, 1 Go en régime établi ; libérée après **5 minutes** sans usage.
- **Synthèse** (`SpeakAsync`, `SpeakScriptAsync`) : **une à la fois** (sémaphore ; `queue` si une autre tourne). Le texte est découpé en phrases par l'hôte (`SplitSentences` : retours à la ligne, `. ! ? …` suivis d'une majuscule, d'un chiffre ou d'un guillemet ; épargne `Mr.`, `Dr.`, `p.m.`, `e.g.`, `U.S.`, `No. 5`, les initiales, les décimaux ; une phrase de plus de 280 caractères est coupée à une virgule). Chaque phrase est synthétisée, écrite dans le cache et annoncée (`sentence`, avec son URL) : la page lit la première pendant que la suivante se calcule. Un script se synthétise **dans son ordre**, ligne après ligne — la page s'appuie sur cet ordre pour savoir qu'une ligne est finie ; les autres accents se chargent juste après la première phrase. Annulation (`cancelSpeak`) : le jeton est testé entre deux phrases — sherpa n'appelant son rappel qu'en fin de phrase, la phrase commencée va jusqu'au bout ; l'événement est alors `done { cancelled: true }`. Voix absentes : `speak` échoue sur un message lisible au lieu de lancer le téléchargement, et les phrases déjà en cache restent jouables.
- **Cache** : clé = SHA-256 (20 hex) de `sherpa-1.13.8|kokoro-v1_0|<voix>|<vitesse 0.00>|<phrase normalisée>`, fichier `cache\<2>\<clé>.wav` (PCM 16 bits mono 24 kHz, ≈ 47 Ko/s, `.tmp` puis renommage), servi sous `https://tts.organizator/` (hôte virtuel de `MainWindow`, accès `Allow` : `<audio>`, `fetch` et `decodeAudioData` lisent ces fichiers). Une URL désigne un contenu unique : le cache de WebView2 ne gêne pas. Au-delà de 500 Mo (après une écriture, et au démarrage), les phrases les moins récemment dites partent jusqu'à 450 Mo, sauf celles des 10 dernières minutes.
- **Mesures** (Core Ultra 7 265H, 6 fils, dans l'application) : chargement d'un accent 1,3 à 2,6 s ; RTF ≈ 0,25 à 0,4 (la synthèse va trois à quatre fois plus vite que la lecture) ; une phrase déjà en cache, quelques millisecondes. Whisper small retranscrit les phrases produites sans faute, en US comme en GB.
- **Lecture** : WebView2 refuse `play()` tant que l'utilisateur n'a pas interagi une fois avec la page ; une lecture qui suit un clic passe toujours.
- `host.log` : `TTS : telechargement des voix (375 Mo : …)`, `TTS : voix telechargees en 30 s`, `TTS : DLL natives chargees depuis …`, `TTS : en-US charge en 1300 ms, pret en 1531 ms (6 fils, +473 Mo)`, `TTS : 2 phrases (4,4 s) synthetisees en 2670 ms (af_heart, 1,00, 0 en cache)`, `TTS : en-GB libere`, `TTS : cache reduit (…)`.
- **Licence** : espeak-ng (GPL-3.0) est compilé dans `sherpa-onnx-c-api.dll` ; sans conséquence tant qu'Organizator n'est pas redistribué.

## Mode développement

- `Organizator.exe --wwwroot <dossier>` sert l'UI depuis ce dossier au lieu des ressources embarquées (F5 dans la WebView recharge la page ; l'hôte doit autoriser F5 / Ctrl+R).
- `Organizator.exe --data <dossier>` remplace `%LOCALAPPDATA%\Organizator`.
- Dans un navigateur ordinaire (sans `window.chrome.webview`), l'UI utilise un **shim** : persistance dans `localStorage`, sessions simulées, `pickFolder` via `prompt()`, `readArtifact` rend un rapport Markdown de démonstration — une revue de quatre constats si le fichier s'appelle `review-…` (`window.__fakeArtifact` impose une autre réponse). Ceci permet de développer et tester l'UI dans Chrome. Le cadre isolé du lecteur tourne dans un autre processus : une capture `--headless --screenshot` à temps virtuel le montre vide, il faut piloter la page par le protocole DevTools (`--remote-debugging-port`) et attendre en temps réel.
- Lectures dans le shim : `window.__fakeArtifacts[chemin]` impose la réponse de `readArtifact` pour ce chemin-là (tel que l'UI l'envoie : relatif pour un rapport de la tâche, absolu pour un lien suivi), avant `window.__fakeArtifact` ; même traitement de l'empreinte (`changed: false` si `stamp` est le sien). Chaque lecture est notée dans `window.__reads` (`{ path, stamp }`) — de quoi vérifier l'ordre du préchargement des revues groupées et que seul l'onglet actif est relu. `window.__organizator.openReviewGroup` et `reviewGroupStep` sont exposés pour les essais.
- Discussions dans le shim : `getFindingChats`, `askFinding`, `stopFinding`, `forgetFinding` simulés en mémoire ; `askFinding` pousse `findingChat` (réflexion, « Lit Calc.cs », texte, `done`) puis rend la discussion. `window.__fakeFindingAnswer` impose la réponse (`'error'` la fait échouer), `window.__fakeFindingDelay` sa durée (1,2 s), chaque question est notée dans `window.__findingAsks` ; `window.__organizator.findingChats` expose `fcStore`.
- Whisper dans le shim : `whisperStatus` / `whisperDownload` / `whisperRemove` / `transcribe` / `cancelTranscribe` simulés, avec leurs événements `whisper` (téléchargement en 0,6 s, transcription en `window.__fakeTranscribeDelay` ms, 600 par défaut). `window.__fakeWhisper` impose l'état des modèles, `window.__fakeTranscript` le texte rendu (`'error'` fait échouer, `''` = aucune parole) ; chaque transcription est notée dans `window.__transcribes` (`{ job, path, data: longueur du base64, model, language }`), chaque `whisperWarm` compté dans `window.__whisperWarm`. `window.__organizator.startDictation(champ)`, `stopDictation`, `cancelDictation`, `dictation()`, `transcribeAttachment` et `buildPrompt` sont exposés pour les essais. Hors WebView2, la dictée enregistre vraiment (Chrome demande le micro ; `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` le simule).
- Journal dans le shim : `window.__fakeLogs[sessionId]` impose les messages que rend `getTranscript` (essais du rendu). `window.__organizator` expose `mdBlocksHtml`, `reportsOf`, `usageOf`, `usageText` et `normalizeUsage`.
- Lancements dans le shim : chaque `startSession` est noté dans `window.__sessions` (`{ payload, at }`, heure de traitement — de quoi vérifier l'ordre et l'espacement d'un lot), et `window.__fakeStartError(payload)`, s'il rend un message, fait échouer ce lancement-là (échec partiel d'un lot). `window.__fakeSessions` impose l'état des sessions (`state`, `alive`, `exists`, `agents`, `artifacts`, `answer` pour `getRecaps`) ; `window.__organizator.checkBatches` et `launchBatch` sont exposés pour les essais.
- Révizator dans le shim : `revizator/core.js` déclare ses simulations par `bridge.shimRegister` (actives hors WebView2 seulement) — `learnLoad` / `learnSave` dans `localStorage` (`organizator.learning`, documents dans `organizator.learning.docs`), `learnGenerate` rend après `window.__fakeLearnDelay` ms (1 200 par défaut, avec des événements `learn`) le document de `window.__fakeLearn[kind]` (`'error'` fait échouer) ou celui que le module a déclaré (`R.fixture(kind, fn | doc | 'revizator/fixtures/<x>.json')` — de vrais documents de l'hôte, lus à la demande) ; chaque appel est noté dans `window.__learnCalls`. `ttsStatus` rend `window.__fakeTts` ou « voix absentes » (les lecteurs passent alors par `speechSynthesis`, ou un minuteur sans voix) ; `speak` / `speakScript` simulés rendent des WAV de silence au rythme de la parole. `transcribe` avec `detail` rend `window.__fakeTranscribeDetail` ou une transcription fabriquée à partir de `window.__fakeTranscript`. Les modules ajoutent leurs propres simulations (tuteur, cours, exercices, bilans, correcteur des cartes : `cardcheck` accepte une réponse contenue dans le verso, `window.__fakeCardCheck` impose son verdict ; `cardfix` garde la première réponse du verso et range le reste en note).
