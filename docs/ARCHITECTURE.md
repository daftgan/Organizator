# Organizator — Architecture et contrat JS ↔ .NET

## Vue d'ensemble

Organizator est une application de bureau Windows :

- **Hôte** : application WPF (.NET 8, `net8.0-windows`) qui affiche une seule fenêtre contenant un contrôle **WebView2** plein cadre. L'hôte gère la persistance sur disque, le lancement des sessions d'agent (Claude Code ou GitHub Copilot CLI) dans PowerShell, la lecture des fichiers de session des deux outils, le sélecteur de dossier et l'état de la fenêtre.
- **UI** : page HTML/CSS/JS **vanilla** (aucun framework, aucune étape de build) dans `src/Organizator/wwwroot/`. C'est le portage hi-fi du mockup `Mockup/design_handoff_organizator/`. Elle parle à l'hôte via `window.chrome.webview.postMessage`.

## Persistance

Dossier : `%LOCALAPPDATA%\Organizator\`

- `data.json` — `{ "version": 1, "tasks": [...], "types": [...], "convos": [...], "remarks": [...], "lastType": "k123" }`. Les champs ajoutés dans les objets des tableaux sont conservés par la normalisation : `type.keywords` contient les mots-clés de la catégorie (des objets, voir plus bas) ; `convo.keywords` contient les identifiants des mots-clés choisis et `convo.artifacts` le dernier relevé des fichiers touchés.
- `settings.json` — `{ "topCount": 3, "showBands": true, "compact": false, "defaultCwd": "", "repoDir": "", "terminal": "powershell", "provider": "claude", "claudeModel": "", "copilotModel": "", "claudeEffort": "", "copilotEffort": "", "draftProvider": "claude", "draftModel": "haiku", "draftEffort": "", "bitbucketUrl": "", "window": { "x", "y", "width", "height", "maximized" } }`. `provider`, `claudeModel` / `copilotModel` et `claudeEffort` / `copilotEffort` sont l'agent, le modèle et l'effort par défaut, réglés dans le dialogue Réglages : ils présélectionnent le formulaire de nouvelle conversation. Vide = réglage propre de l'outil (rien n'est passé sur la ligne de commande). `draftProvider` / `draftModel` / `draftEffort` sont ceux de la **rédaction assistée**, réglés à part : le modèle vaut pour l'agent choisi et repart à `haiku` (Claude) ou vide (Copilot) quand on en change. `repoDir` est le dossier des sources d'Organizator proposé pour envoyer les remarques ; vide = `env.repoDir` (détecté). `bitbucketUrl` est le serveur interrogé par « Mes PRs Bitbucket » ; vide = celui que l'hôte détecte (voir « PRs Bitbucket »).
- `copilot-models.json` — cache du catalogue Copilot : `{ "fetchedAt": ms, "models": [{ "id", "name", "usage", "price", "enabled" }] }`, rafraîchi par la sonde ACP (voir « Sessions GitHub Copilot CLI »).
- `claude-models.json` — cache du catalogue Claude : `{ "fetchedAt": ms, "models": [{ "id", "name", "createdAt" }] }`, lu sur `GET /v1/models` de l'API Anthropic (voir « Sessions Claude Code »).
- `probe\` — dossier de travail de la sonde ACP (vide).
- `launch\<sessionId>.ps1` — scripts de lancement générés (peuvent être supprimés à tout moment)
- `www\` — copie extraite des ressources web embarquées (réécrite à chaque démarrage)

Écriture atomique : écrire dans `data.json.tmp`, puis `File.Move(tmp, data.json, overwrite: true)`. Conserver `data.json.bak` (copie de la version précédente) avant chaque remplacement. À la lecture, si `data.json` est corrompu, tenter `data.json.bak`.

## Modèles de données (JSON, camelCase)

```
task:    { id: string, type: string, text: string, done: bool, doing: bool, created: number(ms epoch),
           parent?: string (identifiant de la tâche parente : la tâche est une sous-tâche — un seul niveau),
           jira?: string (clé du ticket), prs?: string[] (adresses des PRs) — tâches créées par « Mes PRs Bitbucket » }
type:    { id: string, label: string, bg: string, fg: string, bd: string, custom: true,
           keywords: keyword[] }
keyword: { id: string("w…"), name: string(80), desc: string(160), prompt: string(4000),
           team: bool (le mot-clé fait lancer une équipe), agents: agent[] (8 au plus) }
agent:   { id: string("a…"), name: string(60), role: string(32), prompt: string(2000),
           model: string(40) ("" = celui de l'agent principal), effort: string(16) ("" = idem) }
convo:   { id: string(uuid v4 minuscule = sessionId de l'outil), taskId: string, title: string,
           provider: "claude" | "copilot", model: string ("" = modèle par défaut de l'outil),
           effort: string ("" = réglage propre de l'outil),
           cwd: string, created: number, updated: number, messageCount: number,
           keywords: string[] (identifiants de mots-clés),
           artifacts: [{ path: string, action: "written"|"created"|"modified"|"deleted", tool: string,
                         agent: string (nom du sous-agent qui l'a écrit, "" pour la session) }] }
remark: { id: string, text: string, created: number, sentAt: number (0 = en attente), sessionId: string (session qui l'a reçue) }
```

L'ordre du tableau `tasks` **est** la priorité, et c'est aussi l'ordre affiché : rien n'est trié au rendu. Une tâche terminée (`done`) reste donc là où elle était — elle prend `✓` à la place de son numéro, n'occupe aucun rang et n'ouvre aucune bande de priorité (celles-ci sont posées par les tâches actives) ; son bouton ↓ (`move-bottom`) la range en fin de tableau quand on le décide. `move-bottom` et `remove-task` ne sont rendus que sur une tâche cochée : une tâche encore en file ne se supprime pas, il faut d'abord la terminer. `removeTask` le vérifie aussi de son côté (une carte rendue avant le décochage ne doit pas pouvoir effacer la tâche). `convos` ne contient plus de messages : la conversation vit dans l'outil ; l'hôte lit le fichier de session pour fournir titre, nombre de messages, date et transcription en lecture seule. Une `convo` sans `provider` (données antérieures) est une session Claude. Les conversations du carnet de remarques portent `taskId: "__feedback__"`, l'identifiant d'une tâche virtuelle que l'UI ne liste jamais.

**Sous-tâches.** `task.parent` désigne la tâche parente, sur un seul niveau : une sous-tâche n'en a pas, et `regroupTasks` (appelé par `normalize` et par `commit`) détache toute tâche dont le parent manque ou est lui-même une sous-tâche. Il remet aussi chaque sous-tâche derrière son parent, dans l'ordre relatif où elles sont, si bien que le tableau `tasks` reste plat et que son ordre reste la priorité, sous-tâches comprises. `visibleTasks` filtre par groupe : la recherche montre tout le groupe dès qu'un de ses membres répond, et une sous-tâche n'apparaît jamais sans son parent. Au rendu (`renderList`), seules les tâches de premier niveau prennent un rang, comptent pour `topCount` et ouvrent les bandes ; une sous-tâche se numérote sous son parent (`3.1`, `3.2`, ✓ si terminée), sa carte porte `is-sub` (retrait, filet) et celle du parent une pastille `sub-chip` (terminées / total, `subtaskProgress`). Le bouton ↳+ (`add-sub`, sur les tâches de premier niveau seulement) et le trou au-dessus d'une sous-tâche (`data-gap-parent`) ouvrent le dialogue en mode sous-tâche (`ui.composerParent`, catégorie du parent proposée, pas d'import de PRs) ; `addFromComposer` pose la nouvelle tâche dans le groupe — après la tâche visée si elle en fait partie, sinon en dernier. Glisser-déposer (`dropNow`) : un parent emmène ses sous-tâches et reste de premier niveau, posé avant ou après le groupe visé ; une tâche seule lâchée avant ou après une sous-tâche en devient une (même parent), lâchée juste sous la carte d'un parent qui en a devient sa première sous-tâche, lâchée avant une tâche de premier niveau, après un groupe entier ou sur le trou du bas (`ui.overTail`) elle est de premier niveau. `move-bottom` descend un parent avec son groupe, une sous-tâche en bas de sa fratrie ; `remove-task` sur un parent (terminé, comme toute tâche qu'on supprime) détache ses sous-tâches, qui restent dans la file à leur place.

Un mot-clé sans `team` ni `agents` (tout ce qui précède les équipes) se relit tel quel : équipe absente, case décochée. Un agent sans `model` ni `effort` se lit « comme l'agent principal », ce qui est aussi le défaut d'un agent neuf. Décocher la case n'efface pas les agents — ils restent en sommeil, prêts à resservir —, et un agent sans nom est une ligne en cours de saisie : elle se garde, mais ne part pas dans le contexte.

Données antérieures aux mots-clés-objets : un `type.keywords` de chaînes devient une liste d'objets (nom repris, `desc` et `prompt` vides, identifiant attribué), et le `convo.keyword` d'une conversation — un seul mot, sous son nom — devient un `convo.keywords` d'un élément. La conversion se fait à la lecture (`normalize`, côté JS) : `keywordIdsFor` accepte indifféremment un identifiant ou un nom, et ne garde que les mots-clés que la catégorie de la tâche porte encore.

`AgentArtifacts` lit les événements JSONL sans suivre les chemins simplement cités dans le texte : il retient les chemins explicites fournis aux outils d'écriture ou dans un patch (`Write`, `Edit`, `Delete`, etc.), normalise les chemins relatifs au `cwd` (formes Git Bash `/d/…` et `~/` comprises) et déduplique par fichier. Le relevé est **incrémental** : pour chaque transcript, l'hôte garde l'octet atteint (`JsonlTail`) et les fichiers trouvés jusque-là, si bien qu'une écriture n'est payée que pour les lignes qu'elle ajoute. Une session d'équipe cumule des dizaines de Mo de transcripts : les reparser en entier à chaque ligne d'un coéquipier coûtait ~160 ms par passage et par session, contre ~20 ms désormais. Un transcript réécrit ou raccourci est relu du début, un transcript de sous-agent disparu emporte ses fichiers. Trois sources, appliquées dans l'ordre des horodatages pour que le dernier passage sur un fichier dise son action et son auteur :

- le transcript principal, sidechains comprises ;
- les transcripts des **sous-agents** (`ClaudeSessions.GetSubagentsDir` : `<cwd encodé>\<sessionId>\subagents\*.jsonl`, nom lu dans le `.meta.json` voisin, porté par `agent`) — sans eux, un rapport écrit par un coéquipier n'apparaissait nulle part. L'empreinte du cache couvre donc le fichier de session **et** ces transcripts (nombre, taille cumulée, date la plus récente) : un coéquipier qui écrit ne touche pas au fichier de la session ;
- les **commandes shell** (`ShellWrites`, outils `Bash`, `PowerShell`, `powershell`, et tout nom contenant `shell` ou `terminal`, commande lue dans `command` / `cmd` / `script`, même encodée en JSON dans `arguments`) : redirections `>` / `>>` (hors `2>`, `&>`, `>&1`, `/dev/null`, `$null`), `tee`, `cp` / `mv` / `copy` / `Copy-Item` / `Move-Item` (destination), `Out-File` / `Set-Content` / `Add-Content` / `New-Item` (sauf `-ItemType Directory`) / `Export-Csv` (`-Path`, `-FilePath`, `-LiteralPath` ou premier positionnel), et les écritures des scripts en ligne (`open(…, 'w')`, `writeFileSync(`, `File.WriteAllText(`, `Path(…).write_text(`). La commande est découpée par ligne puis sur `&&`, `||`, `;`, `|` ; un `cd` / `Set-Location` / `pushd` déplace la base des chemins relatifs des segments suivants ; les corps de here-documents (`<<'EOF'`) et de here-strings (`@'…'@`) sont sautés pour les redirections. Un chemin n'est retenu que **littéral** : sans `*`, `?`, `$`, `%`, accolades ni backtick, avec une extension d'au plus 8 caractères — une variable ou un joker vaut mieux qu'un faux fichier. L'action est `written` (`modified` pour `>>`, `Add-Content`, `tee -a`).

Le résultat est trié : chemins relatifs (sous le `cwd`) d'abord, puis les autres, chacun par ordre alphabétique.

L'hôte ne trie pas ces fichiers : c'est l'UI qui sépare les **rapports** du reste, par extension (`REPORT_EXT` dans `app.js` : md, txt, rst, pdf, csv, tableurs, documents, html, images). Un rapport est un livrable qui se lit tel quel ; le reste est le code touché en chemin. L'icône de fichiers de la carte n'est rendue que si la tâche a produit au moins un rapport, et son badge les compte. Le panneau liste les rapports, puis les autres fichiers derrière un repli « N fichiers modifiés » (`ui.artifactFilesOpen`). Un clic sur un fichier l'ouvre dans le **lecteur** (section suivante).

## Lecteur d'artefacts

Un rapport se lit **dans la fenêtre** : cliquer un fichier du panneau des artefacts ouvre un lecteur par-dessus la file et le panneau (`ui.reader`, conteneur `#reader`, rendu par `renderReader`), sans passer par un éditeur. Ses boutons gardent les autres chemins sous la main : « VS Code » (`openPath` avec `editor: "vscode"`), « Dossier » (l'Explorateur). Rien n'est persisté.

- **L'hôte rend, l'UI affiche** (`ArtifactReader`, message `readArtifact`). Le genre est déduit de l'extension, puis d'un sondage (un octet nul dans les 8 premiers Ko = binaire) : `markdown` (HTML rendu par Markdig — tableaux, listes de cases, notes de bas de page, identifiants de titres à la GitHub, liens automatiques, listes de définitions… ; le titre est le premier `#`), `table` (CSV / TSV : séparateur détecté sur la première ligne parmi `;` `,` tabulation `|`, lecture RFC 4180, 5 000 lignes au plus), `text` (bloc préformaté, échappé), `html`, `pdf`, `image` (servis tels quels, voir l'hôte virtuel), `binary` (tableur, document Office, archive… : l'UI referme le lecteur et ouvre le fichier avec l'application associée, `openPath` avec `editor: "default"`), `large` (plus de 3 Mo de texte : renvoi vers VS Code), `missing`. Le fichier est lu en partage (`FileShare.ReadWrite`) : l'agent peut être en train d'y écrire.
- **Hôte virtuel des rapports** : `https://report.organizator/` (`ArtifactReader.Host`) est mappé par `SetVirtualHostNameToFolderMapping` (`DenyCors` : images, cadres et PDF se chargent, aucun script ne peut lire ces fichiers par `fetch`) sur la **racine** du rapport courant — le dossier de travail de la session quand le fichier est dessous, pour que les liens relatifs entre rapports et vers les images tiennent, sinon le dossier du fichier seul. Un seul dossier servi à la fois ; il change avec le rapport ouvert (`BridgeHost.ServeReportRoot`, sur le fil de l'interface). Les liens relatifs du Markdown sont réécrits en URL absolues sous cet hôte (`HtmlRenderer.LinkRewriter`) ; `javascript:`, `vbscript:`, `file:`, `//hôte` et les chemins Windows absolus (`C:\…`, pris pour un schéma d'une lettre) deviennent `#`.
- **Cadre isolé** : le HTML rendu (Markdown, texte, tableau, et une image seule — `<figure class="image">`, car sous `DenyCors` la page de l'application ne peut pas charger elle-même une ressource de l'hôte des rapports, alors que le cadre, d'origine opaque, le peut) est posé dans un `<iframe sandbox="allow-scripts" srcdoc>` : origine opaque, et une CSP (`readerFrameDoc`) qui n'autorise que `fonts.css` et `reader.css` de l'application, les images de l'hôte des rapports (et `data:`), les styles en ligne (alignement des colonnes), et le seul script d'amorçage porteur d'un nonce (`READER_SCRIPT`). Le Markdown brut peut contenir du HTML — Markdig le laisse passer — sans que rien ne s'exécute ni n'atteigne l'application. Ce script reçoit le HTML par `postMessage` (`{ type: "html", html, follow }`), signale `ready`, remonte les clics sur les liens (`link`) et Échap (`close`). Un lien vers `https://report.organizator/…` ouvre l'autre fichier dans le lecteur (`followReaderLink`, bouton ‹ pour revenir : `reader.back` chaîne les lecteurs) ; `http(s):` et `mailto:` partent dans le navigateur par `openUrl` ; une ancre `#…` défile dans le cadre. Une page HTML est chargée dans un cadre `sandbox="allow-scripts"` depuis l'hôte virtuel (ses scripts tournent, sans même origine ni accès à l'application), un PDF dans un cadre sans sandbox (le lecteur PDF intégré n'y fonctionne pas). `MainWindow.OnFrameNavigationStarting` refuse aux cadres toute navigation `http(s)` hors des deux hôtes virtuels et l'ouvre dans le navigateur.
- **En direct** : tant que le lecteur est ouvert, l'UI renvoie `readArtifact` toutes les 2 s (`syncReaderPolling`, fenêtre visible) avec le `stamp` connu (taille + date, `TranscriptAccumulator.FileStamp`) ; l'hôte répond `{ changed: false }` sans relire si rien n'a bougé. Sinon le nouveau HTML est poussé dans le cadre, qui garde son défilement — ou suit la fin s'il y était : un rapport qui s'écrit se lit au fil de l'eau. `sessionsChanged` et `focus` déclenchent aussi une relecture. Le cadre n'est reconstruit que si le fichier ou son genre change (`readerKey`) : un rendu de l'application ne le touche pas, et la barre (dossier, heure, taille) est mise à jour en place.
- Le fond ne porte pas d'action ; ✕ ou Échap referment (depuis le cadre, Échap arrive par message ; les dialogues, au-dessus du lecteur, ont la priorité sur Échap).

## Sessions Claude Code

- Lancement d'une nouvelle session : `claude --dangerously-skip-permissions --session-id <uuid> --name "<titre>" [--model <modèle>] [--effort <niveau>] --append-system-prompt <contexte> [<premier message>]` dans le dossier `cwd`. Le premier message est l'argument positionnel : claude ouvre la session et le traite aussitôt, au lieu d'afficher une invite vide.
- Reprise : `claude --dangerously-skip-permissions --resume <uuid> [--model <modèle>] [--effort <niveau>] --append-system-prompt <contexte>` dans le **même** `cwd` (Claude range les sessions par dossier de travail).
- `--model` accepte un alias (`fable`, `opus`, `sonnet`, `haiku`) ou un identifiant complet (`claude-opus-5`). `--effort` : `low`, `medium`, `high`, `xhigh`, `max`.
- La CLI n'expose aucun listing de modèles, mais l'API Anthropic en a un : `GET https://api.anthropic.com/v1/models` répond au jeton OAuth de Claude Code (`~/.claude/.credentials.json`, en-tête `anthropic-beta: oauth-2025-04-20`, le même appel d'identité que « Quotas »), avec `id`, `display_name` et `created_at`, du plus récent au plus ancien. `ClaudeModelCatalog` la garde dans le cache `claude-models.json`, rafraîchi quand il a plus de 24 h (au démarrage, en silence) ou à la demande (bouton ↻, message `refreshModels`), et compose la liste : les alias (`alias`), les modèles de l'API (`anthropic`, nom affiché, identifiant passé à `--model`), puis les identifiants déjà utilisés sur le poste que l'API ne cite pas (`used` : `~/.claude/stats-cache.json` → `modelUsage`, `~/.claude.json` → `projects.*.lastModelUsage`, typiquement les variantes `[1m]`). Sans cache — pas de jeton, jeton périmé, pas de réseau — : alias et déjà utilisés seulement, `fetchedAt` = 0, et l'erreur est rendue en clair au clic sur ↻. Les valeurs par défaut de `~/.claude/settings.json` (`model`, `effortLevel`) sont affichées dans l'option « Par défaut de l'outil ».
- Fichiers de session : `%USERPROFILE%\.claude\projects\<cwd encodé>\<uuid>.jsonl`. Encodage du cwd : chaque caractère qui n'est pas `[A-Za-z0-9]` est remplacé par `-`, casse conservée. Exemples : `D:\02-side\Organizator` → `D--02-side-Organizator`, `C:\Users\dagan.remeur\Impot` → `C--Users-dagan-remeur-Impot`.
- Format JSONL (une entrée JSON par ligne). Entrées utiles :
  - `{"type":"user","message":{"role":"user","content":"texte" | [{"type":"text","text":"..."} | {"type":"tool_result",...}]},"timestamp":"ISO","uuid":"..."}`
  - `{"type":"assistant","message":{"role":"assistant","content":[{"type":"text","text":"..."} | {"type":"tool_use","name":"Read",...}]},"timestamp":"ISO"}`
  - `{"type":"ai-title","aiTitle":"..."}` et éventuellement `{"type":"custom-title","customTitle":"..."}` — titre de la session.
  - Autres types (`mode`, `permission-mode`, `attachment`, `file-history-snapshot`, `last-prompt`, `summary`, `progress`, `system`…) à ignorer.
  - Ignorer les entrées `isSidechain: true` et les messages `user` dont le contenu n'est que des `tool_result`, ou dont le texte commence par `<` (commandes locales type `<command-name>`, `<local-command-stdout>`).
- Compte de messages = nombre d'entrées `user` (texte réel) + `assistant` (au moins un bloc `text` non vide).
- Titre = `customTitle` si présent, sinon `aiTitle`, sinon première ligne du premier message utilisateur (46 caractères), sinon « Nouvelle session ».
- État (voir « État des sessions ») : chaque ligne `assistant` porte le `stop_reason` **final** de son message API — `tool_use` tant que l'agent enchaîne des outils, `end_turn` (ou `stop_sequence`, `max_tokens`) quand la réponse est complète. Une entrée `user` texte relance le traitement, un `tool_result` le poursuit, `[Request interrupted…]` l'interrompt ; `isApiErrorMessage` et `isAbortedMidStream` terminent le tour ; `isCompactSummary` n'est pas un tour. Un `tool_use` nommé `AskUserQuestion` met la session en attente de l'utilisateur.

## Sessions GitHub Copilot CLI

- Lancement : `copilot --allow-all --session-id=<uuid> --name "<titre>" [--model <modèle>] [--effort <niveau>] -i <contexte>` dans le dossier `cwd`. Copilot n'a pas d'équivalent de `--append-system-prompt` : le contexte de la tâche est envoyé comme **premier message** de la session.
- Reprise : `copilot --allow-all --resume=<uuid> [--model <modèle>] [--effort <niveau>]` dans le même `cwd`. Le contexte n'est pas renvoyé, il est déjà dans l'historique. `--effort` : `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
- Fichiers de session : `%USERPROFILE%\.copilot\session-state\<uuid>\` (pas de classement par dossier de travail). `workspace.yaml` porte `name:` (titre donné par Copilot, ou par l'utilisateur quand `user_named: true`) et `cwd:` ; `events.jsonl` contient un événement JSON par ligne.
  - `{"type":"user.message","data":{"content":"…"},"timestamp":"ISO"}` — message de l'utilisateur.
  - `{"type":"assistant.message","data":{"content":"…","toolRequests":[{"name":"powershell",…}]},"timestamp":"ISO"}` — réponse de l'agent ; chaque entrée de `toolRequests` donne une ligne `[outil : nom]`.
  - Les événements qui portent un `agentId` à la racine viennent des sous-agents : ignorés (équivalent de `isSidechain`). Les autres types ne servent qu'à l'état de la session : `assistant.turn_start` / `assistant.turn_end`, `tool.execution_start` / `tool.execution_complete`, `permission.requested` / `permission.completed`, `abort`, `session.error`, `session.start` / `session.resume` / `session.shutdown`. Copilot écrit un `assistant.turn_end` après **chaque** appel du modèle, outils compris : la réponse n'est complète que si aucun `assistant.message` du tour ne portait de `toolRequests`.
- Compte de messages = `user.message` non vides + `assistant.message` dont `content` est non vide.
- Titre = `name` de `workspace.yaml`, sinon première ligne du premier message utilisateur (46 caractères), sinon « Nouvelle session ».
- Détection de la CLI : `copilot.exe` / `copilot.cmd` dans le PATH (en ignorant le « bootstrapper » que l'extension VS Code dépose dans `globalStorage\github.copilot-chat`, qui ne fait que chercher la vraie CLI), sinon `%LOCALAPPDATA%\GitHub CLI\copilot\copilot.exe` (téléchargée par `gh copilot`), sinon `gh copilot --` si `gh.exe` est dans le PATH. Le chemin complet est toujours écrit dans le script.
- Catalogue des modèles (`CopilotModelCatalog`) : la CLI ne l'expose que par son mode **ACP** (Agent Client Protocol, JSON-RPC sur stdio). La sonde lance `copilot --acp --no-auto-update` avec `probe\` comme dossier de travail, envoie `initialize` puis `session/new`, et lit `result.models.availableModels[]` : `modelId`, `name`, `_meta.copilotUsage` (multiplicateur, ex. `1x`), `_meta.copilotPriceCategory` (`low` / `medium` / `high`), `_meta.copilotEnablement`. Elle envoie ensuite `session/close` et ferme l'entrée standard. La CLI ne purge jamais la session vide ainsi créée : la sonde supprime son dossier `session-state\<uuid>` (seulement s'il n'a pas d'`events.jsonl`) et sa ligne `sessions` dans `session-store.db` (Microsoft.Data.Sqlite), pour qu'elle n'apparaisse pas dans `copilot --resume`. Résultat mis en cache dans `copilot-models.json` ; rafraîchi quand il a plus de 24 h (au démarrage, en silence) ou à la demande (bouton ↻, message `refreshModels`). Sans cache, la liste se limite à `auto` et aux identifiants déjà vus dans `~/.copilot` (`settings.json` → `model`, `config.json` → `recentModelIds`, `session.start` → `selectedModel`). Les valeurs par défaut de `~/.copilot/settings.json` (`model`, `effortLevel`) sont affichées dans l'option « Par défaut de l'outil ».
- Le champ libre accepte tout identifiant `[A-Za-z0-9._:/[]-]` (64 caractères max) ; le reste est refusé avant d'être écrit dans un script.

## État des sessions

Chaque conversation affiche ce que fait l'agent. L'état vient de deux sources :

- **Le transcript** (`TranscriptAccumulator.State`, calculé par les deux lecteurs pendant la lecture normale) : `working` (prompt en traitement, outil en cours), `waiting` (question posée via `AskUserQuestion`, autorisation demandée par Copilot), `ready` (réponse complète), `error` (erreur d'API, authentification), `idle` (pas encore de prompt, tour interrompu, session refermée). `stateTs` est l'horodatage d'**entrée** dans l'état : « en cours depuis » le prompt, « réponse prête à » l'heure du `end_turn`. `detail` précise l'outil en cours, le motif (`interrompue`, `fermee`, `question posee`, `autorisation demandee`) ou le message d'erreur (première ligne, 80 caractères).
- **Les processus** (`AgentProcessScanner`) : toutes les 4 s, une requête WMI `Win32_Process` (`System.Management`) liste `claude.exe`, `copilot.exe`, `node.exe` et `bun.exe` et extrait les `--session-id` / `--resume` de leur ligne de commande (environ 300 ms, sur un thread du pool). `alive` vaut `true`/`false`, ou `null` tant que WMI n'a pas répondu ou s'il est indisponible (abandon après 3 échecs, journalisé). Un changement de l'ensemble déclenche `sessionsChanged`.

- **Les agents lancés par la session** (`TranscriptAccumulator.Agents`, alimenté par `ClaudeSessions`) : un agent part par l'outil `Agent` (ou `Task`, `Workflow`) et son résultat revient aussitôt — « Spawned successfully … name: `<nom>` » pour un coéquipier, « launched in background. Task ID: `<id>` » pour une tâche de fond — si bien que la session principale peut atteindre `end_turn` avec toute son équipe au travail. Le retour se lit plus loin dans le même fichier : `<task-notification>` porte le `<task-id>` de la tâche finie, et `idle_notification` le `teammate_id` du coéquipier redevenu disponible. Un `Agent` qui a travaillé sur place (pas de `Task ID`, pas de `Spawned`) est revenu avec son `tool_result`.
- **Les transcripts des sous-agents** (`ClaudeSessions.ScanSubagents`) : Claude Code écrit celui de chaque sous-agent dans `<cwd encodé>\<sessionId>\subagents\agent-…jsonl`, avec un `.meta.json` qui donne son `name`. Un agent au travail y ajoute une ligne à chaque outil et à chaque réponse ; un agent parti sans jamais annoncer son retour (fenêtre fermée, coéquipier arrêté) n'y touche plus. `BridgeHost` croise les deux sources : passé trois minutes de grâce après son départ, un agent n'est encore compté que si son transcript a bougé depuis moins d'un quart d'heure — et un dossier `subagents` absent (autre version de la CLI) laisse le transcript principal seul juge. Reprendre une session dont la fenêtre était fermée efface son équipe d'avant (`_relaunchedAt`) : elle est partie avec la fenêtre.

**La dernière parole de l'agent** (`TranscriptAccumulator.Said`, champ `said`) accompagne cet état : le texte de sa dernière réponse, ramené à une ligne de 160 caractères, sans les lignes `[outil : …]` ni les marques de markdown (titres, puces, gras, code). Quand il pose une question (`AskUserQuestion`), c'est **la question** qui remplace cette parole — `ClaudeSessions.LastQuestion` lit l'`input` de l'outil et joint ses questions par un point médian —, puisque c'est elle qui attend une réponse. Côté Copilot, seul le texte des réponses est retenu : ses demandes d'autorisation ont déjà leur `detail`. La parole est accumulée que la transcription soit collectée ou non, et survit donc à la lecture incrémentale des résumés. L'UI la pose sous l'état, dans la liste des conversations (`.convo-said`, deux lignes au plus, teinte de l'état) et en seconde ligne de l'infobulle de l'icône du terminal.

L'UI en déduit l'état affiché : `alive === false` → « Fermée » quel que soit le transcript ; fichier absent mais processus vivant → « Ouverte » ; un transcript `ready` ou `idle` avec des agents encore au travail → « En cours » (et l'état ne passe au vert, avec toast, que lorsque l'équipe est rentrée) ; sinon l'état du transcript. Sur une carte de tâche, l'état le plus pressant de ses conversations (`waiting` > `working` > `error` > `ready` : une question posée passe devant le travail en cours, puisque c'est elle qui réclame une réponse) est porté par le **bouton terminal** lui-même : classe `is-<état>` sur le bouton (teinte et bordure) et `.btn-dot.st-<état>` posée dans son coin, l'infobulle reprenant `stateText` de la conversation concernée. En `waiting`, la pastille porte un « ? » bleu cerclé d'une onde (`halo-ask`) et la carte reçoit `is-asking`, qui la borde de bleu : cette classe regarde **toutes** les conversations de la tâche, pas seulement la plus pressante, une session pouvant travailler pendant qu'une autre attend. Ce bouton porte aussi, en haut à droite (`.term-count`), le nombre d'agents qui travaillent pour la tâche : par conversation, l'agent du terminal s'il traite un prompt (`state === 'working'`), plus les agents qu'il a lancés et qui ne sont pas revenus ; le badge disparaît à zéro, et une conversation fermée ne compte pour rien. Une seconde icône, représentant un fichier et portant le nombre de rapports, n'est rendue que si au moins un rapport a été produit ; elle ouvre la liste des artefacts sans remplacer l'accès au terminal. Quand une conversation passe de `working`/`waiting` à `ready`, l'UI affiche un toast et envoie `notify` : l'hôte fait clignoter le bouton de la barre des tâches (`FlashWindowEx`) si la fenêtre n'est pas au premier plan.

### Fraîcheur de l'affichage

Trois mécanismes bornent le délai entre « l'agent a répondu » et « la carte le montre » :

- **Lecture incrémentale** (`SessionScan`) : un fichier de session atteint plusieurs mégaoctets et grossit à chaque outil ; le relire en entier à chaque écriture coûtait ~30 ms par rafraîchissement et par session. Chaque lecteur garde, par session, l'octet où il s'est arrêté et l'accumulateur correspondant : seules les lignes ajoutées sont relues (une ligne encore sans `\n` est laissée au passage suivant). Un fichier plus court, ou modifié sans avoir grandi, fait repartir la lecture du début — comme un fichier supprimé puis recréé. Un scan par session pour les résumés, un seul pour la transcription (l'UI n'en affiche qu'une).
- **Notification** (`SessionsWatcher`) : les événements du `FileSystemWatcher` sont regroupés sur 250 ms, mais jamais repoussés au-delà d'**1 s** — un agent qui écrit sans arrêt retardait sinon la notification indéfiniment. Tampon de 256 Ko ; si la surveillance tombe (débordement) ou si le dossier n'existe pas encore (Copilot avant la première session), une reprise est tentée toutes les 15 s et `sessionsChanged` est levé dès qu'elle aboutit, des événements ayant été manqués.
- **Relecture périodique** (UI) : filet de sécurité si une notification manque malgré tout. `refreshSessions` toutes les 1,5 s tant qu'une conversation est `working`/`waiting`/`open`, 10 s sinon, 30 s fenêtre cachée ; relance immédiate au retour au premier plan. Le rendu n'est refait que si un état a changé, pour ne pas interrompre une sélection ou une saisie. La transcription ouverte est relue toutes les 2 s.

`getSessions` porte sur **toutes** les conversations à chaque `sessionsChanged`, `focus`, relecture périodique et au démarrage. L'hôte garde en cache le résumé de chaque transcript avec une empreinte taille + date (`GetStamp`) et ne redemande une lecture que pour les fichiers qui ont changé. Tout ce qui touche au disque — résumés, fichiers produits, transcripts des sous-agents (`ActiveAgents`) — se fait hors du fil de l'interface, qui est aussi celui par lequel passent les touches non imprimables de la WebView.

**Une relecture à la fois.** Trois règles, posées après qu'Organizator a saturé deux cœurs et demi au bout de quelques heures (septembre 2026) :

- `refreshSessions` ne lance jamais un `getSessions` par-dessus un autre : une demande reçue en cours de route (`sessionsChanged`, `focus`, minuteur) est retenue et servie par **une** relecture à la fin (`sessionsInFlight`, `sessionsAgain`). Délai de réponse : 60 s (`SESSIONS_TIMEOUT`), le premier relevé lisant tous les transcripts — une vingtaine de secondes disque froid.
- La boucle périodique n'a qu'**un** minuteur, toujours désarmé avant d'être réarmé (`armSessionsPoll`). L'ancienne boucle réarmait le sien à la fin de chaque relecture sans voir celui qu'un événement de l'hôte avait armé entre-temps : deux boucles tournaient côte à côte, puis trois, et au bout de quelques heures des dizaines de relectures par seconde (chacune suivie d'une sauvegarde complète et d'un rendu complet) saturaient l'hôte et la page. La relecture silencieuse du journal (`loadTranscript(true)`) ne part pas non plus par-dessus une autre (`transcriptInFlight`).
- La liste des fichiers produits ne repart que si elle a changé : l'UI renvoie pour chaque session l'empreinte reçue la fois précédente (`artifactsStamp`, en mémoire seulement), l'hôte omet `artifacts` quand elle n'a pas bougé. Elle pesait l'essentiel de la réponse (plus d'un millier de fichiers pour une soixantaine de sessions).

Ce que la relecture recopie dans `data.json` (titre, nombre de messages, date, fichiers) change à chaque ligne écrite par un agent : `saveDataLater` l'enregistre au plus toutes les 5 s, au lieu de réécrire tout `data.json` à chaque relecture ; une sauvegarde ordinaire ou la fermeture (`organizatorFlush`) l'emporte avec elle.

**La frappe d'abord.** Les rendus provoqués par une relecture (`renderActivity` : sessions, journal silencieux) ne redessinent que ce qui montre l'état des sessions — la file, le panneau, le bouton Remarques —, jamais les dialogues, qui n'en affichent rien. Ils attendent une pause de frappe : tant que le focus est dans un champ et qu'une touche a été frappée il y a moins de 1,2 s (`TYPING_QUIET_MS`), ou qu'une composition est en cours (touche morte `^`, `¨`, IME), le rendu est remis de 0,6 s en 0,6 s. Sans quoi le champ en cours de saisie était reconstruit toutes les secondes : frappe retardée, touche morte avalée, historique d'annulation perdu.

### Performances

« L'application rame, la frappe traîne » doit laisser une trace, avec sa cause probable. `PerfMonitor` (hôte) écrit dans `host.log`, sous l'étiquette `[PERF]` :

- **Le fil de l'interface.** Une sonde lui confie un travail vide toutes les 500 ms (`Dispatcher.BeginInvoke`, priorité `Send`) et mesure le délai avant qu'il le prenne. Au-delà de 250 ms, il était occupé : la fenêtre ne répondait plus, et les touches non imprimables (retour arrière, flèches, Entrée), que WebView2 soumet à l'hôte avant de les laisser à la page, attendaient avec lui. Un blocage de plus d'une seconde est noté sur le moment, avec le dernier message reçu du pont (une ligne par 30 s au plus).
- **Les messages du pont** : nombre, durée moyenne et maximale par type, de la réception à la réponse (`RecordMessage`).
- **L'interface web** : `app.js` observe les tâches longues de son fil (`PerformanceObserver` `longtask`, plus de 50 ms d'affilée), les saisies lentes (`event`, plus de 104 ms entre la touche ou le clic et l'affichage) et la durée de ses rendus, et les envoie chaque minute (message `perf`, et à `organizatorFlush`). Une tâche longue ou une saisie de plus d'une demi-seconde est notée aussitôt (`log`, niveau `perf` : ligne `[JS/PERF]`, une par 30 s au plus).
- **Le processus** : CPU en % d'un cœur, mémoire, threads.

Toutes les 10 minutes, une ligne de bilan : `[PERF] Bilan (10 min) : CPU 3 % d'un coeur, 190 Mo, 41 threads | fil UI : fluide | pont : getSessions 480 x (moy 18 ms, max 90 ms), … | UI web : 0 tache(s) longue(s), 0 saisie(s) lente(s), 310 rendu(s) (moy 9 ms, max 40 ms)`, et une dernière à la fermeture. Elle passe en `[PERF/WARN]` quand quelque chose cloche : blocage du fil de plus d'une seconde, CPU au-delà d'un demi-cœur, saisie ou tâche longue de plus d'une demi-seconde, ou plus de 2,5 `getSessions` par seconde (`emballement` : c'est le défaut décrit sous « Une relecture à la fois », qui en faisait jusqu'à trente). Pour les retrouver : `Select-String '\[PERF' $env:LOCALAPPDATA\Organizator\host.log`.

Côté page, deux règles de rendu tiennent aussi à la fluidité : les animations en boucle n'animent que `transform` et `opacity`, que le compositeur joue sans repeindre la page — l'onde des pastilles « réponse prête » et « question » est un disque posé derrière la pastille (`.btn-dot::before`, `z-index: -1`, d'où `isolation: isolate` sur `.icon-btn`). Animer `box-shadow` repeignait la page à chaque image pour chaque carte concernée : 17 % du fil principal au repos avec vingt cartes prêtes, contre moins de 1 % désormais.

## Quotas des agents

Deux cartes en tête de fenêtre montrent la part consommée des limites de chaque agent (`UsageMonitor`, message `getUsage`) :

- **Claude** (`ClaudeUsageReader`) : `GET https://api.anthropic.com/api/oauth/usage` avec le jeton OAuth de `~/.claude/.credentials.json` (`claudeAiOauth.accessToken`, en-tête `anthropic-beta: oauth-2025-04-20`), l'appel que Claude Code fait pour `/usage`. Le tableau `limits` donne `session` (5 h), `weekly_all` et `weekly_scoped` (par modèle, `scope.model.display_name`) en `percent` avec `resets_at` ; les champs historiques `five_hour` / `seven_day` / `seven_day_opus` / `seven_day_sonnet` servent de repli, et `extra_usage` ajoute une jauge s'il est activé. Le plan vient de `subscriptionType` + `rateLimitTier` (« Max 5× »). Le jeton n'est jamais renouvelé par Organizator : passé `expiresAt`, l'état est `expired` jusqu'à ce que Claude Code le rafraîchisse.
- **Copilot** (`CopilotUsageReader`) : hôte et login du dernier compte connecté dans `~/.copilot/config.json` (JSON avec commentaires, `lastLoggedInUser`), jeton OAuth lu dans le Gestionnaire d'identifiants Windows (`WindowsCredentials`, cible `copilot-cli/<hôte>:<login>`, UTF-8 ou UTF-16), sinon `COPILOT_GITHUB_TOKEN` / `GH_TOKEN` / `GITHUB_TOKEN`. `GET <api>/copilot_internal/user` (`Authorization: token …`) avec `api.github.com`, `api.<sous-domaine>.ghe.com` pour la résidence des données, `<hôte>/api/v3` pour GHES. `quota_snapshots.premium_interactions` donne `entitlement`, `remaining`, `percent_remaining`, `overage_permitted` ; `chat` et `completions` ne donnent une jauge que s'ils ne sont pas `unlimited` ; `quota_reset_date` (jour, minuit local) et `copilot_plan`.

Chaque rapport porte `status` (`ok` ; `missing` : pas de compte connecté ; `expired` : jeton périmé ou refusé ; `error` : réseau), un `message` technique ASCII, `plan`, `account`, `host` et des `bars` (`key` session/weekly/extra/premium/chat/completions, `scope`, `percent` consommé, `used`, `limit`, `overage`, `resetsAt`). L'UI porte les libellés et les messages accentués. L'hôte lit les deux en parallèle (délai 12 s), garde la dernière lecture 2 min sauf `force`, et en cas d'erreur réseau rend les jauges précédentes marquées `stale`. L'UI relit toutes les 5 min fenêtre visible, au `focus`, 2 s après l'arrivée d'une réponse (le quota vient de bouger), et d'un clic sur une carte. Aucun jeton n'est journalisé ni transmis à l'UI.

Les dialogues (nouvelle tâche, réglages) ne se ferment que par leurs boutons ou Échap : le fond (`.dialog-backdrop`) ne porte plus d'action.

Les Réglages sont rangés en onglets (`SETTINGS_TABS` : Affichage, Agents, Rédaction, Dossiers, Bitbucket), un seul affiché à la fois dans un panneau de hauteur fixe qui défile au besoin. L'onglet ouvert vit dans `S.ui.settingsTab` (mémoire de la session, pas `settings.json`) : le dialogue rouvre sur le dernier consulté. Chaque agent a sa carte (modèle + ↻, effort, provenance du catalogue) ; `renderDialogs` garde la position de défilement du panneau d'un rendu à l'autre, sauf changement d'onglet.

## PRs Bitbucket

« Mes PRs Bitbucket » (dialogue Nouvelle tâche, message `getPullRequests`) : `BitbucketPullRequests` interroge le tableau de bord de Bitbucket Data Center, `GET <url>/rest/api/1.0/dashboard/pull-requests?role=REVIEWER&state=OPEN&participantStatus=UNAPPROVED&order=OLDEST` (pages de 50, 10 au plus), avec `Authorization: Bearer <jeton>` : c'est le serveur qui filtre — PRs ouvertes où l'utilisateur du jeton est relecteur et n'a ni approuvé ni demandé des corrections. L'en-tête `X-AUSERNAME` de la réponse donne le compte (`account`), sans appel supplémentaire.

- **Accès** (`Discover`) : l'adresse vient de `settings.bitbucketUrl`, sinon du premier serveur MCP de `~/.claude.json` dont l'`env` porte `BITBUCKET_URL` (racine `mcpServers`, puis `projects.*.mcpServers`), sinon de la variable d'environnement ; le jeton est celui qui accompagne cette adresse (même hôte : `BITBUCKET_TOKEN` du même serveur MCP, ou de l'environnement). `JIRA_URL` (serveur MCP Atlassian, ou environnement) sert au lien du ticket. Rien n'est écrit ni journalisé : `env` ne porte que `bitbucketUrl`, `bitbucketSource`, `bitbucketToken` (présent ou non) et `jiraUrl`, pour le texte d'aide des Réglages (détection sans le réglage de l'utilisateur).
- **Réponse** : `{ status: ok | missing | expired | error, message, host, account, jiraUrl, fetchedAt, prs: [{ id, title, project, projectName, repo, repoName, branch, target, author, url, created, updated, comments, openTasks, draft, key }] }`. `key` est la clé Jira (`[A-Z][A-Z0-9]+-\d+`, non collée à d'autres lettres ou chiffres) lue dans la branche, sinon dans le titre, sinon vide. `missing` = pas d'adresse ou pas de jeton, `expired` = HTTP 401/403, `error` = réseau, délai (20 s), réponse illisible ; `message` est technique, l'UI porte les phrases.
- **Côté UI** (`ui.prImport`, rendu par `prImportHtml` à la place de la zone de texte du dialogue) : `groupPullRequests` fait un groupe par clé, dans l'ordre d'ouverture de la première PR (une PR sans clé fait son propre groupe) ; `prTitle` ôte du titre le préfixe de branche (`Feature/`, `Bugfix/`…) et la clé. `prGroupStatus` cherche une tâche **non terminée** portant `task.jira === key`, sinon l'adresse d'une des PRs (dans `task.prs` ou dans son texte) : `new` (rien en file), `update` (des PRs manquent : elles sont ajoutées au texte par `prAppendText`, après la dernière ligne de PR et avant celle du ticket, et à `task.prs`), `same` (grisé, non cochable). Coché d'office sauf `same` et les groupes tout en brouillons. `createFromPrImport` crée les tâches dans la catégorie du dialogue, à `insertAt`, dans l'ordre des groupes, avec `jira` et `prs` (`prTaskText`), puis ferme le dialogue et le dit en toast. Une tâche terminée ne compte pas : la PR qui revient après de nouveaux commits fait une nouvelle tâche.
- **Pastilles de tickets** (`jiraChipsHtml`, dans la ligne méta de la carte, juste après la catégorie) : `taskJiraKeys` prend `task.jira` puis les clés du texte (`JIRA_KEY_RE`, 2 à 10 caractères avant le tiret, non collées à une lettre, un chiffre, `_` ou `-`), dédoublonnées, sans les sigles de `NOT_JIRA` (`UTF-8`, `ISO-…`, `GPT-5`…), trois au plus. L'adresse vient de `jiraBase` : `env.jiraUrl`, sinon la racine du premier lien `…/browse/<clé>` trouvé dans une tâche ; inconnue, aucune pastille. Chacune est un `<a data-act="open-url">` vers `<jira>/browse/<clé>`, non déplaçable (la carte l'est).
- **Pastilles de PRs** (`prChipsHtml`, juste après celles des tickets) : `taskPullRequests` lit les adresses de `task.prs` puis celles du texte avec `PR_URL_RE` — `…/<dépôt>/pull-requests/<n>` (Bitbucket DC et Cloud), `…/<dépôt>/pull/<n>` (GitHub), `…/<dépôt>/-/merge_requests/<n>` (GitLab) —, coupées après le numéro (`/overview`, `/diff`, `/files` tombent) et dédoublonnées sur cette adresse sans tenir compte de la casse. Libellé `<dépôt> #<n>` précédé de `ICON.pullRequest`, le nom du dépôt seul tronqué au-delà de 200 px (`.pr-chip-repo`) pour que le numéro reste lisible. Trois au plus ; les suivantes font un `<span class="pr-chip-more">+n PR</span>`, non cliquable, dont l'infobulle les nomme. Même mécanique que les tickets (`<a data-act="open-url">`, `draggable="false"`), sans adresse de serveur à connaître.
- `taskTextHtml` rend cliquables les adresses `http(s)` du texte d'une tâche (`<a data-act="open-url">` → `openUrl`), sans ouvrir l'édition — le dispatcher prend l'action la plus proche du clic.

## Remarques sur Organizator

Le carnet (bouton « Remarques » de l'en-tête) est une tâche virtuelle côté UI : `taskById("__feedback__")` renvoie un objet fixe, jamais présent dans `tasks`, si bien que le panneau, le formulaire de lancement, la liste des sessions et le transcript sont ceux des tâches ordinaires. Ses conversations ont `taskId: "__feedback__"`.

- `remarks` (data.json) : une remarque est en attente tant que `sentAt` vaut 0 ; l'envoi la date et note la session (`sessionId`). L'historique des envoyées est effaçable d'un bouton.
- Envoi direct (bouton principal) : agent par défaut des réglages (ou le seul installé), son modèle et son effort par défaut, dossier = `settings.repoDir` / dernière session / `env.repoDir` ; le texte encore saisi devient une remarque avant l'envoi. Sans dossier connu, le formulaire s'ouvre. Le lien secondaire ouvre ce formulaire (agent, modèle, effort, dossier).
- Envoi : `startSession` avec `context` = consignes fixes (lire README et ARCHITECTURE, construire via la solution, ne pas fermer l'application qui tourne, préserver `%LOCALAPPDATA%\Organizator`, répondre en français) et `prompt` = les remarques numérotées comme dans le panneau (les lignes suivantes d'une remarque sont indentées de trois espaces), suivi d'une consigne de récapitulatif. Titre : `Remarques Organizator · <n> · <date>`.
- Envoi dans une session existante : `resumeSession` avec le même `prompt` (bouton ↪ sur la session) ; le contexte est déjà dans l'historique.
- Dossier de travail proposé : `settings.repoDir`, sinon le dossier de la dernière session du carnet, sinon `env.repoDir` (premier parent de l'exécutable contenant `Organizator.sln`).
- Bouton de l'en-tête : badge = remarques en attente ; point d'état = état le plus pressant des sessions du carnet (même règle que la pastille des cartes de tâches).

### Contexte transmis à Claude

`context` (construit côté JS) :

```
Tu travailles sur la tâche suivante, extraite d'Organizator (file de tâches de l'utilisateur).
Catégorie : <label>
Mots-clés : <noms retenus, séparés par des virgules — ligne absente si aucun>
Ce que ces mots-clés demandent :            (ligne absente si aucun ne porte de consigne)
- <nom> : <consigne, lignes suivantes indentées de deux espaces>

Équipe à lancer : …                         (bloc absent si aucun mot-clé retenu n'arme d'équipe)
- <agent> [<rôle>] (modèle …, effort …) : <mission>   (agents groupés par rôle ; parenthèse absente si rien n'est demandé ;
                                             « Pour « <mot-clé> » : » en tête si plusieurs équipes)

Travail déjà fait — ce qu’ont rendu les conversations précédentes liées à cette tâche. Lis-le avant de
commencer, lis sur le disque les rapports qu’il cite s’ils te servent, et ne refais pas ce qui est fait.
<résumé, voir « Travail déjà fait »>          (bloc absent si le formulaire n'en porte pas)

Réponds en français.
```

Le texte de la tâche n'est pas dans le contexte : il est le **premier message** (`buildPrompt`), pour que l'agent démarre dessus plutôt que d'attendre une saisie. Le formulaire de lancement le donne à relire dans une zone « Premier message » (`ui.newConvoPrompt`, remplie à l'ouverture par `buildPrompt`, Ctrl + Entrée lance) : ce qui s'y trouve est ce qui part.

```
Tâche :
<texte complet de la tâche>
```

Seul un message **identique à la tâche** la retire du contexte : elle y ferait doublon. Champ vidé (aucun message ne part, l'agent ouvre son invite et attend) ou message retouché (« commence par reproduire le bug »), `buildContext` reprend la tâche (`withTask`) — sans quoi l'agent n'aurait jamais l'énoncé. Une **reprise** passe toujours `withTask`, le texte de la tâche y étant renvoyé à jour. Côté Copilot, qui n'a pas de prompt système, l'hôte recolle les deux (contexte, ligne vide, message) en un seul `-i` : la session reçoit mot pour mot ce qu'elle recevait avant ce partage.

`title` = première ligne de la tâche, 46 caractères max.

### Travail déjà fait

Une nouvelle conversation ne part pas de rien : `openNewConvo` appelle `loadRecap`, qui réunit les tâches concernées (`priorTasksOf`) — pour une sous-tâche, la tâche parente, les sous-tâches sœurs qui la précèdent dans la file, puis elle-même ; pour une tâche de premier niveau, elle-même puis ses sous-tâches ; jamais le carnet de remarques —, ne garde que celles qui ont des conversations, et demande à l'hôte (`getRecaps`) la dernière réponse de chacune, par ordre de création. `buildRecap` compose alors le texte : par tâche, `## Tâche parente | Sous-tâche précédente | Sous-tâche | Cette tâche : <première ligne> (terminée | en cours)` et, sauf pour la tâche elle-même, le reste de son texte ; par conversation, `### Conversation « <titre> » — <agent · modèle · effort>, <date>, <état>`, `Dernière réponse de l’agent :` suivie de la réponse (`RECAP_ANSWER_MAX` = 3 000 caractères), `Rapports produits (à lire sur le disque) :` avec le chemin complet de chaque rapport (`artifactFullPath` recolle le `cwd` aux chemins relatifs), et le nombre des autres fichiers modifiés. Le contexte part sur la ligne de commande de `claude` / `copilot`, bornée à 32 Ko : `fitRecap` tient le tout sous `RECAP_TOTAL_MAX` (12 000 caractères) en raccourcissant les réponses de la plus ancienne à la plus récente (`RECAP_SHORT` = 500), puis en les omettant dans le même ordre. Côté hôte, `TranscriptAccumulator.LastAnswer` prend le texte final du dernier tour de l'agent — ce qui suit sa dernière ligne `[outil : …]`, là où il récapitule —, ou tout le tour sans ces lignes s'il n'a rien dit après ; `ClaudeSessions.GetLastAnswer` et `CopilotSessions.GetLastAnswer` lisent le fichier d'un seul tenant, avec un `SessionScan` à part, pour ne pas dérégler la lecture incrémentale du journal affiché.

Le formulaire montre le résultat dans un bloc « Travail déjà fait » (`newFormRecapHtml`, textarea `new-recap`, `ui.newConvoRecap`), avec le nombre de conversations et de rapports couverts ; « lecture… » tant que l'hôte n'a pas répondu (`ui.newConvoRecapBusy`, la réponse arrive après le rendu du formulaire, `preserveFocus` garde la saisie en cours). Le bloc est absent quand il n'y a rien à transmettre. Ce qui s'y trouve à l'envoi — retouché ou non — est ce que `buildContext` écrit, entre l'équipe et la tâche ; vidé, rien ne part ; lancé pendant la lecture, rien ne part non plus. Une reprise (`resumeSession`) ne passe pas de résumé : la session a son historique. Côté Copilot, le contexte étant le premier message, le résumé y est aussi.

Un mot-clé peut **lancer une équipe** : cochée, la case ajoute au contexte la consigne d'ouvrir aussitôt les agents décrits, en parallèle, dans la **même session** — c'est l'agent principal qui délègue (outil `Agent` / `Task`), Organizator n'ouvre pas d'autre terminal. Les sous-agents ainsi lancés sont ceux que le badge de la console compte (voir « Agents au travail »). Chaque agent porte un nom, un **rôle** (champ libre, `AGENT_ROLES` n'en propose que quelques-uns dans une `datalist`) et une mission ; `agentsByRole` les groupe par rôle dans le contexte, `teamOf` écarte ceux qui n'ont pas de nom et rend la liste vide si la case est décochée.

**Niveau d'un agent.** `model` et `effort` disent avec quel modèle l'ouvrir et quel soin attendre de lui. Vides — le cas ordinaire —, il travaille comme la session qui l'ouvre ; sinon le contexte le dit agent par agent, avec une phrase qui explique quoi en faire. **Rien n'est contraint** : comme pour le reste de l'équipe, Organizator écrit une consigne, c'est l'agent principal qui ouvre le sous-agent (l'outil `Agent` / `Task` accepte un modèle ; l'effort, lui, tient à la définition du sous-agent, d'où la consigne de le redire dans sa mission à défaut).

Le vocabulaire des deux listes vient de l'**agent de lancement** (`teamProviderId` : le réglage `provider`, pas celui de la rédaction assistée), puisque c'est lui qui ouvrira l'équipe : `teamModels` aplatit son catalogue (`catalogFor`, groupes compris), `teamEfforts` rend ses niveaux d'effort. Une valeur qui n'y figure plus — catalogue changé, agent par défaut changé — reste offerte dans la liste plutôt que d'être perdue.

Les mots-clés se gèrent dans le dialogue **Catégories** (`catsHtml`, ouvert par `ui.catsOpen`, prioritaire sur les autres dialogues) : un nom tapé puis Entrée (ou une virgule) crée le mot-clé et ouvre son éditeur (`keywordEditorHtml`, `ui.catKeywordEdit`) — nom, description, consigne, puis l'équipe (`keywordTeamHtml`, `agentRowHtml`), le tout enregistré au fil de la frappe. Ils sont normalisés et dédupliqués sans tenir compte de la casse (`normalizeKeywords`, 32 par catégorie) ; un nom vidé ne survit pas à la fermeture du dialogue. Retirer un mot-clé le retire aussi des `convo.keywords` des conversations des tâches de cette catégorie.

Ils ne sont **proposés qu'au lancement** (`newFormKeywordHtml`, sous le choix du modèle, absent pour une tâche sans catégorie et pour le carnet de remarques) : pastilles à cocher, choix multiple (`ui.newConvoKeywords`, identifiants), un « + » (`ui.newKeywordOpen`) pour créer un mot-clé sans quitter le formulaire — il est coché d'office, et peut y recevoir son équipe (case + ✦, `ui.newKeywordTeam` / `ui.newKeywordAgents`, retouche fine dans Catégories) —, et un lien vers le dialogue Catégories. Une pastille dont le mot-clé arme une équipe porte le nombre d'agents (`.kw-team-n`), comme l'icône des rapports porte le sien. Le choix est enregistré dans `convo.keywords`, affiché sous le titre de la session et repris lors d'une reprise.

## Rédaction assistée

Le bouton **✦ Rédiger** (dialogue « Nouvelle tâche », tâche en cours d'édition, éditeur d'un mot-clé, composition d'une équipe, mission d'un de ses agents) demande un texte à un agent **hors terminal** : `AgentDraft` lance la CLI en mode non interactif, lit sa sortie standard et la rend à l'UI, qui la propose sans rien enregistrer.

- Claude : `claude -p <prompt> --no-session-persistence [--model …] [--effort …] [--append-system-prompt <consignes>]`.
- Copilot : `copilot -p <consignes + prompt> --session-id=<uuid> [--model …] [--effort …]` — la CLI n'a pas de prompt système, et la session qu'elle crée est supprimée juste après (`CopilotSessionCleanup`, sans égard pour ses événements : elle n'existait que le temps de l'appel).
- L'exécutable est celui qu'`AgentLauncher` a détecté (`CommandFor`) ; les arguments passent par `ArgumentList` (pas de script, donc pas d'échappement PowerShell à refaire). Dossier de travail : le dossier de données, neutre — un dossier de projet vide peut y apparaître sous `~/.claude/projects`, sans fichier de session.
- Deux pièges : **`--bare` est à proscrire** (ce mode saute les lectures du trousseau, l'appel répond « Not logged in » alors que la session l'est), et `--no-session-persistence` est indispensable pour qu'une rédaction ne laisse pas de conversation dans `~/.claude/projects`.
- La sortie est débarrassée des codes ANSI et d'un éventuel bloc ``` encadrant. Vide ou code de retour non nul : message lisible, reconnaissant le cas « pas connecté ». Abandon au bout de 120 s (l'UI attend 150 s), processus tué avec ses enfants. Une seule rédaction à la fois (sémaphore), et le bouton est grisé pendant ce temps.
- Prompts et découpage sont côté UI : pour un mot-clé, l'agent doit rendre `Description: …` puis `Consigne: …` (format non suivi : tout est pris pour la consigne) ; pour une tâche, seul le corps est demandé, et « Garder » le pose sous la première ligne, qui reste le titre écrit par l'utilisateur. L'état vit dans `ui.draft` (`{ key, kind, target, prompt, turns, busy, text, desc, team, note, error, ms }`) : une proposition à la fois, jetée à la fermeture.
- `kind` dit quoi en faire : `composer` / `task` (corps d'une tâche), `keyword` / `new-keyword` (consigne), `team` / `new-team` (composition d'une équipe) et `agent` (mission d'un agent). Pour une équipe, l'agent doit rendre une ligne par membre, `Nom | rôle | modèle | effort | mission` ; les cases du milieu ne sont prises pour un niveau que si `tuneCell` y reconnaît un modèle du catalogue, un effort, ou un tiret (« rien de particulier ») — sinon la mission commence là, et l'ancien format à trois cases se relit inchangé. `teamVocabPrompt` donne au passage les rôles, modèles et efforts possibles, et demande de les régler sur la mission plutôt que de tout mettre au maximum. `parseTeamDraft` relit aussi « Nom [rôle] — mission » et « Nom : mission », numérotation et puces comprises, et l'encadré affiche alors la liste plutôt qu'un bloc de texte. « Garder » remplace l'équipe en conservant l'identifiant des agents dont le nom n'a pas changé (`setKeywordAgents`), pour ne pas refermer la mission qu'on était en train de lire. Une réponse illisible n'écrase rien : l'encadré propose de réessayer.
- **La proposition se discute.** `turns` garde les versions déjà rendues et ce que l'utilisateur en a dit (`{ text, note }`) ; `draftPrompt` reconstruit à chaque tour la demande de départ suivie de tout l'échange, puisque la CLI est appelée sans mémoire de session (`-p`). « Renvoyer » ajoute la version affichée et la note saisie avant de relancer, « Autre version » fait de même avec une note vide (le prompt dit alors que l'utilisateur redemande autre chose). La saisie de la note ne déclenche pas de rendu — seul l'état du bouton est touché — pour ne pas reconstruire le champ à chaque frappe.

### Atelier d'un mot-clé

Le bouton **En discuter** (`kw-chat` dans l'éditeur d'un mot-clé, `kw-new-chat` dans le « + » du formulaire de lancement) ouvre une discussion qui règle la **fiche** entière — nom, description, consigne, équipe — plutôt qu'un champ après l'autre. Même canal que la rédaction (`draftText`, même agent, même modèle), mais un état et un dialogue à part : `ui.chat` (`{ typeId, keywordId, launch, card, turns, note, busy, error, ms }`), rendu par `chatHtml` — `renderDialogs` lui donne la priorité sur les autres dialogues, si bien qu'il se pose par-dessus Catégories et se referme dessus.

Ce que l'agent reçoit à chaque tour (`chatPrompt`) : les **autres mots-clés de la catégorie** avec description, consigne et équipe (`catalogText`, 12 au plus — de quoi s'en inspirer sans les redoubler), la **fiche en cours** (`cardText`), puis toute la discussion (12 derniers échanges), la CLI n'en gardant rien. Il répond soit `Question: …`, soit la fiche (`Nom:`, `Description:`, `Consigne:`, `Équipe: oui|non` suivi des lignes `nom | rôle | modèle | effort | mission`, mêmes règles de relecture que pour une équipe, `teamVocabPrompt` compris).

- **Questionner est le mode normal, boucler ne l'est pas.** Le prompt du tour dépend de l'état de la discussion (`questionRun` compte les tours de questions posés d'affilée, les réponses de l'utilisateur ne le remettant pas à zéro) : tant qu'aucune fiche n'a été proposée, l'agent est invité à interroger (une à `CHAT_QUESTIONS` questions d'un coup, une ligne `Question: …` chacune), et une fiche encore vide lui dit explicitement qu'il vaut mieux demander que deviner ; une fois une fiche posée, on lui demande la fiche revue, **sans** lui interdire de questionner si l'utilisateur le réclame ou s'il lui manque quelque chose d'irremplaçable ; à `CHAT_RUN` tours de questions d'affilée, le prompt le lui dit en clair et réclame la fiche, sauf demande expresse de l'utilisateur. C'est un remplacement de la borne « une seule question, au premier tour », qui empêchait bien la boucle mais rendait l'atelier sourd à une demande de questions.
- **« Questionne-moi »** (`chat-ask` → `askChat`) n'est pas un mode : il pousse dans la discussion un tour utilisateur qui demande des questions, précédé de ce qui était déjà tapé. C'est donc le transcript — la seule chose que l'agent relit — qui porte la demande, sans drapeau à maintenir dans l'état.
- `parseQuestions` relit une ligne `Question: …` par question ; à défaut d'étiquette, une liste dont plusieurs lignes portent un « ? » en est une aussi ; sinon tout le texte fait une seule question. Une réponse hors protocole n'est donc jamais perdue — elle s'affiche comme un message (`parseChatReply`), en liste dès qu'il y a plusieurs questions.
- `parseCard` relit les étiquettes ligne à ligne (la consigne peut tenir sur plusieurs lignes) et récupère l'équipe avec `parseTeamDraft` ; si des lignes « nom | rôle | mission » ont glissé dans la consigne faute d'un `Équipe:`, elles en sont extraites. `mergeCard` garde ce qu'une fiche partielle ne redit pas.
- « Garder la fiche » (`keepChat`) écrit tout d'un coup et rouvre l'éditeur sur le mot-clé ; depuis le lancement (`launch`), elle remplit le formulaire au lieu d'enregistrer. Un nom déjà porté par un autre mot-clé de la catégorie n'est pas repris — il disparaîtrait à la normalisation, qui déduplique — et un toast le dit.
- **Rien de la discussion n'est conservé** : `ui.chat` meurt à la fermeture, rien ne part dans `data.json`. Rouvrir l'atelier plus tard repart de la fiche telle qu'elle est alors, retouches manuelles comprises — c'est la reprise voulue, sans historique à stocker ni à faire vieillir.

Deux détails d'affichage tiennent à ce que l'interface se redessine entièrement à chaque clic : les animations d'apparition ne sont posées qu'à l'ouverture (classe `enter` sur `.panel`, `.dialog` et `.new-form`), sans quoi cocher un mot-clé rejouerait le fondu du formulaire — il clignotait ; et le rayon de bordure « pilule » du thème (`.input { border-radius: 999px }`) est ramené à `--radius-md` pour les `textarea`, dont le rayon suivait la hauteur au point de donner des coins en arcs de cercle.

### Reprise d'une session déjà ouverte

`resumeSession` n'ouvre pas systématiquement un terminal. Si la session n'a **rien à recevoir** (`prompt` vide) et qu'`AgentProcessScanner` connaît le processus qui la porte, `AgentWindows` cherche sa fenêtre et la ramène au premier plan : la réponse vaut alors `{ focused: true }` et aucun second agent n'est lancé sur le même fichier de session. Avec un `prompt` à remettre (remarques envoyées dans une session existante), la reprise se fait comme avant : seul un `--resume` sait transmettre le message.

La fenêtre ne se trouve pas directement : elle n'appartient jamais au processus de l'agent. `AgentWindows` remonte la chaîne des parents (instantané `CreateToolhelp32Snapshot`, six niveaux au plus) jusqu'au processus qui possède une fenêtre de console — `ConsoleWindowClass` pour une console classique, `PseudoConsoleWindow` quand Windows Terminal héberge la session. Dans ce second cas la vraie fenêtre est le propriétaire racine de la pseudo-console (`GetAncestor`/`GA_ROOTOWNER`), c'est-à-dire la fenêtre Windows Terminal. Elle est restaurée si elle était réduite, puis passée au premier plan.

Cette fenêtre-là groupe souvent une dizaine de sessions en onglets : la ramener devant sans plus montrerait la session que l'utilisateur avait laissée, pas la sienne. `TerminalTabs` active donc l'onglet, en deux temps :

1. **Quel onglet ?** Le titre d'un onglet est celui de la console qu'il héberge, que l'agent réécrit à sa guise — glyphe d'activité devant (`✳`, `◑`…), troncature vers 45 caractères : le comparer au titre de la session échouerait. L'hôte lit donc le titre de la console elle-même (`AttachConsole` le temps d'un `GetConsoleTitle`, puis `FreeConsole`), qui donne mot pour mot ce que l'onglet affiche. Organizator n'ayant pas de console, l'emprunt réussit toujours ; il demande à ignorer `Ctrl+C` avant de s'attacher, pour ne pas recevoir celui du terminal, et sérialise ces lectures (une console attachée à la fois par processus).
2. **L'activer.** Windows Terminal n'offre aucune commande pour cela, mais il expose ses onglets en **UI Automation** : chacun est un `TabItem` dont le nom est le titre affiché et qui porte le motif `SelectionItem` — `Select()` l'amène devant. Le nom est comparé au titre lu, à l'identique d'abord, puis sans le glyphe d'activité (il a pu changer entre-temps). Deux onglets du même nom ne sont pas départageables : aucun n'est activé, `tab` porte alors leur titre et l'UI dit lequel activer, plutôt que d'emmener l'utilisateur sur la jumelle.

**Terminal qu'on vient d'ouvrir.** Sous Windows 11, Windows Terminal est le terminal par défaut : le `powershell.exe` lancé par une reprise lui est confié, et il le range volontiers en **onglet d'une fenêtre déjà ouverte**, restée derrière Organizator. L'utilisateur ne voyait rien venir et cliquait une seconde fois — ce second clic trouvait enfin la session et la ramenait. Désormais `AgentLauncher.ResumeSession` rend le PID du PowerShell (`null` sous `wt.exe`, qui ne fait que relayer) et `BridgeHost.BringLaunchedForwardAsync` appelle `AgentWindows.FocusWhenShownAsync` : la fenêtre est cherchée toutes les 150 ms (8 s au plus, abandon si le processus meurt) par la même remontée que ci-dessus, puis ramenée devant et son onglet activé, sans retarder la réponse. Le balayage des processus ne voyant l'agent qu'après quelques secondes, le PID est aussi retenu (`_launchedTerminal`, 2 min) : un second clic dans l'intervalle ramène ce terminal au lieu d'en lancer un second sur la même session. Il est oublié dès que le balayage voit l'agent vivant — un PowerShell `-NoExit` survit à l'agent qui quitte, il ne faut pas le prendre pour la session.

UI Automation demande quelques centaines de millisecondes : la recherche part dans un `Task.Run` (six secondes au plus) une fois la fenêtre déjà devant, jamais sur le fil de l'interface. Son échec ne coûte qu'un clic. La réponse porte `tabActivated: true` quand l'onglet a été amené devant, et `tab` vide quand il n'y a rien à faire — onglet activé, ou fenêtre qui ne groupe pas ses sessions (console classique, onglet unique).

Pour le carnet de remarques, `context` est un texte fixe (consignes du dépôt) et `prompt` porte les remarques ; voir « Remarques sur Organizator ».

### Script PowerShell généré (hôte)

```powershell
$Host.UI.RawUI.WindowTitle = 'Organizator — <titre>'
Set-Location -LiteralPath '<cwd>'
$ctx = @'
<contexte, tel quel>
'@
$ctx = [regex]::Replace($ctx, '(\\*)"', '$1$1\"')
if ($ctx -match '\s') { $ctx = [regex]::Replace($ctx, '(\\+)$', '$1$1') }
& claude --dangerously-skip-permissions --session-id '<uuid>' --name '<titre>' --model '<modèle>' --effort '<niveau>' --append-system-prompt $ctx
```

Pour une reprise : `& claude --dangerously-skip-permissions --resume '<uuid>' [--model '<modèle>'] [--effort '<niveau>'] --append-system-prompt $ctx`.
Avec un `prompt`, un second here-string `$msg` (mêmes deux lignes de protection) est ajouté en argument positionnel final : `… --append-system-prompt $ctx $msg`, à la création comme à la reprise ; claude ouvre la session et traite ce message aussitôt.
Avec Copilot : `& '<chemin>\copilot.exe' --allow-all --session-id=<uuid> --name '<titre>' [--model '<modèle>'] [--effort '<niveau>'] -i $ctx`, et à la reprise `--resume=<uuid>` sans `-i`. Copilot n'ayant pas de prompt système, un `prompt` est fusionné au contexte dans `$ctx` (contexte, ligne vide, message) à la création ; à la reprise, `$ctx` ne contient que le message et `-i $ctx` est écrit.
`--model` et `--effort` ne sont écrits que si une valeur a été choisie ; `--append-system-prompt` / `-i` que si le contexte n'est pas vide (PowerShell 5.1 supprime un argument vide, l'option resterait sans valeur).
Les apostrophes dans les chaînes simples sont doublées (`'` → `''`). Le here-string `@'…'@` n'a pas besoin d'échappement (le terminateur `'@` doit être seul en début de ligne).
Les deux lignes `[regex]::Replace` compensent un défaut de Windows PowerShell 5.1 : il n'échappe pas les guillemets doubles quand il transmet un argument à un exécutable natif, si bien qu'un texte de tâche contenant `"` arrivait tronqué et découpé. Elles appliquent les règles de `CommandLineToArgvW` (antislashs doublés devant un guillemet, guillemet échappé, antislashs finaux doublés quand PowerShell entourera l'argument de guillemets). Le titre passé à `--name` subit le même traitement côté hôte (`AgentLauncher.NativeArg`).

Commande de lancement : `powershell.exe -NoExit -NoLogo -ExecutionPolicy Bypass -File "<script.ps1>"` avec `WorkingDirectory = cwd`, nouvelle console. Si `settings.terminal == "wt"` et que `wt.exe` existe : `wt.exe -d "<cwd>" powershell.exe -NoExit -NoLogo -ExecutionPolicy Bypass -File "<script.ps1>"`.

Environnement hérité : au démarrage, l'hôte retire de son propre environnement les marqueurs qu'une session Claude Code pose dans ses processus enfants (`InheritedEnvironment` : `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET` / `_TOKEN`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `AI_AGENT`) et note dans `host.log` ceux qu'il a trouvés. Lancé depuis une session Claude Code (par exemple par l'agent des remarques après une publication), Organizator les transmettrait sinon à chaque `claude` qu'il ouvre ; celui-ci se croirait session enfant et n'enregistrerait pas sa transcription (« Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker ») : conversation illisible dans le panneau et impossible à reprendre. Les variables que l'utilisateur fixe lui-même dans `~/.claude/settings.json` (`env`) ne sont pas touchées : `claude` les réapplique à son démarrage.

Même passage, mêmes causes : les variables qui coupent la couleur (`NO_COLOR`, `FORCE_COLOR`, `CLICOLOR`, `CLICOLOR_FORCE`) sont retirées elles aussi. Claude Code pose `NO_COLOR=1` dans ses enfants pour lire leur sortie sans codes ANSI ; hérité, il rendait **entièrement gris** chaque terminal ouvert depuis Organizator, l'agent y suivant la règle de `supports-color`. Elles ne sont retirées que si elles ne figurent **pas** dans l'environnement persistant de l'utilisateur ou de la machine (`EnvironmentVariableTarget.User` / `Machine`, c'est-à-dire le registre) : un réglage voulu est respecté, un réglage hérité d'un parent ne l'est pas.

## Mode développement

- `Organizator.exe --wwwroot <dossier>` sert l'UI depuis ce dossier au lieu des ressources embarquées (F5 dans la WebView recharge la page ; l'hôte doit autoriser F5 / Ctrl+R).
- `Organizator.exe --data <dossier>` remplace `%LOCALAPPDATA%\Organizator`.
- Dans un navigateur ordinaire (sans `window.chrome.webview`), l'UI utilise un **shim** : persistance dans `localStorage`, sessions simulées, `pickFolder` via `prompt()`, `readArtifact` rend un rapport Markdown de démonstration (`window.__fakeArtifact` impose une autre réponse). Ceci permet de développer et tester l'UI dans Chrome. Le cadre isolé du lecteur tourne dans un autre processus : une capture `--headless --screenshot` à temps virtuel le montre vide, il faut piloter la page par le protocole DevTools (`--remote-debugging-port`) et attendre en temps réel.
